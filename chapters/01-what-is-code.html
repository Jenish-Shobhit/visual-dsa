What is code?

A program is a sequence of actions. To understand it, watch what changes after each action.

8 minute lesson · One interactive machine

Imagine a counter on your desk. It shows 2. You add 3, then tell a friend the result. The interesting thing is not the final 5; it is the little chain of events that made 5 inevitable.

total = 2
total = total + 3
show(total)

Those lines are a tiny program. The first gives the name total a value. The second reads its old value, adds 3, and stores the result under the same name. The third reads the value and sends it to an output. To run a program is to perform those actions in order.

Before you step: What would change if the second line came after show(total)? Keep your guess in mind while you trace the machine.

There are three things to track.

Where we are. A machine needs to know which instruction runs next. Call this the instruction pointer or program counter. In the figure it is the orange marker. It moves forward after each instruction. Later, a decision may send it somewhere else; that is how the same program can take different paths.

What is remembered. A line can store a value that a later line reads. In this example, the name total lets us talk about that stored value. Treat the value shown in the memory panel as a snapshot after the highlighted line has run. Before the first line, there is no useful value there.

What leaves the program. A value in memory is not automatically visible to a person. Here show(total) copies the current value to the output panel. The exact way output works depends on the environment: a screen, a file, a speaker, or another program. The distinction between stored state and observable output matters whenever you debug.

The equals sign is an action.

In school mathematics, x = x + 1 looks impossible. In code-like pseudocode, assignment means: evaluate the right side using the current state, then replace the value named on the left. The two occurrences of total in total = total + 3 play different roles. The right one is read; the left one is written.

Some languages use a different symbol for assignment, and real languages have precise rules for names, types, and errors. This guide starts with a deliberately small, language-neutral machine so the essential changes are visible. Every figure is a model: useful because it leaves details out, dangerous only if we forget which details it leaves out.

How can text make a physical computer act?

The three lines above are written for people. A real computer cannot directly execute an English sentence. A programming language gives the text exact rules. An interpreter can read and carry out those rules, or a compiler can translate them into lower-level instructions. At the bottom, circuits represent bits with physical states and carry out simple operations such as moving data, comparing values, and adding. Many small, precise operations produce the behavior we call a program.

You do not need to know every circuit to reason about an algorithm. You do need a reliable model of what each step reads, writes, and emits. That model is the bridge from “I think this code works” to “I can explain why it works.”

The reusable idea: A program has a current instruction and a current state. Each step applies one rule to that state. An algorithm is a plan for those steps that solves a whole family of inputs.

Try a different input.

Set the starting value to -2 and the amount to add to 5. Predict the output before running. Then set the amount to 0. Which parts of the state change, and which do not? The same instructions work for both inputs; this is the beginning of an algorithm rather than a memorized answer.

Practice without peeking

  1. Predict the memory and output after each line: x = 4; x = x * 2; show(x). Which line first makes something visible?
