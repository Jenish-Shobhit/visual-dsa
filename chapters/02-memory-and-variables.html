02 · After instructions

Memory and variables.

A name lets one instruction find a value left by another. What gets copied depends on what the value is.

9 minute lesson · Two memory models to compare

Suppose you counted two tickets. You will need that count again later, so you give it a name:

tickets = 2
spare = tickets
tickets = tickets + 1

After the first line, tickets holds 2. The second line reads that value and stores it under spare. The third replaces the value under tickets with 3. The final state is tickets = 3 and spare = 2.

A good trace treats each line as a small transaction: read the right side from the current state, calculate, then write the left side. Do not mentally change tickets while you are still reading the right side.

Here, copying a number copies its current value. It does not create a permanent connection between the two names.

But some values lead somewhere else.

Now imagine a list of ticket prices. Two names can refer to the same list. A change made through either name is visible through the other:

prices = [4, 7]
alsoPrices = prices
alsoPrices[0] = 9
show(prices[0])  // 9

The assignment to alsoPrices copies a reference to the list, not a fresh list of numbers. The names are separate; the object they lead to is shared. Changing alsoPrices[0] changes that shared object. But alsoPrices = [1, 2] would give only that name a new list; it would not replace the object that prices still refers to.

This is the distinction between rebinding a name and mutating an object. It explains many “why did that change too?” bugs. Step through both modes in the figure; notice whether the arrows end at separate values or the same object.

Are variables boxes in real memory?

The boxes in the figure are a teaching model. A real machine stores bits at addressed locations. A programming language maps names and values onto that machine in its own way; an optimizer may even keep a value in a register or remove a name entirely. We use “a name points to a value” because it predicts the behavior we care about here, not because every language stores one literal box per variable.

In JavaScript, numbers behave like the first mode: assigning a number to another variable copies that number. Arrays and ordinary objects behave like the second mode: an assignment copies a reference. Languages differ in syntax and memory management, but the question is portable: is this a new value, a new reference to one object, or a mutation of an existing object?

The reusable idea: Draw names separately from objects. For each assignment, decide whether it replaces a name’s value or changes an object that several names may share.

Why this matters for algorithms.

An algorithm may promise to leave its input unchanged. If it receives a reference to an array and swaps elements in that array, the caller sees the swaps. If it creates a separate copy first, it uses extra time and memory. Later, when we compare “in-place” sorting with sorting that needs a second array, this distinction will be part of the cost.

Before moving on, try to explain the result of a = [1], b = a, b = [2], show(a[0]). The important question is whether the third line changes the old list or points b at a new one. Then compare it with b[0] = 2.
