Arrays
and strings.

One name can lead to many values. An index says which position you mean.

About 11 minutes · Edit the array or text in the figure

Suppose you have three scores: 4, 7, and 2. Three separate names can hold them, but a program that must visit every score would need to know every name. Put them into one ordered collection instead:

let scores = [4, 7, 2];
show(scores[1]);  // 7

The collection is an array. Its positions are numbered 0, 1, 2, so scores[1] means the value in its second position. The number in brackets is an index. Think of it as an offset: index 0 is zero steps from the beginning, index 1 is one step, and index 2 is two steps. That is why counting starts at zero.

There are three items, so scores.length is 3. The last valid index is length - 1, which is 2 here. In JavaScript, reading scores[3] gives undefined; it does not wrap back to the start. Other languages may reject an out-of-range read instead. Either way, position 3 is not a fourth item.

From the last lesson, scores holds a reference to the collection. The collection has its own identity. Assigning scores[1] = 9 changes one position in that shared collection. The reference in scores still leads to the same array, now [4, 9, 2].

Why an index can be fast.

Imagine a low-level array whose equal-sized cells sit side by side in memory. If the first 4-byte cell begins at address 1000, then position 1 begins at 1004 and position 2 at 1008. The machine can calculate an address directly:

address of item i = starting address + i × cell size
For index 2: 1000 + 2 × 4 = 1008.

No walk through positions 0 and 1 is needed to find position 2. That direct calculation is the reason a contiguous array offers constant-time indexed access in the usual algorithm model. The figure uses this 4-byte layout as a model so you can see the arithmetic.

JavaScript arrays give you the same useful indexed interface, but JavaScript does not promise that every element occupies four adjacent bytes, or that an element even has a fixed-sized physical slot. A JavaScript engine may choose different internal layouts. Keep the distinction: array as an abstract indexed collection is the behavior you write against; contiguous cells explain a common implementation and its cost.

    Let a loop visit every item.

    An index becomes more powerful when a loop moves it. To add the scores, start total at zero and start i at zero. While i < scores.length, add scores[i], then increase i by one. For [4, 7, 2], the running totals are 4, 11, and 13. When i reaches 3, the condition fails before a read of scores[3].

    let total = 0;
let i = 0;
while (i < scores.length) {
  total = total + scores[i];
  i = i + 1;
}
show(total);  // 13

    The loop has two moving facts: i tells us which position comes next, and total remembers what the earlier positions contributed. Try the empty array in the figure by clearing the number field. Its length is zero, so the body runs zero times and the sum remains zero. A loop over an empty collection should be a deliberate case, not a surprise.

    Growing changes the physical story.

    A fixed contiguous block cannot always fit another item immediately after its last slot. A growable array can keep a larger block with unused capacity. Imagine capacity 4 holding [4, 7, 2]: one slot is free. Appending 9 fills it. Appending a fifth value may require a new block, perhaps capacity 8, then copying the four old values before adding the new one.

    capacity 4 · 4 used→copy 4 values→capacity 8 · 5 used

    That one append is expensive because it copies old data. If capacity doubles each time it fills, the total copying across many appends is small relative to the number of appends: the copied block sizes form 1 + 2 + 4 + …, and their sum stays below twice the final size. This gives constant amortized work per append over the whole sequence, even though one append can take linear work. It is a model for growable arrays, not a promise about a particular JavaScript engine's exact capacity rule.

    A string has positions too, with a catch.

    For simple text, indexing feels familiar: "CAT"[0] is "C", and "CAT".length is 3. But JavaScript string indices count UTF-16 code units, not always the visible characters a reader sees. Try A😀B in the figure. It looks like three symbols, yet its JavaScript length is 4: the emoji occupies two code units. The figure shows those two indexed pieces separately.

    Array.from("A😀B") groups that emoji as one Unicode code point, so the resulting array has three entries. Even a code point is not always one visible character: some displayed symbols combine several code points. When a task says “character,” ask whether it means code units, code points, or what a person sees. For ordinary ASCII examples these counts agree, which is why the difference can stay hidden for a while.

    Arrays and strings share the idea of ordered positions, but they differ in what can change. JavaScript lets you write scores[1] = 9. A JavaScript string is immutable: writing word[1] = "o" does not replace its second code unit. To make different text, construct a new string.

    More than one moving position.

    A single index scans left to right. Sometimes two indices make a better plan. In a sorted number array, one index can start at the left and another at the right. To find a pair with a target sum, compare their values; if the sum is too small, move the left index inward, and if too large, move the right. Sorted order justifies which possibilities are discarded.

    A sliding window keeps a short consecutive range. If you already know the sum of three adjacent values, move the window right by subtracting the value that leaves and adding the new value that enters. You reuse work instead of adding the whole range again. Both techniques build on this chapter's simple idea: an index is a precise position, and changing positions changes which data a program knows.

    Keep the mental picture: a sequence has an order and a length; an index is an offset from the beginning; a loop advances that offset until it reaches the one-past-the-end boundary. The next lesson uses this to explain and prove a full algorithm.
