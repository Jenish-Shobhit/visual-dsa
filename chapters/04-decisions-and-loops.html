Decisions
and loops.

A program can choose one path, then keep choosing whether to take it again.

About 9 minutes · Try a new starting value

Suppose you have three tickets to hand out. You can write an instruction to hand out one ticket. But how should a program repeat that action exactly three times, then stop? The answer needs only two new tools: a condition that can be true or false, and a way to revisit an instruction.

let tickets = 3;
if (tickets > 0) {
  show(tickets);
}

Read the condition aloud: “Is the current value of tickets greater than zero?” With three tickets it is true, so the instruction inside the braces runs and shows 3. With zero tickets it is false, so that instruction is skipped. The braces mark the instructions controlled by the decision. We use show as the same simple output command from the first lesson; in JavaScript you would usually use console.log.

An if makes a choice once. It does not wait for tickets to change, and it does not return to check again. An else can provide a different path when the condition is false, but exactly one of the two paths runs.

Let the decision repeat.

A while loop returns to its condition after running the body. As long as the condition is true, it enters the body again. Here is the complete ticket program:

let tickets = 3;
while (tickets > 0) {
  show(tickets);
  tickets = tickets - 1;
}
show(tickets);

Before its first test, tickets is 3. The test succeeds, so the program shows 3 and stores 2. Then it goes back to the test. It shows 2, then 1. After subtracting from 1, it stores 0. The next test fails, so it skips the loop body and reaches the final show. The complete output is 3, 2, 1, 0.

Notice the order. The loop tests before every trip through the body, including the first. The subtraction changes the value used by the next test. Without it, a start of 3 would leave the condition true forever: an infinite loop. The loop does not “know” that three trips were intended. It simply follows the condition and updates you wrote.

What changes, and what stays true?

At the top of each loop trip, the current ticket count is a nonnegative whole number. Each completed trip makes it smaller by exactly one. That gives us two useful facts: the output counts down without skipping a number, and the loop must eventually reach zero. This repeated truth is an early example of a loop invariant. We will learn to use invariants to explain why algorithms work, not merely to watch them work.

Try a start of 0 in the figure. The body runs zero times because the first test is already false; the final instruction still shows 0. Try 1 and compare. A boundary input often reveals what the code really says more clearly than an ordinary input does.

A loop can also count upward. If you start at i = 0, test i < 4, and add one each trip, the body sees 0, 1, 2, 3. It never sees 4: the condition is false when i reaches 4. That “one past the last position” boundary will matter when we visit every position in an array.

Keep the mental picture: condition → perhaps enter → do one body → update state → return to condition. The condition controls whether another trip begins; it is not an instruction that runs only at the start.

Practice on paper

  1. Start with n = 4. Trace the output of while (n > 1) { show(n); n = n - 2; }. What is n when the loop ends?
  2. A loop starts at i = 0 and adds 1 each trip. Write a condition that lets the body run exactly five times. List the values of i the body sees.
  3. The ticket loop accidentally says tickets = tickets + 1. For a start of 2, explain why it does not stop. Give one change that repairs it.
