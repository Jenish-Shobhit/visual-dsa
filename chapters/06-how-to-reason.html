About 10 minutes · Test negative and empty inputs

You have a row of numbers and want the largest. For [3, 8, 5, 9, 4], your eyes see 9. A program cannot take in the whole row at once. It can inspect one position, remember the best value found so far, and update that memory when it discovers something larger.

function largest(values) {
  if (values.length === 0) return undefined;
  let best = values[0];
  let i = 1;
  while (i < values.length) {
    if (values[i] > best) best = values[i];
    i = i + 1;
  }
  return best;
}

There are two boundary choices before the main loop. An empty collection has no largest element, so this function returns undefined. For a nonempty collection, it starts best at the first actual value. The index i begins at 1 because position 0 is already included. At each later position, the program asks whether that value is larger than best, replaces best if needed, and moves to the next index.

Trace the sample: start at 3; compare 8 and keep 8; compare 5 and keep 8; compare 9 and keep 9; compare 4 and keep 9. The trace is helpful, but it only checks one row. How can we trust the function on a row we have never seen?

A promise that survives every step.

Before each comparison, best is the largest value among all positions already visited. This is the loop invariant: a statement that remains true as the loop runs. It is strong enough to explain the result and small enough to check at each step.

At the start: only position 0 has been visited, and its value is the largest among that one position. During a step: the new value is either greater than best, in which case replacing best makes it the largest of the longer visited prefix, or it is not, in which case the old best is still largest. At the end: every position has been visited, so “largest among positions visited” means largest in the entire collection. These three checks—start, preservation, finish—are a small correctness proof.

Choose a start that makes the proof true.

A tempting shortcut is let best = 0. It works for the sample row, but fails for [-6, -2, -9]: no negative value is greater than 0, so it returns 0, a value that was not even in the input. The invariant fails at the start: 0 is not “largest among visited positions.” Initializing from values[0] repairs the logic for any nonempty row, including all-negative rows. The separate empty check makes that access safe.

What if the largest value appears twice? With the comparison >, the remembered value remains the same when a tie arrives. If you also stored the index, this choice would keep the first occurrence. Using >= would keep the last. A tiny change in the condition can change the function's promise, so decide which behavior you want before writing it.

Count the work without a stopwatch.

For a nonempty row of length n, the first value initializes best. Each of the remaining n − 1 values is compared exactly once. The loop uses a fixed number of names—best and i—regardless of row length. We describe this as O(n) time and O(1) extra space. These are statements about how work and extra storage grow, not about a particular machine's seconds or bytes.

Could an algorithm always find the maximum of an unsorted row while ignoring some position? No. An unseen position might hold an arbitrarily large value, and the algorithm could not tell. In the worst case, every position must be inspected. This gives a reason the linear scan is not merely simple; for this task on an unsorted row, its order of growth cannot be beaten by another correct method.

The next chapter develops these cost ideas more carefully. For now, take two habits into every algorithm you meet: state exactly what remains true after each step, and count the work as input size changes. A colorful trace is a starting point for questions; an invariant and a cost argument tell you what the trace means.
