Linked lists.

A sequence can be stored as a trail of references, even when its pieces are scattered.

About 12 minutes · Rewire your own example

Imagine the values 4 and 9 in order. You want to put 7 between them. In an array, the order comes from positions: the next item is in the next slot. Making room may require shifting later values. A linked list stores the order another way. Each node holds a value and a next reference to another node:

head → A4: [4 | next → D1]
       D1: [9 | next → null]

head identifies the first node. Starting there and repeatedly following next visits 4, then 9, then null, which means there is no next node. The labels A4 and D1 identify nodes in our model; they are not array indices or literal machine addresses. Their alphabetical order says nothing about the list's order. Two nodes do not need neighboring memory slots to be neighbors in the sequence.

Create a new node F5 holding 7. To insert it after A4, first set F5.next = A4.next. F5 now points to D1, but the list from head is unchanged. Then set A4.next = F5. Following from the head now visits 4, 7, 9. The order of these assignments protects the old suffix. If you overwrite A4.next before saving its old destination, you no longer have a path from the head to 9.

newNode.next = previous.next;
previous.next = newNode;

This is a local operation: once you hold previous, it changes two references regardless of how long the list is. The figure lets you insert before the head, in the middle, or after the tail. Change the values and watch the reachable chain after each single assignment.

Two costs, not one.

It is easy to say “linked-list insertion is O(1)” and leave out the most important condition. If you already hold a reference to the node before the insertion point, the two link assignments are constant work. If the task gives only an index, you must start at head and follow links until you reach that node. Reaching a late position takes O(n) time. The figure separates those costs: its “next links followed” count shows what it takes to obtain the predecessor by position, while “link assignments” stays small.

That is also why the search technique from the previous chapter does not fit this structure. An array reads values[mid] directly. A singly linked list has no direct access to its middle; it must walk there. Even if the list's values are sorted, repeated walks can erase the gain from halving the index range.

Insertion before the head has its own rule: let the new node point to the old head, then change head to the new node. This works even when the old head is null, so it also inserts into an empty list. Insertion after the tail works because the tail's old next is null; the new node becomes the new end. If a program stores a separate tail reference for quick appends, it must update that too.

Removal, identity, and tradeoffs.

To remove a node after previous, use previous.next = previous.next.next, assuming the node to remove exists. To remove the head, use head = head.next. In both cases, decide what references remain to the removed node. A node that no surviving reference reaches becomes eligible for garbage collection in JavaScript; discarding a reference is not the same as instantly erasing bytes.

A list can accidentally form a cycle: if some node's next points back to an earlier node, following links may never reach null. Any traversal must account for that possibility when it receives an untrusted structure. A visited set or two pointers moving at different speeds can detect cycles; we will meet that pattern again in graphs.

Arrays use less bookkeeping per item and usually benefit from nearby memory during a scan. Lists spend space on references and follow one link at a time, but offer cheap local splicing when you already have the right node. Choose a representation by the operations you need—indexed reads, scans, frequent insertions—and by the cost of finding the position, not by a slogan that one structure is always faster.
