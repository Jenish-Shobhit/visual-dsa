Hashing.

Let a key suggest a place to look. Then make a rule for the times it guesses the same place as another key.

About 11 minutes · Change the keys and lookup target

Suppose you keep student records by ID. If the IDs are in a list, finding one record may require checking every entry. What if the ID itself could suggest where to look? With five slots, a toy rule is slot = ID % 5, the remainder after division by five. ID 12 begins at slot 2.

12 % 5 = 2
 7 % 5 = 2

Both IDs ask for slot 2. This is a collision, not a broken hash function. There are more possible IDs than slots, so some IDs must meet. A hash table needs a collision rule. Here we use linear probing: if the starting slot is occupied by a different key, try the next slot, wrapping around after the last slot. ID 7 goes to slot 3 when 12 owns slot 2.

Notice what the table stores: the key itself, or a record containing it, so a later lookup can compare keys. A matching hash result does not prove the keys match. The hash tells us where to start, and comparison tells us when to stop.

Lookup must retrace insertion.

To find 7, calculate 7 % 5 = 2. Slot 2 holds 12, so continue to slot 3. There is 7. If the target is absent, you can stop at the first slot that has always been empty: insertion would have placed the target there if it had followed the same path. Try an absent target in the lab and watch the search stop.

The same rule also explains a subtle deletion bug. If 12 is removed by turning slot 2 into an ordinary empty slot, a lookup for 7 would stop there and falsely report “absent.” A probing table leaves a special tombstone so lookups continue across deleted positions, or it repairs the probe cluster. We use no deletion in the figure, but its invariant depends on this detail.

Probing wraps around. In five slots, if key 19 starts at slot 4 and that slot is occupied, the next candidate is slot 0, then 1. The formula for the jth candidate is (hash(key) + j) % 5. This is why insertion and lookup must agree on both the hash function and the probe order. Changing either rule while entries remain in the table makes old keys unreachable unless the table is rebuilt.

When does the shortcut stay short?

The load factor is stored entries divided by slot count, written α = n / m. As a probing table gets crowded, empty slots are harder to find and clusters lengthen. Real implementations choose a hash function that distributes common keys well and grow and rehash the table before it becomes too full. Our modulo rule is only a transparent teaching example: keys with the same remainder collide by design.

Under suitable assumptions about the hash distribution and a controlled load factor, lookup and insertion take expected constant time, O(1). A worst-case run can still inspect many slots, O(n). Those are different claims: “expected” needs a distribution or randomized hash choice; it is not a guarantee that every lookup is fast. Space grows with the table, O(m). A rebuild costs O(n) at that moment, but an occasional rebuild can have a small amortized cost across many insertions.

Probe invariant: every key is reachable by starting at its hashed slot and following the probe sequence without crossing a never-used empty slot.

Another collision strategy is separate chaining: each slot points to a small collection of keys with that hash value. It trades probing and tombstones for extra links or buckets. The idea beneath both designs stays the same: a hash narrows where to look; a collision policy preserves correctness when many keys share a destination.

Integer remainder is easy to draw, but keys are often words, objects, or compound records. A real hash function converts a key into an integer while respecting equality: if two keys are considered equal, they must produce the same hash. The reverse is impossible to promise—unequal keys can share a hash. A hash table must therefore check equality after it reaches a candidate slot. In JavaScript, Map offers key-based lookup without making you choose a table size or collision scheme; our lab exposes those hidden decisions so their costs are understandable.

Linear probing tends to create clusters. Once a run of occupied slots forms, a new key landing anywhere in or just before that run extends it. This is one reason implementations keep spare capacity and choose their collision strategy carefully. If a hash function sends nearly every key to the same start, even a low overall load factor may be unhelpful. Expected constant time rests on assumptions about both distribution and occupancy.

A hash table is useful when you need exact membership or lookup by key. It gives up sorted order. If you need the smallest key, all keys in a range, or the next larger key, an ordered tree may serve the workload better. The data structure is chosen for the questions you ask of it.

Practice on paper

  1. Use seven slots and key % 7. Insert 15, 22, 8, and 29 by linear probing. Show each checked slot, including any wraparound.
  2. Keys 12 and 7 are stored in five slots as in the example. Remove 12 by making its slot ordinary empty. Trace a lookup for 7 and explain the failure. Propose a state that would let lookup continue.
  3. A table has 8 keys in 10 slots. Compute its load factor, then add one key that collides with an existing cluster. Explain why expected O(1) is a qualified claim rather than a promise about your specific probe.
