Recursion.

Finish a smaller version of the same task, then use its answer to finish this one.

About 8 minutes · Use ← → in the figure

You want 4 × 3 × 2 × 1. Instead of writing the whole product, ask for a smaller answer: factorial(4) = 4 × factorial(3). The same question repeats with a smaller number until it reaches 1.

factorial(n):
    if n == 1: return 1
    return n * factorial(n - 1)

This version expects a positive input. At factorial(1), the answer is already known. A version accepting zero would also return 1 for factorial(0). That is the base case. Without it, calls keep making smaller calls with no way to finish. Step through the figure: first the pending calls stack up, then answers travel back outward.

Each call has its own place to wait.

When factorial(4) calls factorial(3), the first call waits with its own n = 4. The call for 3 waits for 2, and 2 waits for 1. Once 1 returns, 2 computes 2 × 1, then 3 computes 3 × 2, then 4 computes 4 × 6. The call stack holds these unfinished moments.

For this example, the number of calls grows with n, so time is O(n). The stack also holds up to n calls, so extra space is O(n). Recursion is a way to organize a solution, not a promise of speed.

Ask two questions.

What input can be answered directly? How does every other call get closer to that input? If either answer is unclear, the recursion may never stop. Later, tree traversal will use recursion because each child is a smaller tree. Dynamic programming will reuse answers when the same smaller question is asked more than once.
