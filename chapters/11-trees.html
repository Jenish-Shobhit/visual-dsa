Trees.

At each node, which entire branch can a comparison rule out—and why?

Same keys, different route

Build the default keys and search for 6; predict every node visited. Then replace the insertion order with 1, 3, 6, 8, 10, 14 and search for 14. Compare the route length in the figure and explain what changed: the ordering rule or the shape.

A linked list gives each item one route forward. What if each item can lead to two smaller collections? Begin with a value called the root; below it are children, and each child can root another tree. A node with no children is a leaf. A tree has one path from its root to each node. There are no cycles and no second parent leading to the same node.

The branch choice can carry information. In a binary search tree, every value in a node's left subtree is smaller than that node, and every value in its right subtree is larger. “Subtree” matters: the rule applies to all descendants, not merely the two direct children.

          8
        /   \
       3     10
      / \      \
     1   6      14

To find 6, compare with 8 and go left; compare with 3 and go right; then find 6. At 8, the entire right subtree can be ignored because every value there is greater than 8 and therefore cannot be 6. At 3, the entire left subtree can be ignored. The comparisons are doing more than matching values: they are certifying which links cannot help.

Ordering invariant: for every node, all values reachable through its left link are smaller, and all values reachable through its right link are larger.

Insertion keeps the rule true.

Start at the root and compare the new value. Go left if smaller, right if larger, repeating until the appropriate link is empty. Put the new node there. Every comparison follows a constraint the new node must satisfy, so the final location preserves the ordering rule. In this guide's example, duplicate values need an explicit policy: a set may reject them; a multiset may store a count in the matching node. The lab uses distinct values and rejects duplicates.

The shape depends on insertion order. Insert 8, 3, 10, 1, 6, 14 and the tree branches. Insert 1, 3, 6, 8, 10, 14 into an ordinary, unbalanced BST and every new value follows the rightmost link. The result is a chain, even though the ordering invariant remains perfectly true. Try both input orders in the figure.

Height is the price of a search.

A search follows only one path. If the longest root-to-leaf path has h edges, search takes at most h + 1 node comparisons; insertion has the same path cost. The tree in the figure reports its height. A fairly balanced tree has height proportional to log n, because each level can hold roughly twice as many nodes as the previous level. A chain has height n - 1, so the same search rule may take O(n) time. The invariant guarantees correctness, but shape determines speed.

Balanced shapeAbout O(log n) links to a value.
Chain shapeUp to O(n) links to a value.

Self-balancing search trees add a second invariant to control height. AVL trees tightly limit the height difference between child subtrees; red-black trees use color rules with a looser bound. Both use rotations that change links locally while preserving the left-before-node-before-right order. They pay maintenance work during updates to guarantee logarithmic height. A plain BST does not get that guarantee merely by being a tree.

Why can a rotation change shape without scrambling sorted order? Suppose a node x has a right child y. Every key in y's left subtree lies between x and y. A left rotation makes y the parent, moves that middle subtree to become x's right subtree, and makes x the left child of y. The inorder sequence stays the same. A balancing policy decides when to rotate; the BST invariant explains why the rotation is safe.

One shape, several visit orders.

A recursive traversal works because each child roots a smaller tree. In preorder, visit the node before its subtrees. In inorder, visit left subtree, node, then right subtree. The ordering invariant makes an inorder traversal of a BST produce sorted values. In postorder, visit children before the parent, useful when a parent should be processed only after its descendants.

For the six-node example, inorder reads 1, 3, 6, 8, 10, 14. A hash table can offer quick expected lookup, but it does not give this sorted traversal or efficient range walk. An ordered tree earns its place when you need queries such as “next larger key” or “all keys from 5 to 12.” Choosing a structure means choosing which questions should be cheap.

That order also guides deletion. A leaf can simply be detached. A node with one child can be replaced by that child. A node with two children needs a value that fits between its left and right subtrees: the smallest value in its right subtree, called its inorder successor, is one choice. Copy or move that successor into the deleted node's position, then remove the successor from its old location. The details of ownership and rebalancing vary by implementation, but every case has the same goal: leave the ordering invariant true.

Boundary cases still count. The empty tree has no root, so a search returns absent without comparisons. Searching for a missing value reaches an empty child link. A duplicate policy must be chosen before insertion. These cases are easiest to reason about when the ordering invariant is stated first.

Reasoning checklist

Name the current node; state the left and right subtree constraints; compare the target; rule out one subtree; then note that the number of repeated decisions depends on tree height and therefore insertion shape.
