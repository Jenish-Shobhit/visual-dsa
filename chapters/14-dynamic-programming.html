Dynamic programming.

When smaller questions return again and again, solve each one once and keep its answer.

10 minute lesson · Build a minimum-coin table

You have coins worth 1, 3, and 4, and you need to make a total of 6 using as few coins as possible. A tempting rule is “take the largest coin that fits.” That takes 4, then 1, then 1: three coins. But 3 + 3 uses two. A choice that looks best now need not lead to the best complete answer.

Instead, ask a smaller question: if the last coin has value c, what is the fewest coins needed for amount - c? Solve that smaller amount, then add one coin. Try every coin that fits and take the best:

best[0] = 0
best[a] = 1 + min(best[a - c])
          for each coin c that fits a

If an amount cannot be made, its best value is ∞. The equation is a recurrence: it defines a state using smaller states. Notice that it relies on a precise definition of best[a]: the minimum number of coins needed to make exactly a. If the state is vague, the recurrence is hard to trust.

Why remembering changes the work.

To solve 6, you may ask for 5, 3, and 2. To solve 5, you may ask for 4, 2, and 1. The question for 2 can appear along several branches. A naive recursive search repeats it. A table stores the answer for 2 once, so every later request can read it directly.

We can fill the table from small amounts to large ones. When we compute best[a], every best[a - c] it needs has a smaller index and is already known. That gives an evaluation order. The table is not magic memory: it works because the dependency arrows all point backward.

Predict: With coins 1, 3, and 4, what should best[5] be? Which earlier state produces that answer? Then guess best[6] before stepping the figure.

Why does the recurrence find the optimum?

Take any optimal way to make amount a. It must end with some allowed coin c. Remove that coin. The remaining coins make a - c. If that remainder were not an optimal way to make a - c, we could replace it with a better one and improve the original solution—a contradiction. So at least one optimal solution is “an optimal smaller solution plus one coin.” Trying every possible last coin cannot miss it.

The fill order has its own invariant: before we start amount a, every smaller amount has its correct minimum or is known unreachable. The base case best[0] = 0 starts the chain. At each amount, testing every usable coin preserves the claim for the next amount. This is a proof by induction disguised as a table.

Keep the decision, not only the number.

A minimum count says how many coins; it does not say which coins. When a candidate improves best[a], remember that last coin too. Starting at the target, subtract the remembered coin and repeat until reaching zero. This reconstructs one optimal answer. If there are ties, the chosen answer depends on the order in which you test coins.

For target T and k coin values, the table has T + 1 states and tests at most k coins per state. The time is O(Tk); the table and remembered decisions use O(T) extra space. This is pseudo-polynomial in a numeric target: if T is written in binary, its digit count is only about log₂ T. A million-unit target has seven decimal digits but a million table positions.

The reusable recipe: Define a state. Identify its smaller dependencies. Give base cases. Choose an order that solves dependencies first. Prove each transition preserves the state’s meaning. Count states × work per state.

Dynamic programming is much broader than coin change. The deep study builds the same idea on a graph of subproblems, then examines path choices, reconstruction, and cases where a greedy rule can be proved instead.
