## Mechanisms and course corrections

| Chapter | Mechanism | Useful lesson correction |
| --- | --- | --- |
| 1. Dialogue on the Book | Frames the course around virtualization, concurrency, and persistence; learning requires rereading, exercises, and building code. | Treat an interactive visual as practice after an explanation, not as proof of understanding by itself. |
| 2. Introduction to Operating Systems *(inherited)* | The OS virtualizes CPU, memory, and devices, exposes system calls, and applies policy while managing shared resources. | Keep mechanism (“what can happen”) separate from policy (“which eligible choice happens”). |
| 3. Dialogue on Virtualization | Time sharing turns one physical resource into the illusion of many private ones. | State the shared physical resource before introducing the virtual abstraction. |
| 4. The Abstraction: The Process *(inherited)* | A process packages machine state so the OS can stop and resume a running program. | A process is more than source code: its registers, program counter, memory, and OS bookkeeping matter. |
| 5. Interlude: Process API | `fork()` makes a near-copy that resumes after the call; parent and child get different return values. `wait()` establishes a dependency; `exec()` replaces the child program. File descriptors make redirection and pipes possible. | Do not present parent/child output order as fixed unless the code synchronizes it. A shell’s power comes from composing these operations. |
| 6. Limited Direct Execution | User mode limits programs; traps enter kernel handlers and return-from-trap restores user execution. Timer interrupts let the OS regain control, and a context switch saves one execution context and restores another. | A system call is a controlled privilege transition, not an ordinary direct call into arbitrary kernel code. Distinguish the hardware trap save from the OS scheduler’s process-context save. |
| 7. Scheduling: Introduction *(inherited)* | FIFO, SJF/STCF, and round robin trade turnaround, response time, preemption, and I/O overlap. | Ask which metric matters for the workload before calling one scheduler “best.” |
| 8. Multi-Level Feedback Queue | MLFQ learns from observed CPU use: new jobs begin high, CPU-heavy jobs fall, and equal-priority jobs share round robin. Priority boosts prevent starvation; cumulative allotment accounting prevents yielding just before each quantum from gaming priority. | “Interactive” is a behavioral inference, not a property the scheduler knows in advance; tunables such as boost period require workload evidence. |
| 9. Proportional Share | Lottery scheduling gives probabilistic shares; stride scheduling is deterministic through pass values. Linux CFS chooses low virtual runtime, weights it by niceness, and uses a red-black tree for efficient runnable-task selection. | Long-run proportional fairness does not guarantee a short trace looks fair. Separate allocation policy from the data structure that implements it. |
| 10. Multiprocessor Scheduling | Per-core caches create cache affinity and coherence concerns. A single run queue is simple but lock-contended; per-core queues scale but need load balancing, often via migration or work stealing. | Cache coherence gives a consistent memory view; it does not make a multi-step data-structure update atomic. Synchronization is still required. |
| 11. Summary Dialogue on CPU Virtualization | Reconnects scheduler policy to LDE: hardware safely yields control and the OS decides which saved process state to restore. | A context switch changes the current process view; it is not a program calling another program. |
| 12. Dialogue on Memory Virtualization | Introduces the private-address-space illusion over shared physical memory. | A printed program pointer is a virtual address; do not label it a physical location. |
| 13. The Abstraction: Address Spaces | Code, heap, and stack are regions in a process address space. VM aims for transparency, efficiency, and protection while translating virtual references to physical locations. | Diagrams of stack/heap arrangement are models and conventions, not a promise of one literal layout on every platform. |
| 14. Interlude: Memory API | Stack allocation has automatic lifetime; heap allocation via `malloc()` has explicit lifetime via `free()`. Errors include missing/insufficient allocation, uninitialized reads, leaks, dangling pointers, invalid frees, and double frees. | A successful compile or one successful run does not validate memory safety. Require capacity for string terminators and check allocation failure. |
| 15. Mechanism: Address Translation | Dynamic relocation uses base plus virtual address after a bounds check. The MMU translates each reference; the OS establishes base/bounds state and handles violations. | Translate only after validation. A base register alone cannot prevent a process reaching someone else’s memory. |
| 16. Segmentation | Separate base/bounds pairs for logical regions reduce unused-space waste; segment bits choose region, with support for downward-growing stacks and permissions. Variable sizes cause external fragmentation and may require costly compaction. | Segmentation reduces one waste pattern but does not solve sparse, arbitrary address-space use; fixed-size pages address that tradeoff differently. |
| 17. Free-Space Management *(inherited)* | Allocators track free variable-sized blocks and choose placement/coalescing strategies while managing fragmentation. | Total free space is insufficient when no contiguous free extent fits the request. |
| 18. Paging: Introduction | Fixed-size virtual pages map to fixed-size physical frames through per-process page tables. A virtual address splits into VPN and offset; translation replaces VPN with PFN while preserving offset. PTEs carry validity, permissions, present, dirty, and reference state. | Paging removes external fragmentation in physical frames, but a linear page table can consume substantial memory even for unused virtual space. |
| 19. Paging: Faster Translations (TLBs) | A TLB caches VPN→PFN translations. Hits make translation fast; misses invoke hardware or software page-table lookup. Context switches need flushes or address-space identifiers; TLB reach depends on entry count and page size. | A TLB miss is not a page fault. One misses a translation cache; the other means the required page is absent from memory. |
| 20. Paging: Smaller Tables | Bigger pages reduce table entries but increase internal fragmentation. Segmented paging, multi-level tables, and inverted tables cut table space, each adding lookup complexity or different scaling limits. | Use the address bits to derive table size and levels; “hierarchical” alone does not mean a structure is always smaller or faster. |
| 21. Beyond Physical Memory: Mechanisms | Demand paging brings a page in on a page fault; present bits, page-fault handlers, swap space, and replacement free frames. Copy-on-write delays duplication after `fork()` until a write; the clock algorithm uses reference bits to find a victim. | Page faults are normal control flow in VM, but their disk I/O cost is qualitatively larger than ordinary memory or TLB misses. |
| 22. Beyond Physical Memory: Policies | Replacement asks which resident page to evict. OPT is a future-knowledge benchmark; FIFO can show Belady’s anomaly; LRU approximates locality; clock and other policies balance metadata and accuracy. Thrashing arises when working sets exceed available frames. | Do not call LRU universally optimal: it is an online approximation whose overhead and workload behavior matter. |
| 23. Complete Virtual Memory Systems | VAX/VMS combines segmentation, multi-level tables, demand-zero pages, clustered paging, and replacement policy. Linux adds mechanisms such as copy-on-write, memory-mapped zero pages, swapping, and security choices such as address randomization and page-table isolation. | A real VM is an interacting system. Explaining one PTE bit or one replacement rule alone cannot predict its observed performance or security. |
| 24. Summary Dialogue on Memory Virtualization | Synthesizes virtual addresses, page-table structures, TLB speedup, sparse address spaces, and page replacement. | When a memory benchmark has occasional high latency, include TLB behavior and faults in the hypothesis before blaming only cache or CPU speed. |
| 25. Dialogue on Concurrency | Threads access shared memory; coordinating access must preserve correctness without discarding all parallel performance. The OS both supplies primitives and is itself concurrent. | Coherence and multiple cores do not eliminate races. Begin a concurrency lesson with an interleaving that produces a wrong result. |

## Course-wide sequence

Use the book’s causal progression: a program receives a private-looking CPU and address space; privileged hardware transitions let the OS enforce that illusion; scheduler and VM policy choose among constrained alternatives; sharing reappears as the central risk once execution or data are concurrent. Interactive traces should show the saved state, the event that transfers control, the selected policy result, and the state restored afterward.
