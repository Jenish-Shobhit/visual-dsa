Decisions & loops

A program is a token walking through a map. Tests choose the road, and a road that curls back on itself is a loop. Watch the token, and you can predict any program.

  • 20 min
  • Beginner
  • Needs: bits & memory

The problem: instructions that only go forward

So far a program is a list, and the machine runs it from top to bottom. That is enough to add two numbers. It is not enough to add the numbers from 1 to 1,000,000, because you would have to write a million lines.

Drag the slider. Each line on the left is one instruction. The loop on the right stays three lines long, whatever n is.

A second problem is that the right instruction depends on the data. Show a green battery above 50 percent, amber above 20, red otherwise. The program has to choose.

Choosing and repeating are all it takes. Any program, however large, is built from three shapes, and each is easy to draw as a flowchart.

Three shapes are enough

In 1966 Corrado Böhm and Giuseppe Jacopini proved that sequence, choice and loop can express every computation a computer can do. The rest of this lesson takes the last two apart.

Questions with yes-or-no answers

A condition is a question the computer can answer with true or false. The simplest ones compare two numbers. Move a and b and watch all six comparisons answer at once.

One equals sign or two?

a = b is an instruction: put b’s value into a. a == b is a question: are they equal? Mixing them up is the oldest typo in programming.

Conditions combine. AND is true only when both parts are true, OR when at least one is, and NOT flips the answer. A truth table lists every possible input and its result.

Long before computers, telephone engineers built these with switches. Two switches in a row (in series) behave like AND. Two side by side (in parallel) behave like OR. Flip the switches, or click a row of the table.

Choosing a path: if, else if, else

An if sends the token down one of two roads. Chain several and the token works down the list until one test says yes. That test’s branch runs, and every test below it is skipped.

Put the strictest test first. Switch the figure to “Small test first” and slide to 80%: the same three branches now give the wrong answer, because the first true test wins.

A loop is a jump backwards

Underneath, a machine keeps a number, the program counter, which says which instruction is next. Normally it goes up by one. A jump writes a different number into it. Jump backwards, and the same instructions run again.

Step through six instructions that print numbers. Watch the marker on the left and the token riding the arrow when a jump is taken.

When loops were paper

The Harvard Mark I of 1944 had no jump instruction at all. To repeat a calculation, operators rewound the paper tape by hand, and sometimes glued the tape into a real loop.

The while loop: test, body, repeat

A while loop asks its question before every trip. If the answer is yes it runs the body, then asks again. When the answer is no it leaves.

The box below holds numbered tickets. Step through and watch which variable the test looks at, and when it changes.

The test runs one more time than the body

With 5 tickets the body runs 5 times but the test runs 6 times: the last test is the one that says “stop”. With 0 tickets the body runs zero times, and the test still runs once.

The for loop: three parts in one line

A for loop is a while loop with its three loose parts gathered into the header: where the variable starts, when to keep going, and how it changes. Hover or tap each part to see where it sits on the map.

How do you know a loop is right, not just that it ran? Find something that is true at the top of every trip.

Loop invariant

A loop invariant is a statement that is true every time the test runs: before the first trip, after each trip, and when the loop ends. For a running total it is “total equals the sum of every value handled so far”. When the loop ends, “so far” means “all of them”, and the invariant becomes the answer.

The loop lab

Write your own counted loop. Pick where i starts, where it stops and how it steps, then press play. The token, the code, the variables and the trace table all move together. Try “Never runs” and “Countdown”.

A useful habit: before you press play, predict how many times the body will run. A loop from a up to b with step 1 runs b − a + 1 times, or zero times if a is already bigger than b.

Off by one: the fence-post error

The most common loop bug is being wrong by exactly one. It has an old name, the fence-post problem. How many posts hold up a fence with five rails? Six.

A loop over boxes has the same trap. Boxes are numbered from 0, so n boxes end at a[n − 1]. Choose where the loop starts and whether it uses < or <=, then step through. The extra or missing trip is flagged in red.

Two habits catch most of these bugs. Check the first and the last value the loop variable takes, and count the trips on a tiny example, n = 1 or n = 2.

Infinite loops: every trip must make progress

A loop ends only if the test eventually turns false. So the body has to move something toward that. Miss this and the program runs forever, which is why the figure below gives every loop a tank of 20 units of fuel.

The bars show the distance to the exit after each trip. Choose an update line and press play. Some loops burn fuel to no end. Find the updates that reach the exit.

The safer test

i != 10 stops only on an exact hit, so a step that jumps over 10 runs forever. i < 10 stops as soon as i is past it. Prefer a range test unless you need exactness.

Loops inside loops

Put one loop inside another and the inner loop starts again from the top on every trip of the outer one. The pairs (i, j) fill a grid, one row per trip of the outer loop.

Step through and count. Then switch the inner start to i + 1: the loop now visits each pair once, a triangle.

Preview of n²

When both loops run to n, the body runs n × n times. Ten times the data means a hundred times the work. Lesson 05 gives that growth its name: .

Leaving early: break and continue

Two statements bend a loop. break leaves the whole loop at once. continue abandons only the current trip and moves on to the next item.

Run both on your own numbers. Watch the flowchart: break takes a road straight to the exit, and continue a road back to the top.

Stopping early is a real saving: break after the first match can turn a full scan into a few trips. In the worst case, when nothing matches, it still looks at everything.

Putting it together: FizzBuzz on a flowchart

The classic warm-up uses everything above: a loop counts, and a chain of tests decides what to print. For each number, print “FizzBuzz” if it divides by 15, else “Fizz” if it divides by 3, else “Buzz” if it divides by 5, else the number.

Play it and watch the token pick a different branch for each number. Why is the 15 test first?

Why 15 goes first

15 is divisible by both 3 and 5. If the 3 test came first, 15 would print “Fizz” and the chain would stop before it ever reached the 5 test. The most specific case must go first.

History

      

        
1944no jump instruction

        
Harvard Mark I operatorsthen Böhm, Jacopini (1966) and Dijkstra (1968)

        

          
The Harvard Mark I had no jump instruction. When it stopped, an operator read a register and decided whether to wind the paper tape back and run the loop again. People were the control flow. John Backus recalled a tape loop on another Harvard machine that picked up a half-twist and became a Möbius strip.

          
In 1966 Böhm and Jacopini proved that sequence, choice and loops are enough for any program. Two years later Dijkstra’s letter, retitled by its editor “Go To Statement Considered Harmful”, argued that programs should use those three shapes and not arbitrary jumps. Most languages have followed that advice ever since.

        

        
Sources: R. C. Martin, We, Programmers (2025), ch. 4–6; C. Böhm and G. Jacopini, “Flow Diagrams, Turing Machines and Languages with Only Two Formation Rules”, CACM 9(5), 1966; E. W. Dijkstra, “Go To Statement Considered Harmful”, CACM 11(3), 1968.
