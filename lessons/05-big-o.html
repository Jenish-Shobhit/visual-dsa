Complexity & Big-O

Count the work, not the seconds, and watch what happens to the count when the input grows.

  • 20 min
  • Beginner
  • Needs loops (lessons 01–03)

The problem

A directory holds 8 billion names in alphabetical order, and you need to find one. You could read from the top, one name at a time. Or you could open it in the middle, see which half the name must be in, and throw the other half away.

Both methods are correct. Race them on 32 names: on every tick, each method makes one comparison.

On 32 names the score is at most 32 against 6. Slide the directory up to 8 billion names: the scan may need 8 billion comparisons, binary search never more than 33. A faster computer cannot close a gap like that. Only a better algorithm can.

This lesson gives you the tools to see such gaps before you write any code: count the steps, then ask how the count grows when the input grows.

Count steps, not seconds

The obvious way to compare two programs is to time them. But a stopwatch measures the machine as much as the method. The same code runs a thousand times faster on a laptop than on a 1980s PC.

Change n and watch: every marker jumps by the same distance. The seconds belong to the machine. The way the work grows belongs to the algorithm.

Three words you will use all the time

A basic operation is one small step that takes a fixed time: one comparison, one addition, one array read. The input size n is how much data the algorithm gets, such as the number of items in a list. The running time T(n) is the number of basic operations the algorithm performs on an input of size n.

Build the intuition

Picture a party with n guests and three jobs to do. Drag the slider, or add guests one at a time, and watch each job’s count.

Three shapes of work

Greeting grows with the guest list: n. Handshakes grow with the number of pairs: each new guest shakes hands with everyone already there, n(n − 1)/2. Halving grows with the number of times you can cut the pile in half: about log₂ n.

Where the analogy breaks

At a party some handshakes take longer than others. In the analysis every basic operation costs the same one unit. Real machines have caches and slow instructions, so this is a simplification, but it is the right first question.

Read the cost off the code

Code shows its cost through its loops. A line that runs once costs 1. A loop that runs n times multiplies the cost of its body by n. A loop whose counter halves each time runs only about log₂ n times.

Pick n and press Run. All four snippets share one clock: each tick, every snippet that still has work does one operation.

Run a few sizes and the dots trace four shapes: flat, gently rising, straight, and bending up hard. The nested loop is still counting long after the others have stopped.

Key idea

Loops one after another add. Loops inside loops multiply. A counter that halves or doubles gives a logarithm.

Big-O, in one sentence

f(n) = O(g(n)) means: past some size n₀, f(n) stays below a constant times g(n). It names the shape of the growth and ignores the constant.

The doubling game

Here is the fastest way to feel the rungs. Double n and ask: how much more work? Press Double n a few times.

Constant work does not move. Logarithmic work gains one step. Linear work doubles, n log n a little more, and quadratic work quadruples. Exponential work squares: 22n = 2ⁿ × 2ⁿ, so a job that took a second at n = 16 takes 18 hours at 32.

A test you can run on real code

Time your program at n and at 2n. If the time doubles, it is probably linear. If it quadruples, quadratic. The ratio tells you the rung even when you cannot read the code.

Keep the biggest term

Say you count 3n + 5 steps. Big-O throws away the 3 and the 5 and calls it O(n). Zoom out and see why that is fair.

Zoom out and the + 5 vanishes: at n = 1,000 it is under 0.2 % of the total. The 3 never vanishes, but on the log–log view 3n + 5 and n run parallel. A constant factor shifts a curve. A bigger exponent tilts it, which is why n² passes 3n + 5 at n ≈ 4, and even 100n + 1000 at n ≈ 110.

Constants still matter in practice

On small inputs a simple O(n²) method with a tiny constant can beat an O(n log n) one. That is why library sorts switch to insertion sort for short runs. Big-O tells you who wins as n grows, not who wins at n = 10.

O, Ω and Θ: ceiling, floor, tight fit

Big-O is a ceiling. Its two siblings give a floor and a tight fit. Here f(n) = n²/2 + 8n + 20 is the exact step count of some algorithm. Move the constants and find where each bound starts to hold.

f(n) = O(n²) because past n₀ a constant times n² stays above it. f(n) = Ω(n²) because a smaller constant times n² stays below it. Both hold, so f(n) = Θ(n²): n² is its true growth rate.

The three bounds

O (big-O) is an upper bound. Ω (big-Omega) is a lower bound. Θ (big-Theta) is both at once: f is trapped between c₁·g and c₂·g for every n ≥ n₀.

A ceiling can be loose

f(n) is also O(n³). That is true and useless. In everyday talk, and in interviews, “O(n²)” usually means the tight rate. When precision matters, say Θ.

Best, average and worst case

For a fixed n, different inputs can cost different amounts. Linear search stops as soon as it finds the target, so where the target sits decides the count.

Best case: the target is first, 1 comparison. Worst case: it is last or missing, n comparisons. Average case: if every position is equally likely, (n + 1)/2 comparisons, which is still linear.

Two separate questions

“Which input?” picks the case: best, average or worst. “Which bound?” picks O, Ω or Θ. They mix freely: linear search’s worst case is Θ(n) and its best case is Θ(1). An average only means something when you say which inputs are likely.

Space counts too

Memory can grow with n as well. Space complexity counts the extra memory an algorithm needs beyond its input. Slide n and watch which memory grows.

A running maximum needs two variables whatever n is: O(1) extra space. A copy needs n cells. A recursion n calls deep keeps n stack frames alive at once, so it is O(n) even though it allocates no array. A table of all pairs needs n² cells.

When the diagram runs out

Write the count as a sum and simplify it. A triangle of loops (j < i) is 0 + 1 + … + (n − 1) = n(n − 1)/2, still O(n²). For recursion, draw the tree of calls and add the work on each level.

What fits in a second

Growth rates decide what is possible at all. A typical computer does around 10⁸ simple operations per second. If you have one second, how big can n be?

Turn it around: for a given n, how long does each class take? The markers sit on a time line that runs from nanoseconds to past the age of the universe.

At n = 100, n² finishes in a tenth of a millisecond. 2ⁿ needs about 4 × 10¹⁴ years, some 29,000 times the age of the universe. That wall between polynomial and exponential is why computer scientists call polynomial time “efficient”.

Why is bubble sort n(n − 1)/2 even on sorted input?

This version never stops early: pass 1 makes n − 1 comparisons, pass 2 makes n − 2, and so on down to 1. The sum is n(n − 1)/2 whatever the order. A version that stops after a pass with no swaps makes only n − 1 comparisons on sorted input, but it is still Θ(n²) in the worst case.

Where does “at most ⌊log₂ n⌋ + 1 probes” come from?

Each probe leaves at most half of the remaining candidates. After k probes at most n / 2k remain, and the search must stop once fewer than one remains. So k ≤ ⌊log₂ n⌋ + 1. Doubling n adds just one probe.

Variations and patterns

A few patterns come up again and again. Each tab has a picture and the code that produces it.

Two loops one after the other cost n + n = 2n, still O(n). A loop inside a loop costs n × n. With two inputs of sizes n and m, say O(n + m) or O(n·m): never merge them into one letter.


        
A counter that halves (or doubles) reaches its end after about log₂ n rounds. Doubling n adds one round. That is why binary search on a billion items needs only about 30 probes.

        
Split the input in half, solve each half, and combine in linear time. The tree of calls has about log₂ n levels and every level does n work in total, so merge sort is O(n log n). You will meet the full story in the divide-and-conquer lesson.

        
A loop that counts up to a number N looks linear, but the input is only the digits of N. Each extra digit multiplies the work by 10, so the loop is exponential in the size of its input. Checking whether N is prime by trying every divisor has this trap.

History

      

        
1894O is born

        
Paul BachmannDie analytische Zahlentheorie

        

          
Big-O is older than computers. The number theorist Paul Bachmann wrote O in 1894, the O standing for Ordnung, “order”, and Edmund Landau spread it in his 1909 handbook. Fifty years before that, in 1844, Gabriel Lamé proved that Euclid’s algorithm needs at most five division steps per decimal digit, perhaps the first analysis of a running time.

          
Computers made the question urgent. In 1965 Juris Hartmanis and Richard Stearns founded complexity theory, and in 1976 Donald Knuth proposed Ω and Θ so that lower and tight bounds had names too.

        

        
Sources: D. E. Knuth, “Big Omicron and Big Omega and Big Theta”, SIGACT News 8(2), 1976; J. Hartmanis and R. E. Stearns, “On the Computational Complexity of Algorithms”, Trans. AMS 117, 1965; Lamé’s theorem (1844).
