Arrays & dynamic arrays

Put values side by side in memory and any index is one multiplication away. Then watch why inserting in the middle is slow, and how doubling the storage makes appending cheap on average.

  • Beginner → intermediate
  • Needs: Big-O (lesson 05)

The problem

Your music app holds 10,000 songs. You tap song number 7,342 and it must start playing now, not after the app has looked at 7,341 other songs first. New songs also arrive all the time and join the end of the list.

So you need a list that can reach any position instantly and grow. Memory offers two ways to store a list. Pick a position below and race them.

The linked version must visit every node before the one you want. The array does arithmetic instead. That single trick is the whole reason arrays exist, and this lesson follows it to its costs: slow inserts in the middle, a full array that must move, and the surprising maths that makes appending cheap anyway.

Build the intuition

Picture a bookshelf where every book has exactly the same width and the books are packed tight from the left edge. Step through the figure: finding, inserting and running out of room all look like something you have done with real books.

Analogy: the packed bookshelf

Position i is always i book-widths from the left edge, so you can reach for it without scanning. Squeezing a book into the middle means sliding every book after it. And when the shelf is full, you buy a longer one and move all the books.

Where the analogy breaks

Real books have different widths; array elements never do. That is why an array holds values of one type, or, in Python and JavaScript, fixed-size references to values stored elsewhere. And a shelf can sometimes be extended in place, but memory right after an array usually belongs to something else.

One multiplication finds any element

Memory is one long row of numbered bytes. An array claims a single unbroken run of them, starting at its base address. Every element takes the same number of bytes, so element i starts exactly i elements after the base.

Definition

An array stores elements of equal size in contiguous memory: no gaps, in index order. So address(a[i]) = base + i × size, where size is the number of bytes per element.

Key idea

Reading or writing a[i] costs the same for i = 3 as for i = 3,000,000: one multiplication, one addition, one memory access. That is access by index.

Inserting and deleting in the middle

The no-gaps rule that makes reading fast makes editing slow. To insert at index i, every element from i to the end must move one slot right first. To delete, every element after the gap moves one slot left.

Order matters. Moving the first element first would overwrite its neighbour before that neighbour has moved. Step through all three modes, including the wrong one, and predict which value moves first.

When the array is full: grow by doubling

An array claims its run of memory up front. Its capacity is how many slots it reserved; its size is how many it uses. Appending is cheap while size < capacity: write into the next free slot.

When size = capacity there is nowhere to write, and the array cannot stretch because the next bytes belong to someone else. A dynamic array (Python's list, Java's ArrayList, C++'s vector) handles it by allocating a new block twice as big, copying every element across and freeing the old block.

Most appends cost one write. A few are expensive: the fifth append copies 4 values, the ninth copies 8. Hold that thought; the section on amortized cost shows why the expensive ones do not matter as much as they seem.

The lab

Build an array, then run any operation on it: read, search, append, insert or delete. Each run starts from the array the previous run left behind, and a full array grows before it can take a new value. Watch the counters: they are the cost.

Spikes that are already paid for

One append can copy the whole array, so its worst case is . Yet every language advertises appends as constant time. Both are true, and the chart shows how: each bar is the real cost of one append; the line is the average cost of all appends so far.

Definition

An operation has amortized cost c if every sequence of m operations, starting from empty, costs at most m × c in total. A single operation may cost more; the sequence never does.

Why do the spikes never drag the average up? Each copy doubles the room, so the next spike is twice as far away. The copies form the series 1 + 2 + 4 + … + 2k, which is less than twice its last term, and the last term is less than n. So n appends do at most n writes plus 2n copies: under 3n work in total.

The bank account: paying for copies in advance

Another way to see it, and the one that makes it click: charge every append a flat 3 coins. One coin pays for the write. The other two stay on the new element as savings. When the array doubles, the coins on the newer half pay for every copy.

Why two coins are exactly enough

Right after a doubling the array is half full. Before the next doubling, the newer half fills up with as many elements as the older half has. Each new element carries two coins: one to copy itself, one to copy an older element that spent its own coins last time. Charge 3, save 2, and every copy is prepaid.

Amortized is not "on average, if you are lucky"

There is no probability here. The bound holds for the worst sequence an adversary could pick. What it does not promise is that each append is fast: one append still copies everything. If every single operation has a deadline, such as a game frame or an audio buffer, reserve capacity up front.

Why double, and not add 10?

Growing by a fixed amount looks thrifty. It is a trap: the array fills again after a few appends, and every resize copies more than the last. Race four growth rules and count the total copies.

Adding k slots at a time resizes about n/k times, and those copies add up to roughly n²/2k: in total, so per append however large k is. Multiplying by any factor a > 1 keeps the total under a/(a − 1) × n: per append. The factor only trades copying against wasted space.

Why is the average below 3, and not exactly 3?

After n appends the copies total 1 + 2 + 4 + … + 2k = 2k+1 − 1, where 2k is the largest power of two below n. That is less than 2n, and the writes add exactly n. The average touches 3 only in the limit, just after a doubling; right before one, it sits near 2.

If insert is O(n), why do people call arrays fast?

Because shifting is a single sweep over contiguous memory, which hardware does extremely well (see the cache section below). For a few thousand elements, inserting into an array often beats a linked list whose O(1) splice first needs an O(n) walk to find the spot.

Shrinking without thrashing

If you pop most elements, you may want the memory back. The obvious rule, "halve the capacity when the array is half full", has a nasty flaw. Sit exactly at the boundary and alternate push and pop: every single operation copies the whole array.

The fix is a gap between the two triggers: grow when full, shrink only at a quarter full. After either resize the array lands half full, far from both triggers, so many cheap operations must happen before the next copy. Push and pop are both amortized again.

2D arrays are rows laid end to end

Memory has only one dimension, so a grid must be flattened. Most languages (C, C++, Python's NumPy by default) store it row-major: row 0, then row 1, then row 2. Element m[r][c] of a grid with C columns sits at index r × C + c.

Why the walking order matters: cache lines

The processor never fetches one number from main memory. It fetches a whole cache line, typically 64 bytes, and keeps a few recent lines close by. Walking an array in address order uses every number in each line it loads; jumping around wastes most of every load.

Both walks do the same 16 reads, so Big-O calls them equal. In practice the row walk can be several times faster on large grids. It is also why scanning an array beats walking a linked list whose nodes are scattered across memory.

Variations and patterns

Small changes to the rules give you cheaper operations when you can accept a trade-off.

History

      

        
1949first index registers

        
The Manchester Mark 1 team“B-lines”; then FORTRAN, 1957, and Robert Tarjan, 1985

        

          
On the UNIVAC I and the IBM 701, stepping through an array meant the program rewrote the address inside its own instructions, because the machines had no index registers. Manchester had built them in 1949, and FORTRAN in 1957 let scientists write A(I) and leave the address arithmetic to the compiler. Constant-time indexing also needed memory where every address is equally quick to reach: magnetic core, working by 1953.

          
The argument that doubling makes appends cheap on average got its general name and methods in 1985, when Robert Tarjan published “Amortized Computational Complexity”.

        

        
Sources: R. C. Martin, We, Programmers (2025), ch. 4–5; Computer History Museum, “Whirlwind computer debuts core memory”; R. E. Tarjan, “Amortized Computational Complexity”, SIAM J. Algebraic Discrete Methods 6(2), 1985.
