Strings, two pointers & windows

A string is an array of characters, and a surprising number of problems dissolve into one pass with two indices: pointers that walk toward each other, a window that slides, and sums you never add twice.

  • 18 min
  • Beginner
  • Needs: arrays

Text is an array in disguise

Is racecar the same backwards? Which seven days of a year had the best sales? Do listen and silent use the same letters? Each question is about a row of characters or numbers, and each can be answered in one pass if you scan it the right way.

A string is an array of characters, so lesson 06 still applies: positions start at 0, any character is one step away, and neighbours sit side by side. Type below to see it. Each box is one character, and underneath it is the number the machine really stores.

One slot is not always one character

An emoji needs two 16-bit code units, so JavaScript’s .length says 2 where Python’s len says 1. This lesson works with whole characters; the pointer ideas are identical either way.

There is one real difference from an array. In many languages a string is immutable: you cannot change a character, only make a new string. So s = s + c allocates a fresh block and copies everything into it. Watch what that costs in a loop.

Key idea

Copying the old string every turn costs 1 + 2 + … + n, which is about n² / 2 writes. A builder (a dynamic array of characters, then one join) writes about 2n. The rest of the lesson is about scans that never redo work like this.

Three ways to walk a row

Imagine two people at opposite ends of a corridor, walking toward each other and checking a tile as they go. Or one person reading a list while a second one stamps the keepers into a fresh list. Or a picture frame sliding along a wall and showing what is inside it. Those three walks are the whole lesson.

Where the pictures stop

People look ahead and jump. A pointer only knows the values it stands on, so every move must be justified by something already known: a sorted order, a symmetry, a rule the window must keep. That justification is what each figure below makes visible.

Converging pointers: palindromes

A palindrome reads the same forwards and backwards. Put a pointer l on the first character and r on the last. If they differ, you are done. If they match, that pair is settled, so both pointers step inward.

Invariant

At every step, every character outside s[l..r] has already been matched with its mirror image. When the pointers meet or cross, nothing is left unmatched, so the answer is yes. One mismatch answers no immediately.

The work is about n / 2 comparisons and no extra memory. Notice that the odd middle character never gets compared: it is its own mirror image.

Sorted pair sums, and the pair grid

Now a harder question. Given a sorted array, find two values that add up to a target. Brute force tries every pair, about n² / 2 sums. Two pointers do it in at most n − 1, and the picture on the right shows why they can.

The pair grid has one cell for every pair of indices, holding the sum a[i] + a[j]. A pointer move never checks a cell it skipped; it rules out a whole row or column at once.

Why a pointer may move

Say a[lo] + a[hi] is too small. a[hi] is the largest value still in play, so a[lo] is too small with any partner: row lo of the grid is dead. If the sum is too big, a[hi] overshoots even with the smallest partner, and column hi is dead. Every move kills a full row or column and no answer is ever lost. The staircase of moves ends after at most n − 1 sums.

This only works because the array is sorted. On unsorted data “too small” tells you nothing about the values further along; you would sort first (n log n) or use a hash table (lesson 11).

Race: every pair versus one staircase

Same numbers, same target, one clock. Each tick pays for one pair examined. Brute force scans the grid row by row; two pointers take their staircase and rule out the rest. Try First two values: brute force wins, and that is fair, because its cost depends on where the answer hides while the staircase never costs more than n − 1.

Sliding windows

Many questions are about a contiguous stretch: the best 3 days in a row, the longest substring with a property. A window is the stretch a[l..r]. Instead of rebuilding the answer for every stretch, slide the window one step: one value enters on the right, one leaves on the left, and the answer changes by exactly that.

Cost

Re-adding costs k additions for each of the n − k + 1 windows. Sliding costs k for the first window and 2 per slide after that. Drag the window size up: re-adding grows with k, sliding does not.

The window need not have a fixed size. For the longest substring with no repeated character, let the window grow while every character is different and shrink it from the left when a repeat appears. A table of counts tells you instantly whether the window is valid. Both pointers only ever move right.

Prefix sums: a range is a difference of two bars

Windows answer one running question. What if you get thousands of range questions about the same array: “what is the total from day 40 to day 97?” Adding up each range costs up to n. Do the adding once, and each answer becomes a subtraction.

The prefix sum P[i] is the sum of the first i values, so P[0] = 0. Each entry reuses the one before it. Then the sum of a[l..r] is the height of bar P[r + 1] minus the height of bar P[l]: everything before the range is in both bars and cancels.

Trade

You pay n additions once and n + 1 numbers of memory, and every later query costs one subtraction. If the array changes between queries the table goes stale, and lesson 23 shows a tree that repairs it in O(log n).

Frequency counts: same letters?

Two words are anagrams when they use the same letters the same number of times. You could sort both words, but you do not need order at all. Tally each letter once, then compare the two tables.

Cost: one tally per letter, then one look per distinct letter. That is linear, and it is the count table from the window lab in another costume. Slide a fixed window over a long text, keep its table up to date, and you can find every anagram of a word inside it.

Why is the window O(n) when there is a loop inside a loop?

Count the moves, not the loops. r moves right once per character: n moves. l only ever moves right and can never pass r, so it makes at most n moves in total across every run of the inner loop. The whole scan does at most 2n pointer moves. This is an amortized argument: an expensive shrink for one r is paid for by the characters that r added earlier.

Why does sliding a fixed window cost 2 per step?

The new window differs from the old one in exactly two values. Subtracting the one that left and adding the one that arrived updates the sum in two operations, however large k is. The first window costs k because nothing is there yet to reuse.

Variations and patterns

The same three walks appear under many names. Each variation below is one of them with a small twist.

To find three values that add up to zero, sort, fix the first value i, and run the converging two-pointer search on everything to its right for the target −a[i]. That is n rounds of an O(n) search: O(n²), where brute force is O(n³).


        
Read/write pointers also filter in place. The reader visits every value; the writer only advances when a value is kept. After the pass, everything left of w is the filtered array in its original order.

        
To find every anagram of “abc” inside a long text, slide a window of size 3 and keep its letter counts up to date: add the entering letter, drop the leaving one, and compare with the counts of the pattern. It combines the fixed window with the frequency table.

        
Two pointers can also walk two different sorted lists. Compare the values under the pointers, move the smaller one to the output, and advance that pointer. This is the merge step of merge sort, and it costs n + m for lists of length n and m.

        
A window can also carry a fingerprint of its contents, a number computed from the characters. Sliding updates it in O(1): remove the leaving character’s share, shift, add the entering one. Rabin and Karp used this in 1987 to compare a pattern with every window of a text, and lesson 36 builds it out.

History

      

        
1992UTF-8 on a placemat

        
Ken Thompson and Rob PikeUSENIX, January 1993

        

          
Telegraph codes of the 1870s already sent each character as a fixed group of on/off signals, and ASCII in 1963 made a string an array of 7-bit numbers with the letters in a row. Unicode broke that neat picture. In September 1992 Ken Thompson sketched UTF-8 on a diner placemat in New Jersey: ASCII characters stay one byte and others take two to four, which is why a string’s length in bytes and in characters can differ.

          
The sliding window has an older cousin with a fingerprint on it. In 1987 Michael Rabin and Richard Karp published a way to slide a hash over a text and compare a pattern in expected linear time.

        

        
Sources: M. Rabin and R. Karp, “Efficient randomized pattern-matching algorithms”, IBM J. Res. Dev. 31(2), 1987; R. Pike, “Hello World or Καλημέρα κόσμε or こんにちは 世界” (UTF-8 history); C. Petzold, Code, ch. 13.
