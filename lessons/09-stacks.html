Stacks

Touch only one end, and the last thing in is the first thing out. That single rule powers undo, nested brackets, expression evaluation and the call stack, and every operation costs O(1).

Unfinished business

You are writing an essay and need a date, so you open a browser tab. The search result is an article. The article links to a video. Four things are now in progress, and only the newest one is on your screen.

Step through what happens when you finish each one. The figure pauses once to ask you a question.

You resumed everything in the reverse of the order you interrupted it. The rule is the newest unfinished thing goes first. It shows up in nested brackets, function calls, the undo button and the browser’s back button. A structure that follows it exactly is a stack.

Plates in a dispenser

Think of the spring-loaded plate stack in a canteen. You can only add a plate to the top and only take a plate from the top. The plate at the bottom has been there longest and comes out last.

Definition

A stack is a collection that you change at one end only, the top. push(x) puts x on top, pop() removes and returns the top, peek() reads the top without removing it, and isEmpty() asks whether anything is left. The order is LIFO: last in, first out.

Where the analogy breaks

A canteen dispenser is never empty when you reach for a plate, and it never overflows. A program’s stack can do both, and the next figure lets you trigger each on purpose.

Key idea

Overflow (push on a full stack) and underflow (pop on an empty one) are the only ways a stack operation can fail. Real code checks isEmpty() before it pops.

Two ways to build one

An array-backed stack keeps its values in slots and one number, top. A linked stack keeps a chain of nodes and one pointer, head. Both do every operation in a constant number of steps, because both only ever touch the top.

A pop does not erase the array slot. It only moves top, and the old value sits there until a later push overwrites it. The array wins on memory: no pointer per value, and neighbouring values share cache lines. For a plain stack, prefer the array.

An array is fixed in size, so a stack that must grow copies itself into a bigger array when it fills up. How much bigger decides everything. Compare the two policies below and watch the price of each push.

Why doubling works

With doubling, the copies cost 4, then 8, then 16, and so on: the total never exceeds about twice the number of pushes, so the average push is O(1). Adding a fixed 4 slots copies far more often, and the total grows like n². Lesson 06 met doubling growth; the study linked at the end proves the bound.

Lab: matching brackets

Is {[()]} well-formed? Is ([)]? Every opener must be closed by the right closer, and the most recent unclosed opener must close first. That is a stack: push each opener; when a closer arrives, it must match the top.

Three ways to fail

Mismatch: the closer meets the wrong opener on top, as in (]. Underflow: a closer arrives with nothing on the stack, as in )(. Leftovers: the text ends with openers still waiting, as in (((). The matcher passes only when the stack is empty at the end.

Evaluating expressions

Normally we write the operator between its numbers: 3 + 4. In postfix (reverse Polish) notation it comes after: 3 4 +. Then (3 + 4) × 2 becomes 3 4 + 2 ×, with no parentheses at all, because the order of the tokens already says what happens first.

A stack evaluates it in one pass. A number is pushed. An operator pops the two newest numbers, combines them, and pushes the result. Watch the tree on the right: it is the expression, growing as the stack works.

Order matters for − and ÷

The first value popped is the right operand, because it arrived last. So 9 3 − is 9 − 3 = 6, not 3 − 9. Try Too few operands and Leftover value to see how a bad expression shows up as an underflow or a stack that does not end with one value.

From infix to postfix

People write 3 + 4 × 2. To get postfix, use a second stack for operators. Numbers go straight to the output. An operator waits on the stack until nothing on the stack binds more tightly than it, and only then does the waiting operator move to the output. Parentheses are walls on the stack.

Dijkstra called this the shunting-yard algorithm, after a railway yard that sorts train cars. This version handles + − × ÷ and parentheses, left to right.

Undo and redo

Undo needs the most recent action first, then the one before it. That is a stack of actions. But an undone action must not be lost: redo needs it back. So undo pops from one stack and pushes onto a second, and redo does the reverse.

Try this

Draw three shapes, undo twice, then draw a new one. The two undone shapes are gone for good: a new action starts a new future, so the redo stack is emptied. Every editor you use behaves this way.

The monotonic stack

Given daily temperatures, how many days until a warmer one? The obvious method scans right from every day. The faster method keeps a stack of days still waiting for a warmer day, and lets each new day settle every colder day on top of the stack.

The stack stays monotonic: the values never increase from bottom to top. So the first value on top that is not smaller stops the popping. Each day is pushed once and popped at most once, which is why the whole pass is O(n).

Why popping is safe

When index i beats the top t, nothing between t and i was larger (or t would have been popped earlier), so i is t’s answer. And every later value is farther away than i, so t can never get a better one. That is why t can leave the stack for good.

Variations and patterns

Change what the stack holds, or add a second stack, and the same idea answers other questions.

Back and forward are the same two-stack trick as undo and redo. The page you leave goes on the back stack; going back pushes the page you left onto the forward stack.

Keep a second stack of “smallest so far”. Each push records the new minimum, each pop removes it with its value, and getMin() is just a peek: O(1).

History

      

        
1957patent filed

        
Friedrich Bauer & Klaus Samelsonthe “cellar principle”

        

          
The stack was invented at least three times. Alan Turing sketched one for return addresses in 1945. In Munich, Bauer and Samelson patented a “cellar principle” for translating formulas in 1957, and that same year in Australia Charles Hamblin built a reverse-Polish language around a push-down list. By 1961, Dijkstra’s shunting-yard algorithm and the Burroughs B5000’s hardware stack had made it standard.

        

        
Source: Bauer and Samelson, patent DE1094019 (filed 30 March 1957); Hamblin, GEORGE (1957); Dijkstra, Mathematisch Centrum report MR 34/61 (1961).
