Hash tables

Turn a key into an array index and look it up in one step. Collisions are certain, so the whole craft is what to do when two keys want the same slot.

  • 20 min
  • Beginner
  • Needs: arrays
  • Linked lists

Finding things without searching

An array finds the item at index 7 instantly, because the index is the address. But you rarely know an index. You know a name, a username, an order number. Searching a list for one takes n looks, and even a sorted list needs about log n.

Wouldn’t it be lovely if the key told you where it lives? For small whole-number keys it can. Store the value for key k in slot k. That is called direct addressing.

Definition

A hash table stores keys in an array, and a hash function h(k) turns any key into the index where it should live. Lookup is: compute h(k), go there, look.

Direct addressing breaks the moment the keys are big. Six keys out of the numbers 0 to 99 need a 100-slot array, and 94 slots stay empty. For 10-digit phone numbers you would need ten billion slots. Press the button to fold the key space onto ten buckets.

Key idea

Pay for a table the size of the keys you store, not the keys that could exist. The price: many possible keys now share each slot, so two stored keys can land in the same one. That clash is a collision.

The hash function

Integers are easy: k mod m is always between 0 and m − 1. Words need one extra step first, turning the text into a number. Each character already has a numeric code, so the question is only how to combine them. Type any word below and watch the machine work.

What a good hash function does

Deterministic: the same key always gives the same bucket, or you could never find it again. Uniform: keys spread evenly, whatever pattern they follow. Fast: it runs on every single operation.

Uniformity is what the next figure measures. Thirty-odd keys are dropped into 13 buckets by each function. Change the function and every key glides to its new bucket.

Collisions are certain

There are more possible keys than buckets, so by the pigeonhole principle some keys must share a bucket. But collisions come far earlier than you would guess. Throw random keys into 365 empty slots, one at a time, and stop at the first clash.

With 365 slots the first collision usually arrives after about 24 keys: a table only 6% full. The chart shows why. The chance that no pair collides shrinks fast, because n keys make n(n − 1)/2 pairs, and each pair is a chance to clash.

So what

You cannot design collisions away with a bigger table or a cleverer function. Every hash table needs a plan for what happens when two keys want the same slot. There are two famous plans.

Plan A: chaining

Make every bucket the start of a linked list. A new key goes on the end of its bucket’s chain, so collisions cost nothing except a slightly longer list. To search, hash the key, then walk only that one chain.

Insert, search and delete your own keys below (whole numbers or short words). The load factor meter shows α = n / m, the average chain length. The lab pauses once to ask you a question.

Try the All in one bucket preset. Every key is a multiple of 7, so k mod 7 sends them all to bucket 0. The table has become one long linked list, and searching for an absent key walks all of it. That is the worst case: O(n).

Why the average case is still O(1)

If the hash function spreads keys evenly, the n keys share m chains, so a chain has about α = n / m entries. A successful search compares about 1 + α/2 keys and an unsuccessful one about α. Keep α below a constant and every operation costs O(1) on average.

Plan B: open addressing

No lists, no pointers: every key lives in the array itself. If the home slot is taken, try another slot, then another, following a fixed probe sequence. Lookup follows the same sequence, so it finds the key or reaches an empty slot, which proves the key is absent.

The three classic sequences differ only in how far each hop goes. Switch tabs and run the same keys: 22, 33, 44 share home slot 0 in a table of 11.

Watch α as you insert. Above about 0.7 the probe sequences get long, so the table grows: a bigger array, and every key is rehashed from scratch, because h(k) = k mod m depends on m.

Primary clustering

In linear probing a key that lands next to a filled run makes the run longer, and longer runs catch more keys. So the runs grow faster than the keys do. Quadratic and double hashing break the pattern up.

Deleting in open addressing

Deleting a key means emptying its slot, right? Not quite. Other keys may have been placed past that slot while it was full. Lookups rely on empty slots meaning “nothing further along”. Empty a slot in the middle of a probe path and you cut that path.

Three keys share home slot 3 and sit at slots 3, 4 and 5. Delete the first one, then search for the last. Try both ways of deleting.

The rule

A tombstone marks “a key was here”. Searches probe past it. Inserts may reuse it. Tombstones count toward the load, and a resize throws them away.

Load factor and resizing

Everything above depends on one number, the load factor α = n / m: keys divided by slots. Low α means short chains and short probe sequences. High α means the opposite. Chaining degrades gently. Linear probing falls off a cliff as α nears 1.

So every real table grows before α gets high: Java’s HashMap at 0.75, Python’s dict at about 0.67. Growing means allocating a bigger array and rehashing every key, which costs O(n) once. Doing it by doubling makes it rare enough that the average insert is still O(1).

Amortized O(1)

With doubling, a resize at size n moves n keys, but the next resize is n inserts away. Spread the n moves over those n inserts and each insert pays for about one extra move. Adding a constant instead means a resize every few inserts, and the average insert costs O(n).

Hash flooding

The O(1) average assumes keys do not conspire against the function. An attacker who knows it can send keys that all share a bucket, turning every lookup into a scan. Real languages hash with a random secret chosen at startup, so nobody can predict the buckets.

Where do 1 + α/2 and 1 / (1 − α) come from?

Chaining: a key that is stored sits after the keys inserted before it in its chain. Each of the other n − 1 keys shares its bucket with probability 1/m, and about half of those come earlier, so about 1 + α/2 keys are examined. For uniform probing, each probe finds an empty slot with probability 1 − α, so the expected number of probes until it finds an empty slot is 1 / (1 − α). That is the cost of an unsuccessful search, or of an insert. A successful search is cheaper, about (1/α) ln(1/(1 − α)). Linear probing is worse than that because clusters break the independence.

Order in real languages

        
A plain hash table has no useful order, since keys are scattered by the hash. Python’s dict keeps insertion order by storing entries in a separate list and letting the table hold only indexes into it. Sorted order still needs a tree.

History

      

        
1953first memo

        
Hans Peter LuhnIBM internal memo, January 1953

        

          
In January 1953 Luhn at IBM suggested turning a key into a bucket number and chaining the items that collide. About a year later another IBM group, writing an assembler for the IBM 701, hit on open addressing: if the slot is taken, try the next one. Programmers said “hash” for years afterwards, but Knuth found that nobody dared print such an undignified word until 1967.

        

        
Source: D. E. Knuth, The Art of Computer Programming, Vol. 3, §6.4, historical notes; R. Morris, “Scatter storage techniques”, CACM 11(1), 1968.
