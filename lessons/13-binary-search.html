Binary search

In sorted data, one comparison with the middle rules out half of what is left. Twenty comparisons are enough to find one value among a million, and the same trick finds boundaries and even answers.

  • Beginner
  • Needs: arrays, Big-O

Finding one value among many

You have a list of values and one you are looking for. The obvious plan is to start at the front and check every value until you hit it. That is linear search, and it works on any list, sorted or not.

The cost is one comparison per value, so up to n comparisons for n values. For a million values that is a million looks. But the row above is sorted, and linear search ignores that. Can order buy us something?

Play a game to find out. I am thinking of a whole number from 1 to 100. After each guess I tell you “higher” or “lower”. Try to find it in as few guesses as you can.

Whatever number was picked, guessing the middle of the remaining range every time finds it in at most 7 guesses. Each answer crosses out half of the numbers still standing, and 100 can only be halved about seven times before one number is left. Press Watch halving play to see it.

Halving is very, very fast

Analogy: the dictionary

To find a word you do not read from page one. You open the dictionary near the middle, see whether your word comes before or after the words on that page, and throw away the half that cannot contain it. Repeat on what is left. Each look halves the pages that could still hold your word.

How much is that worth? Watch what halving does to a million candidates. The bright bar is what could still hold the target, in the worst case.

Two things stand out. The first ten comparisons take a million down to about a thousand, and the next ten finish the job. And going from a million to a billion candidates costs only ten more comparisons, because a thousand times more data is just ten more halvings.

Where the analogy breaks

You flip a dictionary to roughly the right page because you know the alphabet. A computer only learns order from comparisons, one pair at a time. Binary search also needs random access: jumping straight to index mid. A linked list cannot do that, so binary search works on arrays, not on linked lists.

One comparison, half the array gone

Why does sorted order let you discard half? Probe any item. If it is smaller than your target, then everything to its left is smaller still and cannot be the target. If it is bigger, everything to its right is bigger still. Click an item below and see what one probe rules out.

You do not know the target’s position, so plan for the unlucky answer. Probing near an end can leave almost everything behind. Probing the middle guarantees that no more than half is left. That is why binary search always probes the middle.

Definition

Binary search keeps three indexes. lo and hi mark the range that could still contain the target. mid is the item it compares next, halfway between them. The comparison moves lo up or hi down, and the range shrinks.

The invariant

After every round, if the target is in the array, it is inside a[lo..hi]. It is true before the first round (the range is everything), and every comparison throws away only values that provably cannot be the target. When the range is empty, the target is not there.

Pick Unsorted (breaks it) above. The search follows the same rules, but “everything to the left is smaller” is now false, so it throws the target away. Sorted order is the whole trick: without it the halving argument has nothing to stand on.

The loop must also end. Each round moves lo to mid + 1 or hi to mid − 1, so the range loses at least the item just compared. It shrinks every round, and it can only shrink so many times.

Every search, drawn as one tree

Which positions binary search can probe depends only on the array’s size, never on the values. So you can draw every comparison it could ever make as a tree. The root is the middle item. Smaller targets go left, bigger targets go right, and a search falls off the bottom into one of the ∅ gaps when the target is absent.

Why the tree is short

Seven values fit in a tree of three levels, so every search finishes in at most 3 comparisons. In general a tree with k levels holds 2k − 1 values, so n values need only about log2(n + 1) levels. The tree has n + 1 leaves, one gap per absent outcome, and any method that only compares needs about log2 of the number of outcomes in yes/no answers to tell them apart.

Race: linear against binary

What it costs

Count comparisons, the way the race did. Linear search needs up to n of them, so its worst case grows as a straight line. Binary search needs at most ⌊log2 n⌋ + 1, which grows in a slow staircase: the count goes up by one each time n passes a power of two.

The staircase is so flat that a billion values need only 30 comparisons. Slide n to see how the two plans scale.

When it does not pay off

Sorting costs , so sorting just to answer one query is slower than a single linear scan. Binary search wins when you search the same data many times, or when the data arrives already sorted (a leaderboard, a log by timestamp, a phone book).

Why ⌊log₂ n⌋ + 1 exactly?

After k comparisons at most ⌊n/2k⌋ candidates remain. The search must stop once none remain, that is, when 2k > n. The smallest such k is ⌊log2 n⌋ + 1. For n = 7 that gives 3, and for n = 8 it gives 4: the tree above grows a new level exactly at powers of two.

Duplicates and boundaries

With repeated values, “find x” has more than one right answer. Exact search returns any match, whichever probe lands on one first. Usually you want a well-defined position, so binary search is bent to find a boundary instead.

Lower and upper bound

The lower bound of x is the first index whose value is ≥ x. The upper bound is the first index whose value is > x. Copies of x fill exactly the indexes from lower bound up to, but not including, the upper bound.

From these two numbers everything else follows: the first occurrence is the lower bound (if that item equals x), the last occurrence is the upper bound minus one, the count is upper minus lower, and the insert position that keeps the array sorted is the lower bound. Move the slider to a value that is missing: the two bounds meet, and the count is zero.

Half-open ranges avoid off-by-one bugs

The bound loops use hi = n and lo < hi. The range [lo, hi) includes lo but not hi, and hi may equal n, which means “past the end”. That extra position is what lets them answer “insert at the very end”.

Binary search on the answer

Nothing here needs an array. Binary search works on any question with a monotonic yes/no test: false, false, …, false, then true, true, …, true, and never back. Then the first “true” is a boundary, and halving finds it.

Example: a ship must carry parcels in the given order within D days. What is the smallest capacity that works? A capacity that works for a given D also works for any bigger capacity, so “can we ship with capacity c?” flips from false to true exactly once. Test the middle capacity, and halve.

Look at the strip when the search ends. Only a few of the candidates were ever tested; monotonicity decided all the others for free. That is the same halving as before, on an array that never has to exist.

The idea reaches into continuous problems too. If a continuous function is negative at one end of an interval and positive at the other, it crosses zero somewhere inside. Bisection halves the interval around the sign change, and each probe gains one more correct binary digit.

The bugs everyone writes

The idea takes a minute to grasp and a surprising amount of care to write. In the 1980s Jon Bentley gave professional programmers a couple of hours to code binary search from a description; about nine in ten of them got it wrong. Three bugs cause most of the damage.

Bug 1: the middle overflows. The line mid = (lo + hi) / 2 looks harmless. But with 32-bit integers, lo + hi can pass 2,147,483,647 and wrap around to a negative number. Drag the sliders and watch the sum spill out of the number line.

In 2006 Joshua Bloch reported that this bug had sat in Java’s own library for about nine years. It needs an array of more than a billion items, which was rare when the code was written and ordinary by 2006. The fix is lo + (hi − lo) / 2, where hi − lo can never overflow.

Bugs 2 and 3: the loop that never ends, and the candidate that never gets looked at. Both come from being off by one. Switch each to the fixed code and compare.

A checklist that prevents most bugs

Decide first whether the range is closed [lo, hi] or half-open [lo, hi), and keep the loop test, the starting hi and both updates consistent with that choice. Write the invariant in a comment. Check that every branch shrinks the range. Test on empty, one item, two items, a target smaller than everything and larger than everything.

History

John MauchlyMoore School Lectures · Bentley’s Programming Pearls · Bloch, 2006

John Mauchly described binary search in 1946, at the Moore School Lectures on electronic computing. Yet by Donald Knuth’s count, the first published version that worked for arrays of every length appeared only in 1960, and the first bug-free one in 1962. The early versions assumed the length was one less than a power of two.

When Jon Bentley set the task to professional programmers, about nine in ten got it wrong. In 2006 Joshua Bloch showed that even the version proved correct in Bentley’s book, and the one in Java’s standard library, failed on huge arrays: (low + high) / 2 overflows.

Sources: Knuth, The Art of Computer Programming, Vol. 3, §6.2.1 (history of binary search); J. Bentley, Programming Pearls (1986); J. Bloch, “Extra, Extra — Read All About It: Nearly All Binary Searches and Mergesorts are Broken”, Google Research Blog, 2 June 2006.

Practice

  1. Search insert position
    Easy

    Given a sorted array of distinct integers and a target, return the index where the target is, or where it would be inserted to keep the array sorted. Use O(log n) time.

  2. Count occurrences
    Easy

    In a sorted array with duplicates, count how many times x appears in O(log n) time. Which two bounds do you need?

  3. Search in a rotated sorted array
    Medium

    A sorted array was rotated at an unknown pivot, for example 6, 7, 9, 1, 2, 4. Find a target in O(log n). Which half is always sorted, and how does that tell you where to go?

  4. Split array, minimise the largest sum
    Medium

    Split an array of positive integers into k contiguous parts so that the largest part sum is as small as possible. Binary search on the answer: what is the monotonic test, and what are the search limits?

  5. Find the peak
    Hard

    An array increases and then decreases (no ties). Find the maximum in O(log n) without sorting. What yes/no test flips once, and why is this not a sorted array?
