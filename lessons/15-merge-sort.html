Merge sort & divide and conquer

Halve, sort each half, then merge in one pass: log₂ n levels costing n each, so n log n.

  • Intermediate
  • Needs: recursion

Why n² is too slow

Insertion sort is fine for a hand of cards. Give it a million records and it makes about a quarter of a trillion comparisons. Slide the size up and watch the two bars. Merge sort needs about n log₂ n comparisons, and on this scale its bar is a sliver.

The gap does not come from a faster computer. It comes from a different plan: instead of fixing the whole array at once, solve smaller copies of the same problem and combine their answers.

Divide and conquer

A divide-and-conquer algorithm has three moves. Divide the problem into smaller copies of itself. Conquer each copy by calling the same algorithm. Combine the answers into an answer for the whole. A problem small enough to answer directly is the base case.

Two sorted piles are easy to combine

Imagine two stacks of exam papers, each already sorted by name. To make one sorted stack, look at the top paper of each pile, move the one that comes first, and repeat. You never look deeper than the top two papers.

Analogy: merging two piles

If merging sorted piles is cheap, then sorting a big pile only needs sorting two smaller piles first. And a pile of one paper is already sorted. That is merge sort: divide, conquer, combine.

Where the analogy breaks

A person slides papers around on a desk. A program has to write the merged result somewhere while it is still reading both runs, so a merge needs a separate output area. That extra memory is merge sort’s price, and we come back to it under Cost.

Halve until nothing is left to sort

Dividing is the easy part: take the middle index. Keep halving every piece until each holds one value. A single value is sorted by definition, so there is nothing more to do there. Then merge the pieces back, level by level.

Odd sizes

With mid = ⌊(lo + hi) / 2⌋ the left half gets the extra value, so the two halves differ by at most one. Pick 11 values above and look at the third row: runs of 3 and 2. Halving n values takes ⌈log₂ n⌉ rounds however uneven the halves are.

The merge is where the work happens

Two sorted runs sit side by side. Because each run is sorted, its front value is its smallest. So the smallest value not yet written is always one of the two fronts. Take the smaller one, write it to the output, and advance that run’s pointer.

Invariant

At every moment the output holds the k smallest values of both runs, in order, and the next one is a front. Each comparison writes exactly one value, so merging n values takes at most n − 1 comparisons and exactly n writes: O(n), and the merge never backs up.

Ties decide stability

What if the two fronts are equal? Taking the left one keeps equal values in their original order, which makes the sort stable. Taking the right one still sorts correctly, but equal values swap places. Try both.

Add up the work: every level costs n

Each call of merge sort does its own merge and hands the rest to two smaller calls. Draw the calls as a tree and label each with the values its merge writes. Going down a level doubles the number of pieces and halves each piece, so the pieces on one level always add up to the whole array.

Key idea

Merge work per level is n. The number of merging levels is ⌈log₂ n⌉, because each level halves the piece size and you stop at size 1. Total: n log n writes, whatever the order of the input.

The same thing as a recurrence

Let T(n) be the work for n values. Two calls on half the size, plus a merge of n values: T(n) = 2 T(n/2) + n. Substitute it into itself: T(n) = n + 2·(n/2 + 2 T(n/4)) = 2n + 4 T(n/4) = 3n + 8 T(n/8) = … After k substitutions the cost is k·n + 2ᵏ T(n/2ᵏ). The recursion bottoms out when n/2ᵏ = 1, that is k = log₂ n, leaving n log₂ n + n·T(1). Each substitution is one row of the tree above.

Bottom-up: merge sort without recursion

The recursion only decides which runs to merge. You can skip it: start with n runs of length 1, merge neighbours into runs of 2, then runs of 4, and so on. For a power of two the merges are exactly the ones the recursion makes, just in a different order.


      
Bottom-up needs no call stack, which is handy on a system with a small one, and it is the form used when merging runs stored on disk or tape. With 11 values, watch the last run of 3 wait for a partner two passes later.

    


    
    

      
What it costs

      
Merge sort writes the same number of values whatever the input order, because every level writes every value; only the comparisons vary, between about ½ n log₂ n and n log₂ n. Real runs on real arrays show the difference between n log n and n².

The price: extra memory

        
The merge reads two runs and writes a third, so it needs room for a copy of the values it is merging: O(n) extra space for arrays. The recursion itself is shallow, only log₂ n calls deep. A merge of linked lists relinks nodes instead of copying, and needs no extra space.

      

      

        Where does n log₂ n − n + 1 come from?
        
A merge of n values makes at most n − 1 comparisons, because each comparison writes one value and the last value needs no comparison. Sum n − 1 over the merges at each level and add up the levels: for n a power of two that is n log₂ n − (n − 1) in total.

      

    


    
    

      
Other recursions, other trees

      
Merge sort’s tree is balanced: every level costs the same. Change how many calls you make, or how much each call combines, and the tree changes shape. Pick a recursion and compare the work on each level.

      
      

        
The three shapes

        
Compare the leaves’ work, about n raised to log₂ a, with the root’s combine work, nc. If the leaves win, the total is the leaf cost. If the root wins, the total is the root cost. If they tie, every level costs the same and you multiply by the log n levels. This is the master theorem, read off the picture.

      

    


    
    

      
Variations and patterns

      
The merge step is a tool on its own, and the sort has practical cousins.

      

        

          
          
          
          
        

        
An inversion is a pair that is out of order. While merging, every time a value from the right run is written before m values still waiting in the left run, it is out of order with exactly those m values. Add m to a counter. The merge sort finishes with the inversion count in  instead of n².

        
Recursing down to single values is wasteful: on a handful of values, insertion sort is faster than more calls and merges. Real libraries stop the recursion at a small size, or start from short runs sorted by insertion sort. Python’s and Java’s object sort, Timsort, builds on natural runs and merges them.

        
The merge works for any number of sorted runs: keep a pointer on each and take the smallest front. External sorting does exactly this. It sorts memory-sized chunks, writes them out as runs, then merges many runs at once, reading each one strictly front to back. That is why merge sort suits tapes, disks and huge files.

        
On a linked list you cannot jump to the middle, but you can walk to it, and merging only needs the fronts. Merge sort is the standard way to sort a linked list: the merge relinks the existing nodes, so it uses no extra space beyond the log n calls.

History

      

        
1945an early program

        
John von Neumann and Betty HolbertonEDVAC (1945) · UNIVAC (1951–52)

        

          
Merge sort was among the first programs written for a stored-program computer: John von Neumann wrote it in 1945 to show that EDVAC could do more than arithmetic. Donald Knuth later studied the 23-page manuscript.

          
A few years later IBM salespeople claimed that data on magnetic tape could not be sorted. Betty Holberton answered by writing a tape merge sort for UNIVAC, working it out with cards spread on her floor, and then the Sort-Merge Generator, one of the first programs that write programs. Its descendant Timsort, a merge-based hybrid from 2002, sorts objects in Python, Java and Android.

        

        
Sources: D. E. Knuth, “Von Neumann’s First Computer Program”, Computing Surveys 2(4), 1970; R. C. Martin, We, Programmers (2025), ch. 4 (Holberton and UNIVAC); the UNIVAC Sort-Merge Generator; T. Peters’s Timsort (2002).
