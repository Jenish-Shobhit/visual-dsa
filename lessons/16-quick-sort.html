Quick sort & quickselect

Pick a value, send smaller ones left and larger ones right, and repeat on each side. That one move sorts a million values in about 25 million comparisons, and it also finds the median without sorting. Whether it is fast or slow depends on a single choice: the pivot.

  • Intermediate
  • Needs: elementary sorts, recursion

Split first, sort later

The sorts in lesson 14 compare and move values one neighbour at a time, so they need up to n²/2 comparisons (insertion sort about n²/4). A million values would take half a trillion. Quick sort needs about 1.39 · n · log₂ n comparisons for large n. For the same million values the exact average is about 25 million.

The trick is to cut the job in two before doing any real work. Pick any value and call it the pivot. Send every smaller value to its left and every larger value to its right. The pivot is now exactly where it belongs, and the two sides can be sorted separately.

Try it by hand. Click a value inside a shaded group: it becomes the pivot, and the group splits around it. Keep going until every value is green.

Every comparison you paid for was one value against a pivot: a group of m values costs m − 1 comparisons to split. Pick pivots near the middle and the groups halve quickly. Pick the smallest or largest value in a group and only one value gets settled per split.

Why splitting works

Lining up a class

To line up a class by height, ask one student to stand still. Everyone shorter walks to her left and everyone taller to her right. She will never move again, and nobody on the left can end up on the right, so each side is a smaller, independent line-up. Repeat inside each side.

Three facts make the idea work. Each one is a small picture, so look at them before the mechanics.

Where the analogy breaks

A student can see at a glance who is taller. A program compares one value with the pivot at a time, and it must rearrange values inside the same array without a second list. Doing that cheaply is the whole art of partitioning.

Partition: the one operation that matters

A partition rearranges a range so that every value on one side of a split is at most the pivot and every value on the other side is at least the pivot. It takes one pass, about one comparison per value, and no extra memory.

There are two classic ways to do it. Lomuto keeps one boundary and sweeps a scanner across the range. Hoare, the original, walks two pointers towards each other. Step through both on the same numbers; the figure pauses once to ask you a question.

Lomuto invariant

Before each look at a[j]: a[lo..i] are all ≤ pivot, a[i+1..j−1] are all > pivot, a[j..hi−1] are not seen yet, and a[hi] is the pivot. Each step keeps this true. When j reaches the pivot, one last swap drops it between the two zones: its final place.

Hoare is different in one way that matters

After a Hoare partition, everything left of the split is ≤ pivot and everything right is ≥ pivot, but the pivot itself is not promised to sit on the split. So nothing is green yet, and both sides are sorted again, one of them possibly holding the pivot. Hoare usually makes fewer swaps, and it handles many equal keys better.

Then do it again on each side

After a Lomuto partition the pivot is final, so only the two sides remain. Sort each with the same procedure. A range of one value is already sorted. When every call has returned, the array is sorted, and there is nothing to merge, because each value was placed on the way down.

Each partition below is one step. The tree records every call: a node is a range, and its two children are the ranges left over on each side of its pivot.

Key idea

The total cost is the sum of the partition sizes over every call. If each partition splits its range roughly in half, the tree is about log₂ n levels deep and every level costs about n comparisons. That is where n log n comes from. The next sections show what happens when the splits are lopsided.

Best and worst case

A perfectly balanced tree has about log₂ n levels of n comparisons each: . A chain has n levels of n − 1, n − 2, … comparisons: n(n − 1)/2, which is . Every input has a best and a worst pivot; the lesson of quick sort is how to avoid the worst one.

Pivot rules differ in how easily an input can hurt them. Press Sorted below: the first-element and last-element rules turn quadratic on input that is already in order, which is common in real data. The middle element, the median of three and a random pivot stay near n log n.

Median of three has its own bad input

An adversary who knows you take the median of the first, middle and last values can still build an input that makes every split lopsided. Only a random pivot removes that: no fixed input is bad, only unlucky coin flips are.

Bad luck is rare

With a random pivot, the running time depends on the coin flips, not on the input. Below is the same sorted array of 30 values sorted again and again with fresh random pivots. The worst possible run costs 435 comparisons. Watch where the runs actually land.

Expected cost

Two values are ever compared only when one of them is the first pivot chosen from the values between them (inclusive). For values that are d places apart in sorted order that has probability 2/(d + 1). Adding these up over all pairs gives about 2 n ln n ≈ 1.39 n log₂ n comparisons in expectation, for every input. The study linked at the end proves it in a page.

Choosing a pivot

Answer the questions to walk the diagram. Most libraries pick a random pivot or the median of three, and add a safety net for the rare bad case.

Many equal values: the Dutch national flag

Lomuto puts every value equal to the pivot on the small side, so an array of all-equal values splits into 0 and n − 1 every time: quadratic. Values equal to the pivot are already in place. A three-way partition gathers them in a middle zone that is never touched again.

Edsger Dijkstra posed the puzzle with a flag: red, white and blue items in a jumble, to be sorted in one pass with three pointers and no extra array. The white items are the pivot value.

Three-way invariant

a[lo..lt−1] < pivot, a[lt..i−1] = pivot, a[i..gt] not seen yet, a[gt+1..hi] > pivot. When a big value is swapped in from the right, i does not advance: the value that arrived has not been looked at.

Now count what it saves. The bars show comparisons for each partition on four kinds of input. Look at the all-equal group: the three-way partition finishes in n comparisons.

Quickselect: find the k-th smallest

Sometimes you do not need the whole order: the median, the 90th percentile, the ten cheapest items. Partition once and look at where the pivot landed. If its index is exactly the one you want, you are done. Otherwise the answer is in one side only, so discard the other side and repeat.

How much does skipping half of the work save? Each round discards part of the array, so the work forms a shrinking series like n + n/2 + n/4 + … ≈ 2n when the splits are even. The chart counts real runs, against fully sorting the same array.

Race: quick, merge and insertion sort

Same input, three lanes, one clock. Each tick pays for one comparison or one move. Try Random, then Sorted with the last-element pivot: quick sort suddenly loses to insertion sort. Switch its pivot to the median of three and it is back ahead of merge sort (insertion sort still wins on already sorted input, because it only has to check).

So the honest summary is: quick sort is O(n log n) on average and in the worst case, and randomising the pivot makes the average hold for every input. Compared with merge sort it does no merging, moves values in place, and touches memory in order, which is why it is usually the fastest in practice.

Why is the balanced case n log₂ n?

A range of m values costs m − 1 comparisons to partition. If each split is even, level 0 has one range of n values, level 1 has two ranges that together hold about n values, and so on: every level costs about n. Halving n values down to 1 takes log₂ n levels, so the total is about n log₂ n.

Why is the worst case n(n − 1)/2?

If the pivot is always the smallest or the largest value, one side is empty and the other holds all the rest. The ranges then have sizes n, n − 1, n − 2, …, 2, and partitioning them costs (n − 1) + (n − 2) + … + 1 = n(n − 1)/2 comparisons. The recursion is n levels deep, so a naive implementation can also overflow the stack.

Variations and patterns

Real libraries never ship the textbook version. These are the changes that matter.

Draw the pivot index at random from the range. Then the running time depends on the coin flips, not on how the data is ordered, so an adversary cannot craft a slow input. It costs one random number per partition.


        
Look at a[lo], a[mid] and a[hi] and take the one that is in the middle by value. On sorted or reversed input that is the true median, so the split is perfect. It costs three comparisons per partition and is cheaper than random numbers.

        
Introsort, invented by David Musser in 1997, runs quick sort but counts the recursion depth. If it passes about 2·log₂ n, the pivots have been unlucky, so it switches that range to heapsort, which is guaranteed n log n. Tiny ranges are finished by insertion sort. C++ std::sort works this way.

        
Both recursive calls are independent, so you can recurse into the smaller side and loop on the larger one. Each recursive call then has at most half the values, so the stack is never deeper than log₂ n, even if the pivots are terrible. The time is unchanged.

        
Partitioning swaps values across long distances, so two equal values can trade places. Sort records by one field with quick sort and their earlier order is not kept. If you need stability, use merge sort, or sort with a tiebreaker such as the original index.

        
When quickselect finds the k-th smallest, the partition has already moved every smaller value to its left. So a[0..k−1] are the k smallest values, in no particular order, in expected O(n) time. Sort just those k if you need them ordered: O(n + k log k) in all.

History

      

        
1959Moscow

        
Tony HoareAlgorithms 63–65, CACM (1961)

        

          
Tony Hoare invented quick sort in 1959 as an exchange student at Moscow State University, where he needed to sort the words of Russian sentences for a machine-translation project. Back in London his boss asked him to write Shellsort; Hoare said he knew something faster, and won a bet of sixpence.

          
He published it in 1961 as Algorithms 63 (Partition), 64 (Quicksort) and 65 (Find, the quickselect of this lesson). He later said he could only describe partitioning neatly once he had learned the recursion of ALGOL 60. David Musser added introsort in 1997, and Java 7 adopted Vladimir Yaroslavskiy’s dual-pivot version in 2009. Hoare died in March 2026, aged 92.
