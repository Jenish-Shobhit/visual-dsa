Counting, radix & the n log n barrier

Any sort that works by comparing pairs needs at least n log n comparisons, and a tree of yes/no questions proves it. Then you sort a million integers in linear time anyway, by never comparing two of them.

  • 18 min
  • Intermediate
  • Needs: sorting, Big-O

Is n log n a law?

Merge sort and quicksort sort n values in about n log₂ n comparisons. A million values take about 20 million. Every clever sort you have met is stuck near that number, so it is natural to ask whether it is the floor.

Here is a job that looks easy to do faster. Twelve exam scores, each a whole number from 0 to 9, must be put in order. Give every score its own pocket, deal the cards into the pockets, and read the pockets from 0 upward.

The value is the address

The pockets never compare two scores. They use a score as a position, the way an array uses an index. That is a different kind of move than “which of these two is bigger?”, and it is what the rest of this lesson builds on.

So is n log n a law or not? Both. It is a law for algorithms that may only ask “is a smaller than b?”. It does not bind an algorithm that looks inside the keys. First you will see why the law holds.

Twenty questions, for orderings

Think of the game where a friend picks a number from 1 to 1,000 and you find it with yes/no questions. Ten questions are enough, because each answer can cut the candidates in half, and 2¹⁰ = 1,024.

Sorting is the same game. Your friend has secretly shuffled n cards, and you must name the order they came in. There are n! candidate orders, and a comparison of two cards is one yes/no question. Play the odds yourself: the friend always answers so that the bigger half survives.

Where the game is not the algorithm

A lucky friend might answer so that you finish early. The bound is about the worst case: for every sorting algorithm, some input makes the answers keep the larger half, so the algorithm cannot finish before ⌈log₂ n!⌉ questions.

Why a tree fits every comparison sort

A comparison sort learns about its input only through answers to “is x < y?”. Whatever it does next depends only on the answers so far, so its whole behaviour is a tree of questions. Bubble sort, insertion sort, merge sort and quicksort all have one, each with a different shape.

The tree must have at least one leaf per ordering. Two different inputs that need different rearrangements cannot end at the same leaf, because a leaf announces one fixed rearrangement. For three cards that means at least 6 leaves. The worst input is the deepest leaf, so the number of questions it needs is the tree’s height.

The barrier: height ≥ log₂(n!)

A binary tree of height h has at most 2h leaves: each level can at most double the count. So if a tree needs n! leaves, then 2h ≥ n!, and taking logarithms gives the bound.

The lower bound

Every comparison sort needs at least ⌈log₂ n!⌉ comparisons on some input. Since log₂ n! grows like n log₂ n, that is Ω(n log n).

How big is log₂ n! really? It sits just under n log₂ n and far below n². Drag the slider, and switch to the zoomed view to see how tightly the two n log n curves hug each other, and how the easy lower bound (n/2) log₂(n/2) follows them.

Why is log₂(n!) about n log₂ n?

Write n! = 1 · 2 · 3 ⋯ n, so log₂ n! = log₂ 1 + log₂ 2 + … + log₂ n. Every term is at most log₂ n, so the sum is at most n log₂ n. The top half of the terms, from n/2 to n, are each at least log₂(n/2), so the sum is at least (n/2) log₂(n/2). Both bounds are proportional to n log n, and that pins log₂ n! between them.

What the wall does and does not cover

The tree argument needs two things: the algorithm learns only from comparisons, and the keys could arrive in any of n! orders. Break the first assumption, by looking inside the keys, and there is no tree and no wall. Break neither, and even a perfect algorithm cannot beat n log n on average either: most leaves are deep.

Counting sort: count, add up, place

Counting sort works when every key is a whole number from 0 to k. It never compares two keys. Instead it makes three cheap passes: count how many items have each key, turn the counts into prefix sums that say where each key’s stretch of the output ends, then place every item.

Step through the classic example. The letters on repeated keys let you see later which copy is which.

What the prefix sums mean

After pass 2, count[v] is the number of items whose key is v or less. So the items with key v must fill the slots just below index count[v]: each key owns a fixed stretch of the output, shaded in the figure, before any item moves.

Why right to left?

Look at the duplicates. Two items with key 3 must land in the same stretch, and a stable sort keeps them in their input order. Placing from the right end keeps the order; placing from the left reverses it. Both outputs are sorted, and only one is stable.

Stability is not a detail

Radix sort in a few sections relies on it. If the equal keys of one pass came out shuffled, the work of the previous pass would be lost.

Radix sort: one digit at a time

Counting sort needs a small key range, and a range of a billion would need a billion counters. Radix sort fixes that by sorting on one digit at a time, so every pass only needs ten pockets. Start with the least significant digit and work left.

That order looks backwards, and it works because each pass is stable. Follow the tens pass in the lab: numbers with the same tens digit keep the order the ones pass gave them, which is already the right order for their last digit.

Break it on purpose

Switch the buckets to stack. A stack hands back its newest item first, which reverses ties. On the classic input the result is not sorted: the earlier passes’ work was undone. Radix sort is only as good as its stable inner sort.

Older than computers

Punched-card sorting machines ran this exact algorithm on the 1890 US census: a card dropped into one of ten pockets by the digit in one column, and operators sorted a many-column key by feeding the deck through once per column, right to left.

Bucket sort: spread, then tidy

What if the keys are decimals, like measurements between 0 and 1? Bucket sort cuts the interval into equal ranges, drops each number into its range with one multiplication, sorts each small bucket, and reads the buckets in order. If the data is spread evenly, each bucket holds about one number.

The catch is the distribution

Choose Clustered. Every number lands in the same bucket, and that bucket is sorted with an ordinary comparison sort, so all the work is back. Bucket sort trades a guarantee for a bet on how the data is spread.

“Linear” hides two knobs. Counting sort does about 2n + k steps, so a wide key range is expensive. Slide n and watch where counting sort stops beating an n log₂ n comparison sort.

Radix sort answers the wide-range problem: split a big key into digits and sort each digit in its own pass. A bigger base means fewer passes but a bigger count array per pass, so there is a best size in between.

When linear sorts lose

  • The key range k is huge, such as arbitrary 64-bit integers into one counting pass: the count array needs 2⁶⁴ cells.
  • The keys are not integers or digit strings, so “the key is an address” has no meaning. Sorting by a custom comparison forces a comparison sort.
  • Memory is tight. All three need O(n) extra space, while heapsort and quicksort work in place.

No contradiction

Counting sort makes n log n look beatable only because it is allowed to do more than compare: it reads a key as an array index. The lower bound is about a weaker model, and it is still true there.

Variations and patterns

These ideas come back in interviews and in real systems.

Counters need non-negative indexes. Subtract the smallest key from every key, count as usual, and add it back on the way out. The key range becomes max − min + 1, so a lone outlier still makes it huge.


        
Counting sort moves whole records, not just numbers, and its stability is the whole point: sort students by grade and those with the same grade stay in roll-number order. To sort by two fields, sort by the second field first, then stably by the first.

        
Fixed-length strings are numbers in base 26 (or 256), so LSD radix sort applies with a pass per character. Variable-length words use MSD radix sort instead: bucket by the first letter and recurse into each bucket, which is how tries and many library string sorts behave.

        
Often you never need the sorted array, only the counts: the most frequent letter, how many scores fall in each grade, whether two words are anagrams. The first pass of counting sort answers those in O(n + k) and skips the rest.

History

      

        
1954counting pass on a computer

        
Herman Hollerith, Harold H. SewardCensus tabulator (1890) · MIT thesis R-232 (1954)

        

          
Radix sort is older than electronic computers. Punched-card operators sorted a deck on a many-digit key one column at a time, least significant first, as the machine dropped each card into one of ten pockets. In 1954 Harold Seward’s MIT thesis moved the method onto computers and added the counting pass that tells each key exactly where to go.

          
The lower bound has a quieter history. Counting the n! possible orders is enough to see how many comparisons must be spent, and in 1959 Lester Ford Jr. and Selmer Johnson published merge insertion, a sort that comes very close to ⌈log₂ n!⌉ comparisons for small n.
