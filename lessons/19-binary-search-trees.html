Binary search trees

Keep every smaller key to the left and every larger key to the right, and finding anything becomes one walk down a single path: as fast as the tree is short.

  • Intermediate
  • Needs: trees and binary search

The problem: a sorted list that will not sit still

A game server keeps a live leaderboard. Every second new scores arrive, players leave, and each player asks “who is just above me?”. The scores have to stay in order while they keep changing.

A sorted array finds any score fast: binary search needs about log₂ n comparisons. But inserting a score means shifting every larger score one place to the right. A hash table inserts instantly, but it scatters keys on purpose, so it cannot tell you who is next in line.

Watch both structures take the same three new scores. Count the moves.

The tree finds the spot with the same handful of comparisons, then hangs one new node. Nothing shifts. That is the promise of a binary search tree: ordered like a sorted array, as cheap to change as a linked list, as long as the tree stays short.

Build the intuition: binary search, frozen into a tree

Analogy: write down every question

Binary search on a sorted array always asks about the middle key first, then the middle of whichever half is left. Write each possible question under the one before it, and you have drawn a binary search tree.

Step through the figure. The middles rise out of the array level by level. Then one search runs on the array and the tree at the same time, asking the same questions.

Where the picture breaks

A real binary search tree is not built from the middle outwards. It grows one insert at a time, and its shape depends on the order the keys arrive in. Feed it keys in sorted order and it folds into one long stick. You will watch that happen below.

One rule, for whole subtrees

Definitions

A node’s subtree is the node together with everything below it. A binary search tree (BST) is a binary tree where, at every node, every key in the left subtree is smaller than the node’s key and every key in the right subtree is larger.

Click any node. The two shaded regions are its left and right subtrees. The rule holds for every key in each region, all the way down, not just for the two children.

Because the rule is about whole subtrees, a tree can pass every parent–child check and still be broken. Exactly one key below is in the wrong place. Find it.

Search: every comparison throws away a subtree

To find a key, start at the root and compare. Equal: found. Smaller: it can only be in the left subtree. Larger: only in the right. Repeat until you find it or step onto an empty link.

Watch the grey regions. Each comparison rules out a whole subtree without looking at one key inside it, and the candidates counter drops.

Key idea

A search visits one node per level, so at most height + 1 nodes. Its cost depends on how tall the tree is, not on how many keys it holds.

Insert: search until you fall off

Insertion is a search that is allowed to fail. Walk down as if you were looking for the new key. When you step onto an empty link, that spot is the only place the key can go without breaking the rule. Hang a new leaf there.

Every empty link below is a dashed circle. Where does 7 go? Click the spot, then press play to watch the key drop.

No existing link changed. An insert adds exactly one link, and the new key is always a leaf. (The drawing spreads out to make room, but the tree itself only grew.)

Minimum, maximum and successor

The smallest key is as far left as you can go: follow left links until there are none. The largest is as far right as you can go.

The successor of a key is the next larger key in sorted order. If the node has a right subtree, the successor is the smallest key in it: step right once, then left as far as possible. If it has no right subtree, the successor is the lowest ancestor whose left subtree contains the node, the last node on the root-to-node path where you turned left. The predecessor is the mirror image.

Delete: three cases

Removing a key is the one operation with real cases, because a node may be holding up two subtrees. First find the node, then count its children:

  • No children (a leaf). Remove it. Nothing hangs below it.
  • One child. The child’s whole subtree moves up into its place.
  • Two children. Copy in the key of its successor, then delete the successor, which has at most one child.

Why the successor fits

The successor is the smallest key larger than the one you delete. So it is larger than everything in the left subtree and smaller than everything else in the right subtree: it fits exactly in the hole. The predecessor, the largest key on the left, works too by mirror symmetry. Thomas Hibbard showed this method in 1962.

In-order: the tree, read left to right

Walk the tree in-order: left subtree, then the node, then the right subtree. Everything on the left is smaller and everything on the right is larger, so the keys come out sorted.

Each node sits directly above its place on the number line, so the walk looks like the tree being flattened.

A sort for free

Insert n keys, then walk in-order, and you have sorted them. That is tree sort: about n log n comparisons on a random order, but n²/2 on sorted input, for the reason in the shape section below.

Range queries: every key between lo and hi

A hash table cannot answer “every score between 40 and 60” without checking every key. A BST can skip whole subtrees. At each node: if its key is greater than lo, the left subtree may hold answers; if it is less than hi, the right subtree may. Otherwise the subtree is skipped.

Drag the sliders. The grey regions are skipped without a single comparison inside them.

The walk touches the nodes on the two boundary paths plus the answers, so it costs about O(h + k) for k answers: fast when the tree is short.

Insertion order decides the shape

Every insert lands at the bottom of a search path, so the order the keys arrive in decides the shape. The same 15 keys can build a tree of height 3 or a stick of height 14.

The height of a tree is the number of links on its longest root-to-leaf path. Sorted input makes every new key the largest so far, so each one hangs off the right end: height n − 1, and a search can cost n comparisons. It is a linked list wearing a tree’s clothes.

What it costs

Every operation walks one root-to-leaf path, so it costs O(h). And h sits between ⌊log₂ n⌋, for a complete tree, and n − 1, for a stick. Random insertion orders land near the low end of that range: the average depth of a key grows like 1.39 log₂ n, and the height stays a small multiple of log₂ n.

Why is the height between ⌊log₂ n⌋ and n − 1?

Level 0 holds at most 1 node, level 1 at most 2, level d at most 2d. A tree of height h therefore holds at most 2h+1 − 1 nodes, so n keys need h ≥ ⌊log₂ n⌋. At the other end, nothing stops each level from holding a single node: that is a stick of height n − 1.

Where does 1.39 log₂ n come from?

Building a BST from a random order makes the same comparisons as quicksort with the first key as pivot: the root splits the other keys into smaller and larger, and each side repeats. Quicksort’s expected comparisons, about 2n ln n, are the total depth of all nodes. Divide by n: the average depth is about 2 ln n ≈ 1.39 log₂ n, minus a small constant (for 1024 keys the chart shows about 11). The height, the deepest node, is larger but still O(log n): about 21 for 1024 random keys, and 4.3 ln n in the limit.

Can you guarantee the short tree?

Not with a plain BST: the insertion order decides, and real data often arrives sorted (timestamps, auto-increment ids, the output of a previous sort). Self-balancing trees, the next lesson, repair the shape after each update with rotations and guarantee O(log n) height for every input.

Variations and patterns

The same walk answers many questions. Each tab changes what you remember on the way down.

What should insert do with a key that is already there? Pick a policy and state it. Reject it (a set, like this lesson). Count it in the node, so the shape never changes. Or always send equal keys to one side; that works, but repeated keys pile up into a stick and delete must choose which copy goes.


        
The floor of x is the largest key ≤ x. Walk down as in a search. Every time you step right, the node you leave is ≤ x: remember it as the best so far. When the walk falls off, the last remembered key is the floor. The ceiling is the mirror image.

        
An in-order walk finds the k-th smallest key in O(h + k). To do it in O(h), store in each node the size of its subtree. At a node whose left subtree holds L keys: if k ≤ L go left; if k = L + 1 this is it; otherwise go right looking for the (k − L − 1)-th.

        
Checking each node against its two children is the classic bug. Pass an open range (lo, hi) down instead: going left sets hi to the node’s key, going right sets lo. Every key must fall inside its range. An in-order walk that is strictly increasing is an equivalent test.

        
The lowest common ancestor of two keys is where their search paths split. From the root, if both keys are smaller go left, if both are larger go right; otherwise the current node is the answer. O(h) time and no extra space, which a general binary tree cannot match.

History

      

        
1960first published

        
P. F. Windley; A. D. Booth and A. J. T. Colin; Thomas N. HibbardSeveral inventors in the 1950s; first papers in 1960; deletion by successor in 1962

        

          
Several people invented binary search trees independently in the 1950s. The first papers appeared in 1960: P. F. Windley’s “Trees, Forests and Rearranging” in The Computer Journal, and Andrew Booth and Andrew Colin’s study of building dictionaries in Information and Control.

          
In 1962 Thomas Hibbard analysed the trees and showed how to delete a node with two children by replacing it with its successor: the method in this lesson. The trees are fast on random data and slow on sorted data, the problem the next lesson solves.

        

        
Sources: D. E. Knuth, The Art of Computer Programming, Vol. 3, §6.2.2; T. N. Hibbard, “Some Combinatorial Properties of Certain Trees With Applications to Searching and Sorting”, Journal of the ACM 9(1), 1962.
