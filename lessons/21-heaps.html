Heaps & priority queues

You rarely need everything in order, only the most urgent item, again and again. A heap keeps just enough order to hand it over instantly and repairs itself in a few swaps, inside a plain array.

  • Intermediate
  • Needs: arrays

Always the most urgent

An emergency room does not treat patients in the order they arrive. It treats the most urgent one first, and new patients keep arriving. Operating systems pick the next task the same way, and so do route finders, event simulators and data compressors.

The priority queue

A priority queue stores items with priorities and promises three operations: insert(x), peek() (look at the most urgent) and extract() (remove it). Here “most urgent” means the smallest key, a min-priority queue.

The obvious storage is a plain array. Step through both variants below: an unsorted array and an array kept sorted. Watch what the counter says about each operation.

The dilemma

Either insert is cheap and extract costs about n, or the other way round. Run n of each and you pay about n² either way. A heap makes both cost about log n.

Partial order is enough

Sorting pins down the rank of every value. A priority queue only ever asks about the top one. So keep only the order that protects the top: every parent is at most as large as its children. Nothing else is promised.

Heap property (min-heap)

In a binary tree, every node’s key is ≤ the keys of its children. A max-heap flips the comparison. Siblings and cousins may be in any order.

Follow any path from the root downwards and the keys never decrease. So the root is at most everything below it: it is the minimum. The three trees below hold the same six keys, and all three obey the rule.

Analogy: a company chart

Every manager’s salary is at most that of their reports (odd, but it is a min-heap). You can always find the lowest salary at the top, yet two teams under different managers are never compared.

A tree that lives in an array

The rule needs a tree, but a pointer-based tree wastes memory and is slow. Add one more rule instead: fill the tree level by level, left to right, with no gaps. Such a complete tree can be stored in an array, and its shape is fixed by its size alone.

Click any node or any array cell. The neighbours follow from arithmetic, with no pointers at all.

Why complete?

With no gaps, a heap of n values is only about log2 n levels tall (a million values: 20 levels). Every repair below walks one path, so it costs at most that many steps.

Hover a node in the figures from here on: its array cell lights up, and the other way round. The tree is how you think; the array is what is in memory.

Two repairs: climb and sink

Every change to a heap breaks the rule in exactly one place, and one path fixes it. To insert, put the new value in the first free slot at the end of the array, then let it sift up: while it beats its parent, swap.

To extract the minimum, the root leaves a hole. Fill it with the last value of the array, which keeps the tree complete, and let that value sift down: swap it with its smaller child while that child beats it.

Why the smaller child?

If the larger child moved up, it would sit above its smaller sibling and break the rule. Only the smaller child can safely take the parent’s seat.

Building a heap in linear time

You have n loose values. Inserting them one by one costs about n log n swaps in the worst case. Floyd’s trick is faster: put them in the array as they are, then sift down every node that has a child, from the last such node back to the root.

Half the nodes are leaves, which need nothing. A quarter sit one level above and can sink one level. Only the root can sink all the way. Watch the bars: each height level is allowed nodes × height swaps, and the total stays below n.

Why the sum is linear

A node at height h sinks at most h levels, and about n / 2h+1 nodes sit at height h. The total is at most n × Σ h / 2h+1 = n. The many cheap nodes at the bottom outweigh the few expensive nodes at the top.

Heap sort

Extracting the minimum over and over yields the values in order. Do it inside the array itself and no second array is needed: extract the maximum instead, so each value lands at the end, where the heap has just made room. Build a max-heap, then repeat: swap the root with the last heap slot, shrink the heap by one, and sift the new root down. The sorted region grows at the right while the tree shrinks.

Invariant

After k rounds, the last k slots hold the k largest values in their final places, and the first n − k slots are still a max-heap. Heap sort is in place and always about n log n, but it is not stable: long-distance swaps can reorder equal values.

Two jobs a small heap does well

Top-k of a stream. Keep the k largest values seen so far in a min-heap of size k. Its root is the weakest member of the current top k, so a newcomer only has to beat the root. Memory stays at k values however long the stream.

Merging k sorted lists. The next value of the merged output must be the first unused value of some list, so a min-heap of the k list heads always exposes it. Each output value costs one heap repair instead of a scan of all k heads.

Beyond the binary heap

d-ary heaps use wider nodes to shorten the tree, and Fibonacci heaps make decrease-key cost O(1) amortized, which speeds up Dijkstra in theory. On real hardware the humble array heap usually wins, because it is compact and cache-friendly.

Variations and pitfalls

Flip every comparison and the largest value rises to the top. Heap sort uses a max-heap because the largest value belongs at the end of the array.

To get a max-priority queue from a min-heap library, store the negated keys.

Dijkstra’s algorithm lowers the key of a vertex it already holds. Change the key in place, then sift up: the value only got better, so only its parents can now be wrong.

History

      

        
1964heapsort and build-heap

        
J. W. J. Williams and Robert FloydAlgorithm 232 (June) and Algorithm 245 (December), CACM

        

          
J. W. J. Williams introduced the binary heap in 1964 as the engine of heapsort, storing a whole tree in an array with no pointers. Six months later Robert Floyd showed how to build a heap in linear time by sifting down from the middle.

          
Priority scheduling had its most famous test in 1969, when Apollo 11’s guidance computer, overloaded during the landing, dropped low-priority jobs and kept the vital ones running.

        

        
Sources: J. W. J. Williams, “Algorithm 232: Heapsort”, CACM 7(6), 1964; R. W. Floyd, “Algorithm 245: Treesort 3”, CACM 7(12), 1964; Fredman and Tarjan on Fibonacci heaps, 1984–87.
