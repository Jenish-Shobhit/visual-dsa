Tries

Spell every word along a path of letters and let words that start alike share the start of their path. A lookup then costs one hop per letter, however many words you keep, and every word with a given prefix hangs below one node.

  • Intermediate
  • Needs: trees and hash tables

The problem: a search box that must not scan

You type ca into a search box and it suggests car, cat and cap before you finish the word. The list behind it holds every word people search for. It might be a million entries.

A hash set answers “is car in here?” instantly, but it scatters words on purpose, so it knows nothing about prefixes. To find everything starting with ca you must look at every word. Type a prefix and watch the scan.

Twenty words, twenty checks, on every keystroke. Scale that to a million words and the search box freezes. We need a structure where the prefix itself is the address.

Build the intuition: share the start of the path

Look at the words car, card, care, cat and dog. Written out, the first four repeat the same letters over and over. Step through the figure to merge everything that starts the same way.

Analogy: the paper dictionary

To find candle you do not read from A. You jump to the C thumb tab, then to ca, then can. Each letter narrows the pages you still need. A trie is those thumb tabs, nested all the way down.

Where the analogy breaks

A printed dictionary is sorted and fixed. A trie is not read by flipping, it is walked: you can add and remove words at any time, and no sorting ever happens. The order comes from the letters themselves.

What a node holds

A trie (say “try”, from retrieval) is a tree where every edge is a letter and every path from the root spells a string. Each node keeps two things: its children, one per next letter, and a flag saying whether the path ending here is a stored word.

Definitions

The root spells the empty string. A prefix is the start of a word: ca is a prefix of car. The end-of-word flag (isEnd, drawn as a green check) marks a node whose path is a word in its own right.

Flip the flag on the left and watch what changes. Nothing moves: ca is on the path either way. Only whether it counts as a word changes. Then compare three ways a node can store its children.

The flag matters because a word can also be a prefix. In the trie of car, card, care, cat and dog, the node for car is a word and has children. Try it.

The lab: insert, search, starts-with, delete

Type your own words, choose an operation and press Run. The path lights up letter by letter, new nodes grow out of their parent, and every step lights the line of code that runs. The trie keeps its state between operations, so you can build it up, query it, then take it apart.

Key idea

Every operation walks the letters of the query. The number of words stored never appears in the walk, so the cost is O(L) for a word of length L.

Why delete climbs back up

Unflagging a word is not enough: its last letters may now hang in the air with no word below them. Delete walks back up and cuts nodes until it meets one that still ends a word or still has children. Deleting card leaves car and care untouched.

Autocomplete: everything below the prefix

To list every word that starts with ca, walk to the node for ca and read the whole subtree under it with a depth-first search. Nothing outside that subtree can match, so it is never touched.

Type in the box. The path to your prefix lights up, the subtree below it tints, and the words it holds are listed, ranked by how popular they are.

Two costs, kept apart

Finding the prefix node costs O(L) for a prefix of length L. Listing the results costs time proportional to the size of the subtree you read. Real search boxes stop early or store the top few suggestions inside each node, so a keystroke stays cheap.

What it costs

Count node hops: one per letter of the word or prefix you are handling. Let L be that length and n the number of stored words. Insert, search and starts-with take O(L) hops. They never depend on n.

Now the question a hash set could not answer: how many words start with this prefix? Give every node a counter of the words that pass through it, and the answer sits one node away. The race below counts keys examined against nodes visited.

The trie’s catch is its constant: every letter costs a whole node with a table of children, which is far more than one byte. With hash-map children, hashing a letter is O(1) on average. With an array of 26 slots, it is one indexed read, but the array is mostly empty.

Why is the hash-set scan O(n·L) and not O(n)?

Testing “does this key start with the prefix?” compares up to L letters per key, and there are n keys. A hash set has no structure that lets it skip any of them, because a hash function scrambles words that start alike.

When is a trie worse than a hash set?

When you only ask exact questions. A hash set answers those in O(L) on average with far less memory and far better cache behaviour: one array lookup instead of L pointer hops through scattered nodes. A trie earns its memory only when prefixes matter.

Compress the chains: the radix tree

Many trie nodes are just a single child after a single child, with no fork and no word ending between them. Those chains cost a node per letter and give nothing back. A radix tree (also called a compressed trie or Patricia tree) folds each chain into one node whose label is a whole string.

Pick a word set, or type your own, and step through the folding. Watch the node count fall while every letter stays.

The rule

After compression every node except the root is a word end or a fork (two or more children). A radix tree with n words therefore has fewer than 2n nodes, no matter how long the words are. Routing tables and the Linux kernel use it for exactly this reason.

Longest-prefix match: routing packets

A router holds a table of address prefixes, each with a next hop, and a packet matches every prefix its address starts with. The rule: use the longest one. A trie over the address bits finds it in one walk.

Here the alphabet is just 0 and 1, so each node has at most two children. Type an address, or pick one, and follow the bits. The walk remembers the last node that held a route.

Variations and patterns

Most trie problems are one of these four ideas. The nodes are the same; only what you store in them, and what you do while walking, changes.

Increase count on every node you step through while inserting. The number of words that start with a prefix is the counter of its node, read in O(L).


        
Walk to the node for the prefix, then depth-first search below it, carrying the letters so far. Each time you pass a flagged node, you have found a word.

        
In a letter grid, extend a path one neighbouring letter at a time while following the trie in step. When the trie has no child for the next letter, no word can continue this path: stop. That prune is what makes word search fast.

        
Given a dictionary of roots, replace each word by its shortest root. Walk the word through a trie of the roots and stop at the first flagged node. If the walk falls off the trie first, keep the word.

      

      

        
Pitfall: array-of-26 children on a big alphabet

        
An array of 26 child pointers per node is fast but wasteful: most slots stay empty. For Unicode text it would be millions of slots per node. Use a hash map (or a sorted small list) for the children whenever the alphabet is large or the trie is sparse.

History

      

        
1960named

        
Edward Fredkin“Trie Memory”, Communications of the ACM

        

          
René de la Briandais described tries in 1959, and Edward Fredkin named them in 1960 after the middle of the word “retrieval”. Fredkin said it like “tree”; many people now say “try” to avoid the confusion. In 1975 Alfred Aho and Margaret Corasick added failure links to a trie of search words, and their algorithm became the Unix tool fgrep.

        

        
Sources: R. de la Briandais, “File Searching Using Variable Length Keys” (1959); E. Fredkin, “Trie Memory”, CACM 3(9), 1960; A. Aho and M. Corasick, CACM 18(6), 1975.
