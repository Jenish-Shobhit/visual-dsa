Segment & Fenwick trees

Add up any slice of an array, and change any single number, in about log n steps. The trick: keep the sums of blocks whose sizes are powers of two, and answer every question with a handful of them.

  • 22 min
  • Intermediate
  • Needs: arrays, binary trees, bits

The problem: sums that keep changing

A shop keeps its daily sales in an array. The manager keeps asking, “how much did we sell from day 3 to day 12?”, and every so often someone corrects a day’s number. Two operations, over and over.

Definitions

A range query asks for a summary (here the sum) of a[l..r]. A point update changes one cell, a[i] = v. We want both to be fast, however many of them arrive.

There are two obvious answers, and each makes one operation cheap and the other slow. Press the buttons and watch what each approach has to touch. Numbers count cells read or written.

The trade-off

A plain array reads up to n cells per query. A prefix-sum array answers in two reads but rewrites up to n cells per update. A tree keeps partial sums, so neither operation ever touches more than about log n cells.

Build the intuition: subtotals of blocks

Analogy: a company’s org chart

Every manager reports the total budget of their team. To get the budget of “everyone from team 3 to team 12”, you do not add up every employee. You add up a few managers whose teams fit exactly inside that range.

Cut the array into halves, then quarters, then eighths, and keep the sum of every block. Now choose any range with the sliders. It splits into a few blocks that the tree already knows.

Where the analogy breaks

A manager’s total goes stale the moment one employee’s pay changes. Every manager above that person must be corrected, and that chain of managers is what an update has to walk.

The segment tree: one node per segment

Definition

A segment tree is a binary tree where every node stands for a segment [lo, hi] of the array and stores one summary of it. The root is the whole array, the two children are its halves, and the leaves are single cells. The thin bar under a node shows which cells it covers; dotted lines tie each leaf to its cell.

Building is bottom-up: a leaf copies its cell, and every other node combines its two children, so both children must be ready first. Step through and watch the values climb.

Key idea

n cells need only n − 1 more nodes, and the tree is about log₂ n levels tall. Nodes are usually stored in one array numbered like a heap: the root is 1, and node k has children 2k and 2k + 1. The lab’s variable panel shows these numbers.

Answering a query: three kinds of node

A query starts at the root and asks each node one question: how does my segment relate to the range? There are only three answers, and each has one action.

Pick a range and step through. A node that only partly overlaps has to ask both children. Everything else is settled on the spot, which is why the walk stays short.

Why the walk is short

At each level at most two nodes are partly covered: the ones holding the left and the right end of the range. Each of them spawns at most two children, so a query visits at most four nodes per level, about 4 log₂ n in total, however wide the range is.

Changing one number: the path to the root

Only the nodes whose segment contains the changed index hold a sum that included the old value. That is exactly the path from the leaf up to the root, one node per level.

Key idea

An update rewrites ⌈log₂ n⌉ + 1 nodes, a query reads at most about 4 log₂ n. Both are logarithmic, so a million-cell array needs about 20 steps instead of a million.

Range updates and lazy propagation

What if the update is “add 3 to every cell in a[2..5]”? Point updates would cost one path per cell, k log n in all. A smarter tree changes the biggest fully covered nodes only, and leaves a note for the rest.

Definition

A lazy tag on a node means “every cell below me still has to get this amount added”. The node’s own sum is already right; its children are stale (dashed) until the tag is pushed down.

Why laziness is safe

The invariant is: a node’s stored value is correct for everything at and above it; only the nodes below a tag are behind, by exactly the tag. A query that stops at a node takes a correct value. A query that goes through a node pushes the tag first, so nothing stale is ever read.

Fenwick tree: the same idea in one array

A segment tree stores about 2n nodes and uses recursion. A Fenwick tree (or binary indexed tree) gets prefix sums with just an array of n numbers and a bit trick. It only needs one piece of arithmetic: the value of the lowest set bit of an index.

Why i & −i works

Negative numbers are stored as “flip every bit, then add 1”. Adding 1 carries through the trailing zeros of the flipped number and stops at the lowest set bit, so below and at that bit −i equals i, and above it every bit is flipped. AND-ing the two leaves exactly that one bit.

Now the structure. Index i (counting from 1) is responsible for the block of lowbit(i) cells ending at i. Index 12 is 1100 in binary, its lowest bit is 4, so it stores a[9..12]. Click any index to see the blocks a prefix query and an update use for it.

Key idea

A prefix query starts at i, adds T[i], then strips the lowest set bit (i −= i & −i) and repeats. It adds one block per set bit of i. An update does the opposite: it adds the lowest set bit (i += i & −i) to climb through every bigger block that contains the cell.

Why can a Fenwick tree not answer range minimum?

A range query is prefix(r) − prefix(l − 1), which needs to subtract a prefix. Sums have an inverse; minimum does not: knowing the minimum of a[1..r] and of a[1..l − 1] says nothing about the minimum of a[l..r]. A segment tree combines the exact blocks and never subtracts.

Why an update in a Fenwick tree touches at most log₂ n + 1 blocks

Adding the lowest set bit to i moves it past a run of 1 bits and turns them into a single higher 1. Every jump makes the lowest set bit strictly larger, so it can be doubled at most log₂ n times before the index passes n.

Variations and patterns

The tree does not care what “combine” means, as long as it is associative and has an identity. Change those two and the same code answers other questions.

Swap + for min and the identity 0 for ∞. A query returns the smallest value of a range, for example the cheapest day in a window, in O(log n).


        
The greatest common divisor is associative, and gcd(0, x) = x, so 0 plays the role of “nothing”. Point updates rewrite one path, exactly as before.

        
Store the differences d[i] = a[i] − a[i − 1] in a Fenwick tree. Adding v to a[l..r] is two point updates: +v at l and −v at r + 1. The value of a[i] is then prefix(i).

        
To count, for every element, how many earlier elements are smaller (or count inversions), index the tree by value. Read each element left to right: query how many values below it were seen, then add 1 at its own value. n queries and n updates make O(n log n) in total.

History

      

        
1977segment tree

        
Jon Bentley · Boris Ryabko · Peter FenwickKlee’s problem (1977) · 1989 · 1994

        

          
Jon Bentley introduced segment trees in 1977, in unpublished Carnegie Mellon notes on Klee’s problem: how much area does a set of overlapping rectangles cover?

          
Fenwick trees came from data compression. Peter Fenwick published them in 1994 to keep running symbol counts for arithmetic coding, not knowing that Boris Ryabko had described the same structure in 1989.

        

        
Sources: P. M. Fenwick, “A New Data Structure for Cumulative Frequency Tables”, Software: Practice and Experience 24(3), 1994; B. Ryabko, “A fast on-line code”, Soviet Math. Doklady 39(3), 1989; J. L. Bentley, unpublished notes on Klee’s rectangle problem, Carnegie Mellon University, 1977.
