Greedy algorithms

Pick the best-looking option, lock it in, never look back. It is the fastest way to solve a problem, and sometimes it is simply wrong. This lesson shows how to tell which.

  • 24 min
  • Intermediate
  • Needs: sorting, heaps, trees

The problem

One meeting room, many requests. Each request has a start and an end, and two requests cannot overlap. You want to say yes to as many as possible.

Try it yourself. Click requests to add them to the room. A request that overlaps one you already chose turns red.

You probably went left to right, or grabbed the short ones. Which rule always works? Checking every subset takes 2n tries. A greedy algorithm tries for a shortcut: sort once, walk the list once.

Build the intuition

Picture a hiker in thick fog who can see only the two steps next to them. The greedy rule is: always step to the higher neighbour, stop when neither is higher. Click the ground to choose where the hiker starts.

Definition

A greedy algorithm builds an answer one piece at a time. At each step it takes the option that looks best right now and never undoes it.

On one hill, every local peak is the global peak, so greedy wins. On two hills it strands you. Everything in this lesson is the question: which problems are one-hill problems? The answer is a proof, not a hunch.

Interval scheduling: which rule?

There are four natural greedy rules for the meeting room: earliest start, shortest, fewest conflicts, earliest finish. Only one is always right. Pick each rule, then use the presets to load an input that breaks it.

Earliest start grabs a huge request that blocks everything. Shortest can straddle two requests that would have fit together. Fewest conflicts fails on a subtler input. Earliest finish never loses, because finishing early leaves the most room for whatever is next.

Test your reading of that rule. Click the request that earliest finish keeps first.

Why earliest finish is safe: the exchange argument

Take any best schedule (bottom row) and compare it with greedy’s (top row). Greedy’s first request ends no later than the optimum’s first. So swap it in: the optimum still fits, and still has the same size. Repeat for the second request, the third, and the optimum becomes greedy without ever shrinking.

The shape of every greedy proof

Show that some optimal solution agrees with greedy’s first choice (exchange). Then the rest of the problem is the same problem, only smaller, so the argument repeats. The other route is staying ahead: after k picks greedy is never behind any other solution.

When greedy is wrong: coin change

Pay an amount with the fewest coins. The greedy rule is what every cashier does: hand over the biggest coin that fits. With US coins it is perfect. Change the coin set and watch it break.

With coins 1, 3 and 4, greedy takes the 4 for amount 6 and is left with 2. The right answer, 3 + 3, never uses the biggest coin. The local choice closed a door. Finding the true minimum needs dynamic programming.

For which coin sets does greedy work? The line under the coins tells you: if it ever fails, it fails below the sum of the two largest coins (a theorem of Kozen and Zaks), so checking that far is a proof.

Fractional or whole: knapsack

A bag holds a fixed weight. Take items with the best value per kilogram first. If you can pour part of an item (gold dust), that is provably best. If items are whole (gold bars), leftover space cannot be refilled and greedy loses.

The pouring bag is optimal because every kilogram is used by the best remaining value. The whole-item bag wastes 20 kg. Both use the same rule; only the freedom to cut changed. That is the difference between a greedy-friendly problem and one that needs DP.

Huffman coding: greedy that compresses

Text normally spends 8 bits on every character. Give frequent characters short codes and rare ones long codes, and the same text needs fewer bits. The codes must be prefix-free: no code is the start of another, so a decoder never has to guess.

Huffman’s greedy rule builds the code tree from the bottom: repeatedly merge the two rarest trees. Type your own text.

Frequent symbols end up near the root with short codes; rare ones sink deep. The greedy step is safe by an exchange argument too: the two rarest symbols can always be siblings at the deepest level of some optimal code.

Is greedy safe here?

Before you write a greedy algorithm, ask three questions. Pick a problem below and watch the answers light the path.

Matroids in one sentence

Some problems come with a guarantee: if the feasible sets are closed under taking subsets and any smaller feasible set can always borrow an element from a larger one (a matroid), then greedy by weight is optimal. Spanning forests, scheduling with deadlines and pouring knapsack are matroid-like; whole-item knapsack is not.

Cost

Greedy algorithms are fast because they decide once. Usually the cost is the sort or the heap; the walk itself is linear.

History

1951a term paper

David Huffman“A Method for the Construction of Minimum-Redundancy Codes”, Proc. IRE, 1952

In 1951 MIT professor Robert Fano let his students skip the final exam if they could find the most efficient binary code. David Huffman almost gave up, then saw that he should build the code tree from the bottom, repeatedly merging the two rarest symbols. That beat the method Fano had worked out with Claude Shannon.

Twenty years later Jack Edmonds showed that matroids are exactly the structures on which greedy choices like this are always optimal. Whitney had defined them in 1935.

Sources: D. A. Huffman, Proc. IRE 40(9), 1952; H. Whitney, Amer. J. Math. 57, 1935; J. Edmonds, “Matroids and the Greedy Algorithm”, Math. Programming 1, 1971.

Practice

  1. Minimum number of arrows
    Medium

    Balloons are intervals on a line. One arrow bursts every balloon it passes through. Find the fewest arrows. Which sort key makes the greedy step safe, and what is the exchange argument?

  2. Jump game
    Medium

    Each cell tells how far you may jump. Decide whether you can reach the last cell by tracking only the farthest position reachable so far. Why is that one number enough?

  3. Assign cookies
    Easy

    Each child needs a cookie of at least some size; each cookie goes to at most one child. Maximise satisfied children. Sort both lists and argue why the smallest cookie that works is the right choice.

  4. Break the greedy
    Medium

    Find a coin set of four coins, including 1, where greedy fails at an amount below 20, and confirm with the Kozen–Zaks bound that no smaller amount can fail earlier than the bound says.

  5. Optimal merge pattern
    Hard

    You must merge n sorted files; merging two costs the sum of their sizes. Which merge order minimises the total cost, and how is it the same problem as Huffman coding?
