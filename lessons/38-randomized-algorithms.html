Randomized algorithms

Flip a coin and a slow or fussy algorithm turns fast and simple. The price is a small chance of being slow, or wrong, and you get to set that chance.

  • 20 min
  • Intermediate
  • Needs: Quick sort
  • Needs: Hash tables

The problem: someone knows your rule

Quick sort picks a pivot, splits the array around it, and recurses. If you always pick the last element, a sorted array is a disaster: the pivot is the biggest value, one side gets everything, and the work adds up to about n²/2 comparisons.

You could pick the middle instead. Then the adversary, whoever hands you the input, simply builds an array that defeats that rule. Any fixed rule has a worst input, and a determined adversary can find it.

The fix is almost embarrassingly simple: choose the pivot with a coin flip. The adversary can read your code but not your dice, so no input is bad in advance. Some runs are lucky, some unlucky, and the average over your own coins is fast for every input.

Key idea

A randomized algorithm trades a fixed rule for a random choice. The guarantee is no longer “this input is fast” but “on every input, the odds are on your side”.

Two ways to gamble

Randomness can spend one of two things: your time or your certainty. Every randomized algorithm picks one.

Definitions

A Las Vegas algorithm always returns the right answer, but its running time depends on the coins. A Monte Carlo algorithm always finishes in a fixed number of steps, but its answer is right only with high probability.

Analogy: the lost key

Searching drawers at random until you find your key is Las Vegas: you are always right when you stop, but nobody knows how long it takes. Asking ten friends to look for five minutes each and trusting the “no” is Monte Carlo: bounded time, and a small chance the key was there.

The rest of this lesson meets both kinds: a Monte Carlo estimate of π, a fair shuffle, a stream sampler, a skip list, a Bloom filter, and randomized quick sort. Then one diagram sorts them all.

Monte Carlo: throwing darts at π

Draw a square of side 1 and a quarter circle of radius 1 inside it. The circle covers π/4 of the square, about 78.5 %. Throw darts that land at uniformly random spots, and the fraction inside estimates π/4.

Throw some. Each dart is just two random numbers x and y, and it is inside when x² + y² ≤ 1.

The 1/√n law

Random error shrinks slowly: 100 times more darts buys only 10 times more accuracy. That is poor for π in two dimensions, but the law does not care about dimension, so Monte Carlo wins on huge problems (volumes in 100 dimensions, physics, finance) where nothing else works.


    


    
    

      
A fair shuffle is harder than it looks

      
To shuffle, for each slot swap it with a random slot. It sounds right, and thousands of programs shipped it. The catch is which slots you may swap with.

      
The naive shuffle swaps slot i with any of the n slots. Fisher–Yates swaps slot i only with slots 0 to i, walking from the right, so each slot is fixed for good once it is placed. Step through both.

      
      
Both look shuffled. To tell them apart you need statistics: shuffle the same six items 10,000 times and count how often each item lands in each position. A fair shuffle puts every item in every position 1 time in 6 (16.7 %).

      
      

        
Why the naive shuffle cannot be fair

        
With 3 items the naive shuffle makes 3 × 3 × 3 = 27 equally likely sequences of random choices. There are 6 orders, and 27 is not divisible by 6, so some orders must get more sequences than others. Fisher–Yates makes 3 × 2 × 1 = 6 choices, one per order.

Lab: sampling a stream you cannot store

      
A log file has billions of lines and you want 3 of them, chosen uniformly at random. You do not know how many lines there are until you reach the end, and you cannot read it twice. Reservoir sampling keeps a reservoir of k items and updates it as the stream flows past.

      
The rule: the first k items go straight in. Item number i after that is kept with probability k/i, replacing a random reservoir item. That makes late items unlikely to enter, and early items unlikely to leave, so the odds balance out.

      
      
The same logic as a map of decisions. It is wired to the lab: step the lab and the current box lights up.

      
      
One run proves little. Run the whole stream 10,000 times and count how often each item ends up in the reservoir. If the sampler is fair, every bar reaches the same height: 10,000 × k / n.

      
      

    


    
    

      
Lab: a skip list, balanced by coin flips

      
A sorted linked list is easy to insert into but slow to search: you walk every node. A skip list adds express lanes. Every key gets a tower; the tower height is decided by flipping a fair coin, one more level for each heads.

      
Half of the keys reach level 2, a quarter reach level 3, an eighth reach level 4. Each lane is about half as crowded as the one below, which is exactly the shape of a balanced binary search tree, built by luck instead of rotations. Grow some towers.

      
      
To search, start at the head on the top lane. Hop right while the next tower is still smaller than your target, and drop down a lane when it would overshoot. To insert, search for the spot, flip coins for the height, and splice the tower in with a few pointer changes.

Lab: a Bloom filter, a set that forgets the words

      
You want to know whether a URL is in a blacklist of a hundred million entries, using almost no memory. A Bloom filter keeps only an array of m bits, all 0, and k hash functions.

      
To add a word, hash it k times and set those bits to 1. To check a word, hash it and look: if any bit is 0 the word was definitely never added. If all bits are 1 the answer is only maybe, because other words may have set them.

      
      

        
One-sided error

        
A Bloom filter can say “maybe” for a word that was never added (a false positive) but it can never say “definitely not” for a word that was added. You also cannot delete: clearing a bit could erase other words.

      

      
How often does “maybe” lie? After adding n words, a fraction 1 − e−kn/m of the bits are 1, so a stranger passes all k checks with probability (1 − e−kn/m)k. The dots below are measured with the real hash function.

      
      

    


    
    

      
Race: fixed pivot against random pivot

      
Back to where we started. Pick a fixed pivot rule and an input, then start the race. Both sides sort the same numbers with the same quick sort; only the pivot choice differs. The bars advance one comparison or move at a time, so the faster side finishes first.

      
      
The “Adversary’s input” button is not a trick: it hill-climbs, swapping two values whenever the swap makes your chosen rule slower, so every fixed rule, even median-of-three, gets its own nasty input. The random side never notices, because its pivot is chosen after the input is fixed.

The two kinds convert into each other

        
A Las Vegas algorithm becomes Monte Carlo if you stop it after a time limit and guess. A Monte Carlo algorithm becomes Las Vegas if you can check its answer: run it again until the check passes. Verifying is the whole trick.

Monte Carlo error can be pushed down almost for free by repeating. If one run is wrong with probability p and the errors are independent (and one-sided, like “composite” claims in Miller–Rabin), then k runs are all wrong with probability pk.

      
      

        Why is randomized quick sort O(n log n) in expectation?
        
Call a pivot good if it lands in the middle half of the range. A random pivot is good with probability 1/2. A good pivot leaves each side at most 3/4 of the size, so after about log4/3 n good pivots a branch is finished. Half of all pivots are good, so a branch needs about twice that many pivots in expectation, and every level of the recursion costs about n comparisons in total.

      

      

        Why is the expected skip-list height about log₂ n?
        
A key reaches level h with probability 2−(h−1). With n keys the expected number reaching level h is n / 2h−1, which drops below 1 when h ≈ log₂ n + 1. So the tallest tower is around log₂ n plus a small constant, and a search walks that many levels with about two steps per level.

      

    


    
    

      
More places coins help

      
The same idea shows up all over. Try a small live version of each.

      

        

          
          
          
          
        

        
A fixed hash x mod 7 is defeated by keys that are all multiples of 7: they pile into one bucket. Universal hashing picks the hash at random from a family, ((a·x + b) mod 101) mod 7 with random a and b, so no fixed key set is bad in advance.
Draw new a and b: the load evens out every time.

        
Miller–Rabin tests whether a number is prime. A random base a either proves the number composite (a witness) or fails to. At most a quarter of the bases lie, so 20 random bases leave an error below 4−20. It is Monte Carlo with one-sided error, and it is how cryptography picks primes.

        
A count-min sketch counts how often each item appeared in a stream using a small grid: each row has its own hash, each item bumps one cell per row, and the estimate is the minimum of its cells. Collisions only add, so it never under-counts. It is a Bloom filter that counts.

        
A treap is a binary search tree whose shape comes from random priorities: it behaves like randomized quick sort, frozen into a tree. Karger’s algorithm finds a minimum cut by contracting random edges. HyperLogLog counts distinct items in a stream with a few kilobytes by watching the longest run of leading zeros in random hashes. History

      

        
1946solitaire

        
Stanislaw Ulam, John von Neumann, Nicholas MetropolisLos Alamos, ENIAC

        

          
Monte Carlo methods began with a card game. In 1946, recovering from an illness, Stanislaw Ulam wondered how often a game of solitaire comes out, and realised that dealing many random games on a computer would answer faster than any formula. Nicholas Metropolis named the method after the casino where Ulam’s uncle liked to gamble, and by 1948 it was running on ENIAC.

          
Burton Bloom published his filter in 1970 for a hyphenation program that could not afford a dictionary in memory. Jeffrey Vitter analysed reservoir sampling in 1985, and William Pugh introduced skip lists in 1989 as a friendlier alternative to balanced trees.

        

        
Sources: Metropolis and Ulam, The Monte Carlo Method, J. American Statistical Association 1949; B. Bloom, CACM 13(7), 1970; J. Vitter, ACM TOMS 11(1), 1985; W. Pugh, CACM 33(6), 1990.
