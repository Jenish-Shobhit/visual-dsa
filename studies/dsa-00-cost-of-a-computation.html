The Cost of a Computation

FIELD NOTE / 00Before the long read

Build onA loop and an input size

Core invariantA running time counts operations on a stated input model; O, Ω, and Θ bound that function.

Try this first · A sorted array has 1,024 keys. What is the worst case number of halving decisions?

At most 11 comparisons in a standard binary search, since ⌈log₂(1,025)⌉ = 11.

The Analytical Engine could weave a calculation as a loom weaves flowers. But before a single value is computed, we can already foretell whether the weaving will finish before lunch — or after the Sun burns out. That foretelling is a science. This is its first lecture.

One problem, two engines. Find a name in a sorted directory of 8 billion people. Engine A reads top to bottom. Engine B halves the remaining range each step. Both are "correct." On a machine doing one billion comparisons per second:

Engine B · binary search
33
comparisons, worst case. Finished before you blink — about 33 nanoseconds.
Engine A · linear scan
8×10⁹
comparisons, worst case — about 8 seconds. A 240-million-fold gap.
The lesson
log n
The gap is not the machine. It is the order of growth. Buy a faster computer and Engine A is still hopeless.

Now push it. An algorithm that tries every subset of n items does 2n units of work. At n=100, that is about 1.27 × 1030 operations. Even at a billion per second, that takes about 40 trillion years. A different algorithm for the very same task might run in n2 = 10,000 steps: ten microseconds. Same problem. The difference between "instant" and "never" is the shape of a function.

The aim is to find the computational skeleton beneath a problem — to strip away the surface and ask what is really being mechanized, and at what cost. Today the skeleton is the cost itself. We will build, from first principles, a way to measure the price of a computation that does not depend on which machine you own, which language you wrote it in, or what mood the operating system is in. We will measure the algorithm, not the run.

04 · Build it from first principles

Measuring the algorithm, not the run

Why a stopwatch is the wrong instrument

The naive way to ask "how fast is this algorithm?" is to run it and time it. But a wall-clock measurement answers a question we did not ask. It folds together your CPU's clock speed, the compiler's cleverness, the language's overhead, the cache's mood, what else the machine was doing, and the one specific input you happened to feed it. Change any of these and the number changes — yet the algorithm did not. A stopwatch measures a run; we want a property of the method.

So we make two moves. First, we stop measuring seconds and start counting operations — a quantity intrinsic to the procedure. Second, we report that count not as a single number but as a function of the input size n, because the only honest answer to "how expensive?" is "expensive relative to how much data?" The result is T(n): the number of basic steps the algorithm performs on an input of size n. But "basic step" is doing a lot of quiet work in that sentence. To make it precise we need a model of the machine.

The RAM model — an honest fiction

The Random Access Machine (RAM) is the idealized computer on which all of classical algorithm analysis stands. It is deliberately simple, and deliberately a fiction. Its rules:

  • One processor, one instruction at a time. No parallelism, no hidden concurrency. Steps happen in sequence.
  • Memory is an unbounded array of cells. Each cell holds one word — an integer of w bits. Accessing any cell by its address costs the same: one unit. This is the "random access" promise — cell 2 and cell 2,000,000 are equally near. (This is the model's most beautiful lie; hold that thought.)
  • The basic operations each cost one unit of time. Arithmetic (+ − × ÷ mod), comparison (< = >), a load or store, following an array index, a branch, a function-call hop. One "step" = one of these.
  • The word is wide enough to be useful. We assume w=Θ(logn) bits — large enough to hold an index into the input and to add two such indices in one step, but not so large that we can cheat by packing the whole input into one cell.

This is the uniform-cost model: every basic operation is priced at 1, regardless of the actual magnitudes involved. Its purpose is not to be true — it is to be portable. An operation count in the RAM model is a statement about the algorithm that survives translation across machines, decades, and languages. When we later need more truth (huge integers, real caches), we will name exactly where the fiction tore.

The contract Cost = number of unit-cost RAM operations, as a function of input size n. That single sentence is what "running time" will mean for the rest of this course.

What is n, exactly?

The input size is the number of words it takes to write the input down. For an array of items, n is the number of items. For a graph, it is two numbers, V and E. For a single integer N, here is the subtlety that trips everyone: the size is not N but the number of bits to write it, n=⌈log2N⌉. Doubling N adds one bit. An algorithm that loops N times is exponential in its input size — a trap we will spring deliberately in the failure-modes section.

Why we go asymptotic: the tyranny of constants

Suppose careful counting gives one algorithm TA(n)=100n and a rival TB(n)=n2100. For small n, B looks faster. But set them equal: 100n=n2/100 gives n=10000. Beyond that crossover, A wins and the lead only widens — forever. The leading term's shape eventually dominates every constant factor and every lower-order term. Since we deploy algorithms on data that grows, we care about behavior as n→∞. This is the asymptotic stance: throw away constants and lower-order terms, keep the shape.

That throwing-away must be made rigorous — otherwise "keep the shape" is hand-waving. The rigor is three pieces of notation.

Big-O — the ceiling

We write f(n)=O(g(n)) to say "f grows no faster than g, up to a constant, eventually." Formally:

Definition · Big-O (asymptotic upper bound)
f(n)=O(g(n))   ⟺   ∃c>0,n0>0 s.t. 0≤f(n)≤c·g(n) for all n≥n0.

Read it as a promise with two escape hatches: you may scale g up by any constant c you like, and you may ignore all small n below some threshold n0. If, with those allowances, g sits above f, then f is O(g).

Worked claim: 3n2+5n+7=O(n2). We must exhibit a c and an n0.

Unfold the proof — exhibit the constants

For every n≥1 we have n≤n2 and 1≤n2. Therefore

3n2+5n+7≤3n2+5n2+7n2=15n2

So the definition holds with c=15 and n0=1. The constants are not unique — c=4,n0=6 works too. Existence is all the definition asks for. That is the whole game: bound the small terms by the big one, collect the coefficients.

A ceiling, not a portrait O is an upper bound, so a true O statement can be wildly loose. 3n2 really is O(n3), and even O(2n). Both are correct and both are useless. And note the abuse of "=": f=O(g) really means f belongs to the set O(g); it never runs the other way.

Omega and Theta — the floor and the tight fit

Flip the inequality and you get the lower bound; demand both at once and you get a tight bound.

Definition · Big-Omega (lower) & Big-Theta (tight)
f=Ω(g) :  ∃c>0, 0≤c·g(n)≤f(n)  eventually.
f=Θ(g) :  ∃c1,c2>0, c1·g(n)≤f(n)≤c2·g(n)  eventually.

So Θ(g)=O(g)∩Ω(g): f is trapped between two constant multiples of g. Θ is the honest answer to "what is the growth rate?" — it commits to a shape from both sides. There are strict cousins too: little-o (f=o(g), "f is dominated by g for every constant," e.g. n=o(n2)) and little-ω, its mirror. Most of the time, reach for Θ and say exactly what you mean.

The two axes — and why people conflate them

Here is the single most common confusion in this entire subject, and the reason I draw it twice. There are two independent questions hiding inside "what is the running time?":

  1. Which input? — the case. For a fixed size n, different inputs cost different amounts. Worst-case Tworst(n)=max|x|=ncost(x) is the guarantee — the promise that holds no matter what. Best-case is the minimum. Average-case is the expectation over a stated input distribution — and "stated" is load-bearing: there is no average without a distribution.
  2. Which bound? — the notation. Once you have fixed a case, its cost is a function of n, and you can put a ceiling (O), a floor (Ω), or a tight fit (Θ) on that function.

These axes are perpendicular. "The worst case is O(n2)" and "the best case is Θ(n)" are both well-formed and can both be true of one algorithm. The category error — and you will hear it constantly — is to say "O means worst case." It does not. O is a bound; it can bound any case.

What "efficient" formally means

We have ranked growth classes by feel. Theory draws a hard line: an algorithm is efficient if its worst-case running time is O(nk) for some constant k — polynomial time. The problems solvable this way form the class P. Everything that needs super-polynomial time — 2n, n! — we call (so far as anyone can prove) intractable.

Why draw the line at polynomial, and not, say, at n2? Two reasons, both about robustness. First, polynomials are closed under composition and addition: a polynomial-time routine calling another polynomial-time routine a polynomial number of times is still polynomial. The class does not leak. Second — and this is the deep one — the boundary is model-independent. Whether you compute on a RAM, a Turing machine, or any other reasonable sequential model, the set of polynomial-time-solvable problems is the same. (Quantum machines are the live exception — the boundary of the classical model, which we will reach at the very end of this course.) Polynomial is the largest class that stays invariant under the things we are choosing to ignore. That is why it is the definition of feasible, and it is a profound statement about the limits of mechanization, not a mere convenience.

Polynomial ≠ practical The definition is necessary, not sufficient. An O(n100) algorithm, or one with a constant of 1040 hiding inside the O, is "efficient" by the theory and worthless in the world. These are called galactic algorithms. Polynomial is the floor of the conversation, never the end of it.

05 · Worked examples

Two derivations, every step shown

Example 1 — "Does a pair sum to the target?" — counting Θ(n2), then beating it

The task: given an array A of n numbers and a target t, decide whether some two distinct elements sum to t. The first idea is to try every pair.

Count the dominant work — the inner comparison. For a fixed i, the inner loop runs (n−1−i) times. Sum over i:

Total inner comparisons (worst case — no early return)
T(n)=∑i=0n−1(n−1−i)=(n−1)+(n−2)+⋯+1+0=n(n−1)2=Θ(n2)

The arithmetic series collapses to n(n−1)2, which is Θ(n2): the constant ½ and the loop overhead vanish into the notation. Now mind the two axes:

  • Worst case (no pair, or the only pair is the last one checked): all n(n−1)2 comparisons run → Θ(n2).
  • Best case (A[0]+A[1]==t): one comparison, then return → Θ(1).
  • Space: a handful of variables → Θ(1) extra memory.

Can we do better? Yes — by spending memory to buy time. Walk once through A; for each x, ask a hash set whether t − x was already seen.

One pass of n iterations, each doing Θ(1) expected hash work → Θ(n) expected time, at the price of Θ(n) space for the set. This is the recurring bargain of the entire course — the time–space trade-off — and a preview of how a data structure (the hash set, Lecture 08) collapses a quadratic into a linear. Notice too that "expected" appears because hashing's Θ(1) is an average over hash outcomes, not a worst-case guarantee. The axes never stop mattering.

Example 2 — Binary search — deriving Θ(logn) from halving

Back to the hook. The array is sorted. To find key, probe the middle; the comparison throws away half the array; repeat on the survivor.

Each iteration is Θ(1), so the whole cost is Θ(number of iterations). Let the window size be m; the body replaces m with at most ⌊m/2⌋. Starting at m=n, after k iterations the window is at most n/2k. The loop ends when the window falls below 1:

Solving for the iteration count
n2k<1⟺2k>n⟺k>log2n

So the loop runs at most ⌊log2n⌋+1 times: worst case Θ(logn) (key absent), best case Θ(1) (key sits at the first mid). Watch the halving evaporate a galaxy of data:

06 · Where it breaks

Failure modes & the lies of the model

Formal elegance can blind you to where the formalism stops applying — that is the thing I most often have to remind myself of. Here are the traps, in the order they bite.

  1. Treating "Big-O" as a synonym for "worst case"

    The deepest and most common error. O, Θ, Ω are bounds; best / average / worst are cases. You can put an O on the best case and an Ω on the worst. When someone says "the complexity is O(n2)," always ask: of which case?

  2. Saying O when you mean Θ — over- and under-claiming

    Every merge sort is O(n2) — true and useless, because it is also Θ(nlogn). An O alone never tells you the bound is tight. If you know the matching lower bound, say Θ and mean it; if you only have a ceiling, do not pretend it is the rate.

  3. Dropping constants when constants are the whole story

    Asymptotics describe the limit, not your actual n. For small inputs the constant and lower-order terms dominate — which is exactly why real sort libraries fall back to insertion sort below ~16 elements even though it is Θ(n2). And a "galactic" O(nlogn) with a constant of 1040 loses to a quadratic on every input mankind will ever run.

  4. The RAM model's beautiful lie #1 — unit-cost arithmetic

    We priced × at one unit. For machine-word integers, fine. But multiply two n-bit numbers and it is not Θ(1) — schoolbook multiplication is Θ(n2) bit-operations (the FFT in Lecture 04 does far better). When numbers grow with the input, switch from the word model to the bit-cost model.

  5. The RAM model's beautiful lie #2 — uniform memory

    "Every memory access costs 1" ignores the cache hierarchy, where an L1 hit and a DRAM miss differ by ~100×. A cache-friendly Θ(nlogn) algorithm can crush a pointer-chasing Θ(n) one in wall-clock time. The RAM count is still the right first question — just know it is not the last.

  6. "Average case" with no distribution named

    Average-case is an expectation, and an expectation is meaningless without a probability distribution over inputs. Quicksort's celebrated Θ(nlogn) "average" assumes a uniform-random permutation (or random pivots). State the distribution or do not say "average."

  7. Adding when you should multiply (and vice-versa)

    Sequential blocks add: O(n) then O(m) is O(n+m). Nested loops multiply: O(n) inside O(m) is O(nm). Also: max(f,g)=Θ(f+g), so a sum's growth is just its largest term.

  8. The pseudo-polynomial trap — looping to a value

    A loop for k in range(N) over a numeric input N runs N times — which looks linear but is Θ(2n) in the input size n=⌈log2N⌉. Such "pseudo-polynomial" algorithms (trial-division primality, the textbook knapsack DP) are exponential in disguise. This is Practice Problem 4.

  9. Forgetting space — including the call stack

    "Fast" is half the question. A recursion n levels deep uses Θ(n) stack memory even if it returns nothing; a naive recursive Fibonacci is Θ(φn) in time. Always report both time and space.

  10. Confusing amortized with average

    They sound alike and are not. Average-case averages over random inputs; amortized averages over a sequence of operations on a worst-case input — a deterministic guarantee with no randomness. The doubling array's O(1) amortized append (Lecture 02) holds for every input, not on average.

Problem 2 · The two axes on one algorithm

Insertion sort: best, worst, average

For insertionSort below, give a tight Θ-bound on the number of element-comparisons for (a) the best case, (b) the worst case, and (c) the average case over a uniformly random permutation of n distinct keys. For (a) and (b), exhibit an input of each size n that achieves the bound.

def insertionSort(A):           # n = len(A)
  for i in range(1, n):
    key, j = A[i], i - 1
    while j >= 0 and A[j] > key:    # the comparison we count
      A[j+1] = A[j]; j -= 1
    A[j+1] = key
constraints: 1 ≤ n ≤ 10⁵ · deliverable: three Θ-bounds (state the distribution) + worst/best witnesses

Problem 4 · The pseudo-polynomial trap

Is trial-division primality "efficient"?

The routine tests whether integer N is prime by trial-dividing up to N. Express its worst-case running time (a) as a function of the value N, and (b) as a function of the input size n=⌈log2N⌉ bits. Is it polynomial-time by the formal definition? Justify, and name what would have to change to make primality testing provably poly-time in n.

def isPrime(N):                  # N ≥ 2, integer
  d = 2
  while d * d <= N:             # runs until d > √N
    if N % d == 0: return False
    d += 1
  return True

08 · Recap & next

The one thing to remember

Cost is the order of growth of unit-cost operations in the RAM model — and you must state it on two independent axes: which case (best / average / worst) and which bound (O ceiling / Θ tight / Ω floor).

Everything downstream — every data structure, every algorithm in this course — is an attempt to move a problem to a better growth class, or to prove that no better class exists. You now own the language in which all of those claims are made. Keep the growth-race picture in your head; it is the map of the whole territory.
