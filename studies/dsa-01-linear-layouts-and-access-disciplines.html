Linear Layouts & Access Disciplines

FIELD NOTE / 01Before the long read

Build onCost of indexing an array

Core invariantRepresentation determines access cost: contiguous positions support arithmetic indexing; a linked list follows pointers.

Try this first · Which layout gives direct access to element 500, and which gives constant time insertion after a known node?

An array gives direct indexing. A linked list inserts after a known node by changing a constant number of links.

A sequence — the ordered list a₀, a₁, …, aₙ₋₁ — is a single idea. But you cannot store an idea; you must lay it out in memory. There are exactly two primitive ways to do so, contiguous and linked, and the choice silently fixes the price of every operation you will ever run. This lecture makes that choice, and the four containers built on it — array, linked list, stack, queue — fully concrete.

A number to unsettle you. Sum one million integers two ways: once striding across an array, once chasing the next pointers of a linked list holding the same values. Both visit n elements. Both are Θ(n). In Lecture 00's RAM model they cost exactly the same — one step per element.

On real silicon the array finishes roughly 10–50× sooner. The RAM model charged them equally; the memory hierarchy did not. That entire gap hides inside the constant Big-O throws away — and learning to see it, and choose for it, is the craft this lecture begins.

01 layout is destiny

The idea, and the engine beneath it

Start with a distinction this lesson makes mechanical. There is the operation — the abstract thing we wish to perform — and there is the engine that carries it out. Ada Lovelace described how the Analytical Engine weaves algebraic patterns much as the Jacquard loom weaves flowers and leaves; the pattern is one thing, the arrangement of cards and wheels that realises it is quite another. Confuse the two and you understand neither.

A sequence is such a pattern: an ordered run of elements, with a notion of first, next, and position. That is the idea. To run it on a machine you must commit to an arrangement in memory — and here nature offers only two primitives. You may place the elements side by side, each at a computable distance from the first (a contiguous layout, the array). Or you may scatter them and have each element point to the next (a linked layout, the list). Every richer structure in this course — trees, heaps, hash tables, graphs — is assembled from these two atoms.

The thesis of the lecture is blunt: the layout you choose is the cost model you accept. Contiguity buys instant arithmetic access and pays for edits in the middle; linking buys instant splicing and pays for reaching the middle at all. No layout is cheap everywhere — that is not pessimism, it is a conservation law we will see again and again. Choose the layout and you have already chosen which operations are free and which are dear.

03 separate the interface from the representation

The sequence, as an abstract type

Before any memory, fix the interface. An abstract data type (ADT) is a set of values together with the operations permitted on them — a contract stated in terms of behaviour, saying nothing about storage. The Sequence ADT holds an ordered collection a₀ … aₙ₋₁ and offers, at minimum:

  • access(i) — return the element at position i;
  • insert(i, x) / delete(i) — splice an element in or out at position i, shifting the meaning of later positions;
  • first / last / next(p) — navigate by position rather than index;
  • length().

Notice the contract is silent on cost. That silence is the whole game. A data structure is a representation of an ADT — a concrete arrangement in memory — and it is the representation, not the contract, that assigns a price to each operation. The same Sequence contract, realised as an array or as a linked list, yields two completely different cost profiles. So the engineering question is never “what is the best data structure?” in the abstract; it is “which operations does my workload run most often, and which layout makes those cheap?”

the formal lensOne contract, many engines. When you find yourself arguing about a structure, first write down the operation mix — the frequencies. The optimal representation is a function of that mix, and of nothing else.
04 the contiguous layout

The array: access as arithmetic

Place the n elements in a single unbroken block of memory, element i immediately after element i−1. Let the block begin at address base and let each element occupy s bytes — the stride. Then the address of element i is not searched for; it is computed:

address of the i-th element
addr(A[i]) = base+i·s

One multiplication, one addition — a fixed amount of work whatever i is. Reaching A[5] costs no more than reaching A[0]. This is what “random access” means and why the RAM model's Θ(1) indexing is, for arrays, a faithful description of the hardware: the array is precisely the structure the RAM model was abstracted from. With base = 1000 and a 4-byte stride, addr(A[5]) = 1000 + 5·4 = 1020, computed directly.

05 the price of contiguity

Editing an array: the shift cascade

Contiguity is a strict promise: position i lives at base + i·s, with no gaps. To insert(2, X) into a full-packed array you must make room at slot 2, which means every element from slot 2 onward slides one place to the right to keep the promise intact. Insert near the front and you move almost the whole array; on average you touch n/2 elements, so insertion and deletion at an arbitrary position are Θ(n).

The end is the happy exception. Appending or removing at the last slot disturbs no one — provided spare capacity exists. Manufacturing that spare capacity cheaply, so that a sequence of appends is Θ(1) on average even though an occasional append must grow and copy the whole block, is the dynamic array, and its amortised analysis is the entire subject of Lecture 02. For now, hold the asterisk: append is Θ(1) amortised.

06 the linked layout

The linked list: splice freely, but walk to arrive

Abandon contiguity entirely. Store each element in its own little parcel — a node — holding the value and the address of the next parcel. The nodes may sit anywhere in memory; the next pointers thread them into an order. A single head pointer names the first node; the last node points at ∅ (null).

record Node { value; next }        // one datum + one pointer to the next node

INSERT-FRONT(L, x):                 // O(1) — allocate, point, repoint. No shifting.
  n ← new Node(value = x, next = L.head)
  L.head ← n

GET(L, i):                          // Θ(i) — there is no address shortcut; walk.
  p ← L.head
  repeat i times: p ← p.next
  return p.value

Now the costs invert. To insert at the front you allocate a node and repoint head — a fixed amount of work, Θ(1), with nothing shifted, because there is no contiguity promise to keep. More generally, if you already hold a node, splicing a new neighbour in or cutting one out is pure pointer surgery: Θ(1). That is the linked list's gift.

But ask for access(i) and the gift is revoked. The nodes' addresses are unrelated — look again at Figure 1 — so base + i·s is meaningless. The only route to the i-th node is to start at head and follow next exactly i times: Θ(i) work, Θ(n) in the worst case. The array trades cheap edits for instant access; the list trades instant access for cheap edits. Neither escapes the bargain.

The array reaches by computing; the list reaches by walking. Cheap access and cheap splicing are bought with different currencies — and you cannot pay in both at once.

Singly vs. doubly linked — a second pointer changes what you can delete

A singly-linked node knows only its successor. So to delete a node you must repoint its predecessor's next around it — and a singly-linked node cannot name its predecessor. Hand me a pointer to a node and ask me to delete it, and I must walk from head to find who points at it: Θ(n). Add a second pointer, prev, making the list doubly-linked, and that same deletion becomes Θ(1) — I can reach both neighbours and stitch them together directly. The price is one extra pointer of space per node, and two pointers to maintain on every edit. This is the exact trade that makes the doubly-linked list the backbone of LRU caches and of most language runtimes' deque types.

Why can a singly-linked list still delete in O(1) given a node — sometimes?
There is a sly trick: to “delete” node p, copy p.next's value into p, then splice out p.next instead. You have effectively removed p's value in Θ(1) without its predecessor. The catch: it fails when p is the last node (there is no p.next to copy), and it relocates the survivor, invalidating any pointer someone else held to p.next. A genuine Θ(1) delete-given-a-node needs the prev pointer. The trick is a classic interview answer and a classic source of subtle bugs.

08 where the model breaks

The hidden charge: cache locality

Now mark the boundary of the model. The last row of the table holds equal Θ-bounds yet says “excellent” against “poor.” That is not sloppiness; it is the RAM model failing honestly, and it is the most practically important idea in this lecture.

The RAM model of Lecture 00 charges 1 for any memory access, at any address. Real machines do not. Memory is a hierarchy: a tiny, ~4-cycle L1 cache; larger, slower L2/L3; and main memory (DRAM) a couple of hundred cycles away. Crucially, hardware never fetches one byte — it fetches a whole cache line, typically 64 bytes, and a prefetcher races ahead to pull in the next lines when it detects a sequential stride.

Watch what this does to our two Θ(n) scans. The array's elements sit in one run; the very first access drags in a line holding the next ~16, and the prefetcher keeps the pipe full. Across a million elements you pay a small handful of misses for every sixteen reads. The linked list's nodes are scattered, so each p ← p.next jumps to an unrelated address — a likely miss, every single step, with nothing to prefetch because the next address is not known until the current node is read. Same instruction count; one is a smooth read of memory, the other a storm of misses.

the boundary, namedThe RAM model is not wrong — it is an abstraction with a stated domain of validity, and uniform-cost memory is exactly the assumption that lapses here. Use Θ to rule out the catastrophes of kind (Lecture 00); use locality to win the contests of constant. A mature engineer holds both lenses and knows which one the situation is testing.
09 power through constraint

Access disciplines: stack, queue, deque

So far we let the caller touch any position. Now comes the lecture's second great idea, and it runs against intuition: restricting the interface increases what we can promise. If the caller agrees to only ever touch the ends of the sequence, then both layouts — which charged Θ(n) for interior edits — can serve every operation in Θ(1). An access discipline is a Sequence that has voluntarily given up middle access in exchange for guaranteed-cheap end access. Constraint is not weakness here; it is leverage.

Three disciplines exhaust the useful end-restrictions:

  • Stack — LIFO, last-in-first-out. Both push and pop act on one end (the “top”). The most recently added element is the first removed.
  • Queue — FIFO, first-in-first-out. enqueue adds at the back; dequeue removes from the front. Elements leave in arrival order.
  • Deque — double-ended queue. Insert and remove at either end; the general primitive of which stack and queue are restrictions.

Why does the restriction pay off? Because every operation now touches a fixed end, and both atoms can service an end cheaply: an array keeps an integer top (or head/tail) index and writes there directly; a linked list keeps head and tail pointers and repoints them. No scan, no shift, no walk. The stack and queue ADTs are not weaker sequences — they are sequences that bought a guarantee by selling away a freedom they did not need.

Backing a queue with an array — the naive trap, and the ring

A stack on an array is trivial: push and pop at index top. A queue is subtler. enqueue at the back is fine, but dequeue from the front — index 0 — tempts you to shift everything left, restoring the Θ(n) we were trying to escape. The fix is to stop moving the data and instead move the boundaries: keep a head index that advances on dequeue, and let the back wrap around to reuse the slots the front has vacated. A fixed array used this way, with indices taken modulo the capacity, is the ring buffer (circular buffer) — the canonical Θ(1) bounded queue, and the structure behind every audio buffer, network stack, and producer–consumer pipe you have ever used.

10 worked example A

The ring buffer, derived and traced

Let us build it from the invariant and run it by hand. Take a fixed array buf[0…C−1] of capacity C. Store two facts: head, the index of the front element, and size, how many elements are live. The back is not stored — it is derived, because the slot after the last element is exactly head + size places past the front, wrapped into range:

the write index for the next enqueue
idx= (head+size) mod C

The mod C is the whole trick: when the arithmetic runs off the end of the array it wraps to the beginning, reclaiming slots the front has freed. Tracking size directly (rather than a second tail index) sidesteps the famous full-versus-empty ambiguity before it can arise — we will dwell on that in §12.

record Ring { buf[0…C−1];  head ← 0;  size ← 0 }

ENQUEUE(R, x):                       // O(1)
  if R.size = C: return FULL
  R.buf[(R.head + R.size) mod C] ← x
  R.size ← R.size + 1

DEQUEUE(R):                          // O(1)
  if R.size = 0: return EMPTY
  x ← R.buf[R.head]
  R.head ← (R.head + 1) mod C
  R.size ← R.size − 1
  return x

Now the trace. Take C = 4 and run this sequence of operations; watch head, size, and the physical array. A dot · marks a slot that is logically empty (stale), even if an old value still physically sits there.

11 worked example B

The stack at work: matching brackets

A second worked example, to show why the LIFO discipline is not a toy but a precise tool for a precise structure: nesting. Decide whether a string of brackets ()[]{} is well-formed — every opener closed, in the right order. The governing fact is that the most recently opened bracket must be the first one closed. “Most recent out first” is the definition of a stack; the problem and the structure are the same shape.

MATCH(s):
  st ← empty stack
  for c in s:
    if c in "([{":  push(st, c)              // an opener: remember it
    else:                                  // a closer: it must match the latest opener
      if empty(st) or top(st) ≠ partner(c):

  return empty(st)                          // well-formed iff nothing left open

12 where it breaks

Failure modes & common mistakes

Keep the gap between the clean model and the running machine in view. Here is where these structures bite — the edge cases, the seductive-but-wrong shortcuts, the off-by-ones that survive every “it worked on my example.”

1 · The full-vs-empty ambiguity in a ring buffer

If you track head and tail indices and nothing else, then head == tail means the ring is empty and also means it is full — the two states are indistinguishable, because the pointers wrapped all the way around. Three honest fixes, each a real engineering choice: (a) store an explicit size (or count) as we did — cleanest; (b) sacrifice one slot, declaring “full” when (tail+1) mod C == head, so the two states never collide, at the cost of one unusable cell; (c) keep a boolean full flag. Pick one deliberately. The bug is choosing none and shipping a buffer that silently reports empty when it is jammed full.

2 · Negative modulo on insertFront / decrement

Moving a head index backwards — as a deque's insertFront must — you compute head = (head − 1) mod C. In most languages (−1) mod C is −1, not C−1, and you index out of bounds. Always wrap as head = (head − 1 + C) mod C. This single missing + C is among the most common bugs in handwritten ring code.

3 · The “O(1) linked-list insert” half-truth

“Linked lists insert in O(1)” is true only once you already hold the node at the insertion point. insert(i, x) from an index must first find position i — a Θ(i) walk — so the honest cost is Θ(i), the same order as the array's shift. The O(1) applies to the splice, not the search. Quoting the splice cost as if it were the whole operation is how linked lists get chosen for workloads they then lose.

4 · Deleting from a singly-linked list without the predecessor

You cannot stitch a node out of a singly-linked list without repointing the node before it, and a singly-linked node cannot name its predecessor. Either walk from head to find it (Θ(n)), keep a prev pointer as you traverse, or use a doubly-linked list. The copy-the-successor trick from §06 fails on the tail node — guard it.

5 · Iterator / index invalidation across a mutation

Hold an index into an array, then insert or delete before it: your index now points at the wrong element — every position past the edit shifted. Hold a raw pointer to an array element, then trigger a dynamic-array regrowth: the whole block was reallocated and copied elsewhere, and your pointer now dangles into freed memory. Linked-list node pointers survive their neighbours' edits (a virtue), but a pointer to a node you yourself free is a use-after-free waiting to happen. Never cache a position across a structural mutation unless the structure guarantees stability.

6 · Equal Big-O, unequal reality — picking a list where an array wins

From §08: a linked list and an array can share a Θ(n) bound while the array runs 10–50× faster from locality alone. For a stack or a plain traversal — pure end-access, sequential reads — prefer the contiguous backing every time. Reach for the linked list when you genuinely need Θ(1) splicing of interior nodes you already hold, or stable node identity across edits. “It's O(1) on paper” is not a reason; the constant is real money.

7 · Forgetting the bound, or the empty case

A bounded stack or ring must define behaviour on push-when-full and pop-when-empty: reject, block, or overwrite — but decide, because the default is a crash or silent corruption. And every pop/dequeue/top needs an empty-guard before it touches storage. In garbage-collected languages, also null out the popped slot — a stale reference left in the array keeps a dead object alive (the classic ArrayStack memory leak); in manual-memory languages, free the node and drop the pointer.

13 practice

Problems

1

Design a circular deque

ring buffer · modular arithmetic · both ends

Implement MyCircularDeque(k) on a fixed array of capacity k, every operation O(1) time and O(k) space: insertFront(v), insertLast(v), deleteFront(), deleteLast(), getFront(), getRear(), isEmpty(), isFull(). The four mutators return a boolean (false if the operation is impossible); getFront/getRear return −1 when empty. State your representation (which of head, tail, size you keep and why), and handle the negative-modulo wrap on insertFront. Argue full-vs-empty cannot be confused under your scheme.

2

Implement a FIFO queue using only two stacks

stack↔queue duality · amortised analysis

Using two LIFO stacks (and no other container), implement Queue with push(x), pop(), peek(), empty() obeying FIFO order. Then prove your pop/peek run in O(1) amortised time even though a single call may be Θ(n). Give the amortised argument explicitly — an accounting or potential argument is ideal: define a potential Φ over the two stacks and show each operation's amortised cost is constant. (This previews Lecture 02.)

3

Reverse a singly-linked list in place

pointer surgery · O(1) extra space

Given head of a singly-linked list, reverse it and return the new head, using O(1) auxiliary space and a single pass. Specify your loop invariant precisely (what prev, cur, and the saved next denote at the top of each iteration), and identify the one line whose omission would either lose the tail of the list or create a cycle. Then give the recursive formulation and state its space cost and why it differs.

4

Min-stack: track the minimum in O(1)

augmented invariant · O(1) all ops

Design a stack supporting push(x), pop(), top(), and getMin() — the current minimum — each in O(1) worst-case time. State the auxiliary invariant you maintain and prove it survives both push and pop (mind duplicate minima — what must happen on ties so that a later pop keeps getMin correct?). 14 recap & next

The one thing to remember

A sequence is one idea with two physical layouts, and the layout you pick is the cost model you accept. Contiguous arrays compute access in Θ(1) and bill Θ(n) for interior edits; linked lists splice in Θ(1) and bill Θ(n) to arrive. Restricting access to the ends — stack (LIFO), queue (FIFO), deque, ring buffer — buys Θ(1) on both layouts. And when two structures tie on Θ, locality breaks the tie: the constant the RAM model discards is real money on real silicon.
