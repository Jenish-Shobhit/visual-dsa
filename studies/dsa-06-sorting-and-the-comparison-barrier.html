Build onComparison based algorithms

Core invariantA comparison tree needs enough leaves to distinguish every possible input ordering.

Try this first · Why can counting sort run in linear time without violating the comparison lower bound?

It uses integer keys as array indices. The Ω(n log n) bound assumes the algorithm learns order only through comparisons.

Sorting is the most-run non-trivial algorithm on Earth, and it is where this course first meets a provable limit. We will build randomized quicksort and prove it averages O(n log n) with nothing but indicator variables; then prove that no algorithm that learns about its data only by comparing pairs can ever beat Ω(n log n) — a law, not a failure of imagination; then walk straight through that wall with counting and radix sort, which sort in linear time by refusing to compare at all.

A number to fix the stakes. Shuffle a standard 52-card deck. There are 52! ≈ 8.07×10⁶⁷ possible orderings. Any algorithm that sorts the deck by asking only “is this card before that one?” must, in the worst case, ask at least ⌈log₂(52!)⌉ = 226 yes/no questions. Not 226 on average for a clumsy method — 226 is the floor for the best comparison sort that will ever be invented.

Yet if those 52 cards carried integer ranks 0…51, I can sort them in one linear pass with no comparison whatsoever. Two facts, both true, both proved on this page. The reconciliation — that the barrier guards a model, not the problem — is the deepest idea in elementary algorithmics.

01 a wall and a door

Two true statements that seem to fight

I think first in terms of what a machine is permitted to do, because the permissions fix the price. Sorting hands us the cleanest example in the whole course of this principle. Restrict an algorithm to one kind of question about its data and a hard floor appears beneath every method, present and future. Grant it one extra power — the ability to read a key's value as an address — and the floor vanishes.

Hold both of these in your head at once; the lecture exists to make them coexist:

  • The wall. Every comparison sort — merge sort, heapsort, quicksort, insertion sort, any algorithm whose only way of learning about the elements is to ask “is a < b?” — must perform Ω(n log n) comparisons in the worst case. This is a theorem about an entire class of algorithms at once, the rarest and most powerful kind of result in our field.
  • The door. If the keys are integers drawn from a modest range, counting sort and radix sort sort them in Θ(n) time. They do not contradict the wall — they stand outside the room the wall encloses, because they never compare two keys; they use each key as an index.

Randomized quicksort is our vehicle into the wall: a method so fast in practice that it is the default in most standard libraries, yet whose elegance is an average, paid for with a coin flip. We will prove its expected cost with a technique — the indicator variable — that you will reuse for hashing, for skip lists, for half the randomized structures in this syllabus. So this one lecture carries three of the deepest tools in the course: expectation as a design instrument, the adversary lower bound, and the change of model that escapes it.

the formal lensA lower bound is a statement about a model of computation, never about a problem in the abstract. Before you accept “this is as fast as it gets,” always ask: as fast as it gets in which model? Change the permitted operations and the bound can dissolve. That single habit is most of what this lecture teaches.
02 objectives & prerequisites

What you will be able to do

  • Implement randomized quicksort with a correct in-place partition, and say precisely why randomizing the pivot — not the input — is what buys the average-case guarantee.
  • Prove that randomized quicksort makes O(n log n) comparisons in expectation, from scratch, using indicator variables and the “2/(j−i+1)” lemma — and reproduce the harmonic-sum bound.
  • Derive the Ω(n log n) comparison lower bound by modelling any comparison sort as a binary decision tree with ≥ n! leaves, and explain why it pins both worst-case and average-case cost.
  • Build counting sort and radix sort, prove their linear-time bounds, and state the exact conditions on the keys under which linear sorting is legitimate.
  • Reconcile the wall and the door — articulate why linear-time sorting does not refute the lower bound, citing the operation each model is and is not allowed.
  • Diagnose the classic disasters: quicksort's quadratic worst case, the sorted-input pivot trap, recursion-depth blow-up, the all-duplicates collapse, and counting sort's silent memory explosion when the key range is large.

The one tool you must hold firmly is linearity of expectation: for any random variables, E[X₁+…+Xₘ] = E[X₁]+…+E[Xₘ], with no independence required. An indicator variable is a random variable that is 1 when some event happens and 0 otherwise; its expectation equals the probability of that event, E[X] = Pr[X = 1]. Those two sentences are the entire engine of §05.

03 strip the problem to its skeleton

The comparison model, made precise

Before any algorithm, fix what the algorithm is allowed to know. In the comparison model the input is a sequence of n elements from some totally ordered universe, and the algorithm may inspect them in exactly one way: pick two, aᵢ and aⱼ, and learn which of aᵢ < aⱼ, aᵢ = aⱼ, aᵢ > aⱼ holds. It may move elements about freely, but it may not look inside them — not their bits, not their magnitude, only their order relative to one another.

Now extract the computational skeleton. The actual values are irrelevant; only their relative order matters. So sorting an input of distinct elements is exactly the task of identifying which of the n! permutations arranges the input into increasing order. The algorithm starts knowing nothing — any of the n! orderings is possible — and each comparison is a single yes/no question that splits the still-possible orderings into two groups. The algorithm is done only when one ordering remains. That reframing — sorting as a question-asking game against an unknown permutation — is the whole reason a lower bound exists, and we cash it in §07.

This is also why the model matters so much. A comparison costs Θ(1), but it also yields only one bit. An operation that reads a key and uses it as an array index yields log k bits in one step and lives in a different model — the model counting and radix sort inhabit. Keep the two straight and nothing on this page will ever seem paradoxical.

A comparison sort plays twenty questions against a hidden permutation. With n! suspects, you cannot always win in fewer than log₂(n!) questions.
04 divide by a pivot

Randomized quicksort & the partition

Quicksort is divide-and-conquer with the cleverness moved to the divide. Choose one element as the pivot; rearrange the array so that everything smaller sits to its left and everything larger to its right; the pivot is now in its final sorted position; recurse on the two sides. The combine step is empty — that is the trick. All the work is in the partition, and the quality of the split is decided by the pivot.

Here is the in-place Lomuto partition, the cleanest to reason about. It keeps a single boundary i marking the end of the “≤ pivot” zone and scans the rest with j, swapping any small element across the boundary. The one line that makes it randomized — and so immune to adversarial input — is choosing the pivot index at random and parking it at the end before the scan begins.

function quicksort(A, lo, hi):          # sort A[lo..hi] in place
    if lo < hi:
        p = partition(A, lo, hi)        # p = pivot's FINAL resting index
        quicksort(A, lo, p - 1)         # the ≤-pivot side
        quicksort(A, p + 1, hi)         # the >-pivot side

function partition(A, lo, hi):
    r = random_int(lo, hi)             # THE randomization: a uniform pivot
    swap(A[r], A[hi])                  # park the chosen pivot at the end
    pivot = A[hi]
    i = lo - 1                         # i = last index of the "≤ pivot" zone
    for j in lo .. hi - 1:
        if A[j] ≤ pivot:               # one comparison per loop step
            i = i + 1
            swap(A[i], A[j])             # move the small element across the boundary
    swap(A[i + 1], A[hi])              # drop the pivot into its seat
    return i + 1

The loop performs exactly hi − lo comparisons — one per non-pivot element against the pivot — and at most that many swaps, so a single partition of a block of m elements is Θ(m) time and Θ(1) extra space. Correctness rests on a loop invariant you should be able to state in your sleep:

partition invariantAt the top of each iteration of the scan, the array is split into four contiguous zones: A[lo..i] are all ≤ pivot; A[i+1..j−1] are all > pivot; A[j..hi−1] are not yet examined; and A[hi] is the pivot. Each step restores it. When j reaches hi, the final swap drops the pivot exactly between the ≤ and > zones — its sorted home.

Why randomize the pivot rather than shuffle the input?

Both work, and for the same reason, but randomizing the pivot is cleaner. A deterministic pivot rule — “always take the first element” — has a permanent worst-case enemy: feed it already-sorted data and every partition peels off just one element, giving n + (n−1) + … + 1 = Θ(n²) comparisons. Randomizing the pivot means no fixed input is bad; there is only bad luck, and bad luck cannot be arranged by an adversary who hands you the data. The expectation in §05 is taken over the algorithm's coin flips, so it holds for every input equally. That is the precise, formal payoff of randomization: it converts “slow on some inputs” into “slow only on some coin sequences, with vanishing probability.”

05 the crown jewel

Expected O(n log n) from indicator variables

We will not write or solve a recurrence. There is a far more beautiful route, and it is the template for nearly every randomized analysis you will meet later. The total running time of quicksort is dominated by the number of comparisons, so let X be the total number of comparisons across the entire sort. We want E[X].

Rename the elements by their sorted rank: let z₁ < z₂ < … < zₙ be the elements in increasing order (the order statistics). This renaming is just bookkeeping — the algorithm never sees it — but it lets us talk about any specific pair. For each pair i < j, define the indicator

indicator variable for one pair
Xij = { 1 if zi and zj are ever compared 0 otherwise

Two facts make this the right variable. First, every comparison quicksort ever makes is between the pivot and another element, so any pair is compared at most once in the whole execution (once one of them is the pivot, it is removed from its subarray; two non-pivots in the same block are never compared directly). Second, the total comparison count is therefore exactly the sum of these indicators — nothing is double counted:

total comparisons, then take expectation
X= ∑i=1n−1 ∑j=i+1n Xij   ⇒   E[X] = ∑i=1n−1 ∑j=i+1n Pr[zi, zj compared]

The implication is linearity of expectation, and it asks for nothing — the Xᵢⱼ are wildly dependent, and we simply do not care. We have traded one hard question (the distribution of a sum) for Θ(n²) easy ones (a single probability). Now the only thing left is that probability.

The key lemma: Pr[zᵢ, zⱼ compared] = 2/(j − i + 1)

Consider the contiguous band of order statistics Zᵢⱼ = {zᵢ, zᵢ₊₁, …, zⱼ} — there are j − i + 1 of them. Track which element of this band is chosen as a pivot first (somewhere in the recursion, some member of the band must be picked before the others, because pivots are removed one at a time). Everything turns on that first pick:

  • If the first pivot drawn from the band is an interior element zₖ with i < k < j, then zᵢ and zⱼ land on opposite sides of that partition (one below zₖ, one above) and are separated forever — they can never be compared.
  • If the first pivot drawn from the band is an endpoint — zᵢ itself or zⱼ itself — then at that moment the whole band is still together in one subarray (nobody from the band has been a pivot yet), so the pivot is compared against every other band member, including the other endpoint. They are compared.

So the pair is compared if and only if the first-chosen pivot of the band is one of its two endpoints. Because every pivot is chosen uniformly at random, each of the j − i + 1 band members is equally likely to be the first one picked. Two of them are favourable. Hence:

the probability, and the sum it produces
Pr[zi, zj compared] = 2j−i+1 ,   so    E[X] = ∑i=1n−1 ∑j=i+1n 2j−i+1

Substitute d = j − i (the gap), so the inner term is 2/(d+1). Summing the inner series and bounding it by a harmonic number Hₙ = 1 + 1/2 + … + 1/n gives the finish:

close it with the harmonic bound
E[X] < ∑i=1n 2 ∑d=1n 1d = 2nHn = 2n(lnn+O(1)) = O(nlogn)

That is the whole proof. No recurrence, no Master Theorem, no case analysis on the split — just a clean count of which pairs ever meet. The constant is sharp, too: 2 ln 2 ≈ 1.39, so randomized quicksort makes about 1.39 n log₂n comparisons on average — only 39% more than the information-theoretic floor we prove in §07.

Why “at most once” is the load-bearing fact — a one-line guard

If a pair could be compared twice, the sum X = ∑ Xᵢⱼ would undercount and the analysis would be wrong. It holds because comparisons happen only against the current pivot, and the pivot is pulled out of the recursion before either of its subarrays is processed. So once zᵢ and zⱼ are compared, one of them was the pivot and is gone; they never share a subarray again. This is exactly why Lomuto/Hoare partitions never compare two non-pivot elements with each other — only pivot-versus-rest. Break that property (e.g. a partition that re-scans) and you must redo the count.

07 the wall, proved

Any comparison sort needs Ω(n log n)

Now the result that makes quicksort's 1.39 n log₂n look not lucky but nearly optimal. We prove that every comparison sort — including ones not yet invented — must, on some input, make Ω(n log n) comparisons. The argument is one of the most elegant in computer science, and it is pure counting.

Model any comparison sort as a decision tree. Each internal node is a single comparison aᵢ : aⱼ; its two children correspond to the two answers (≤ goes one way, > the other). The algorithm starts at the root and walks down, one comparison per node, until it reaches a leaf — at which point it must output a definite permutation. A particular input drives a particular root-to-leaf path; the length of that path is the number of comparisons that input costs. So the worst-case comparison count is the height of the tree, and the average-case count is the average leaf depth.

Here is the crux, in two short claims:

  • The tree needs at least n! leaves. Each of the n! distinct input orderings requires a different output permutation to sort it. Two different orderings cannot end at the same leaf, because a leaf emits one fixed permutation, which would mis-sort at least one of them. So there are ≥ n! reachable leaves.
  • A binary tree of height h has at most 2ʰ leaves. Trivial induction: doubling per level.

Combine them and take logarithms, then apply Stirling's approximation ln(n!) = n ln n − n + O(log n):

the floor, in one line
2h≥n!  ⇒  h≥ log2(n!) = nlog2n − nlog2e +O(logn) = Ω(nlogn)

That is the wall. With log₂e ≈ 1.443, the floor is about n log₂n − 1.44 n comparisons — for the 52-card deck, log₂(52!) ≈ 225.6, i.e. 226, the number from the hook. And it is not only a worst-case statement: the average leaf depth of any binary tree with L leaves is at least log₂L, so even the average-case comparison count of any comparison sort is Ω(n log n). Merge sort and heapsort hit the floor in the worst case; randomized quicksort hits it in expectation. No comparison method does better, ever.

08 walk through the door

Escape I: counting sort

The lower bound's grip is total within its model. So we change the model. Suppose the keys are not abstract orderable tokens but integers in a known range 0 … k−1. Now a key is not merely comparable — it is an address. We can read a key and use it to index an array, an operation the comparison model forbade. With that one new power the floor disappears.

Counting sort never compares two keys. It (1) tallies how many times each value appears, (2) turns those tallies into positions by a running prefix sum, and (3) places each element directly into its slot. The prefix-sum step is the clever part: after it, C[v] tells you exactly how many keys are ≤ v, which is exactly where the last v belongs.

function counting_sort(A, k):           # keys A[i] in 0 .. k-1
    C = array(k, 0)                    # 1) histogram
    for x in A:  C[x] = C[x] + 1
    for v in 1 .. k-1:               # 2) prefix sums: C[v] = #keys ≤ v
        C[v] = C[v] + C[v-1]
    B = array(n)
    for i in n-1 .. 0:                # 3) place RIGHT-to-LEFT → stable
        v = A[i]
        C[v] = C[v] - 1
        B[C[v]] = A[i]
    return B

Two loops over n elements and one over k values give Θ(n + k) time and Θ(n + k) space. When k = O(n) — keys in a range proportional to the count — this is Θ(n), linear. And the right-to-left placement makes it stable: equal keys keep their original relative order, which is the property that lets us bolt counting sort into radix sort next.

09 through the door, at scale

Escape II: radix sort

Counting sort is linear only while k stays small. For 32-bit integers, k = 2³² ≈ 4×10⁹ — a four-billion-cell count array to sort, perhaps, a thousand numbers. Absurd. Radix sort fixes this by sorting on the keys' digits, one digit at a time, using counting sort (with its small per-digit range) as the inner engine. Process digits from least significant to most significant (LSD), and a subtle miracle occurs: the order is built up correctly across passes — provided the inner sort is stable.

Stability is the entire trick. When you sort on the tens digit, two numbers with the same tens digit must stay in the order their ones digit already established. Counting sort gives us exactly that, so each pass refines the previous one instead of scrambling it.

function radix_sort(A, d, b):           # d digits, base b, LSD first
    for p in 0 .. d-1:                # p = 0 is the least significant digit
        A = stable_counting_sort_by_digit(A, p, b)
    return A                          # each pass keeps the previous order on ties

Each of the d passes is a counting sort over base-b digits, costing Θ(n + b), so the total is Θ(d(n + b)). The art is choosing b. To sort n integers in the range 0 … nᶜ−1 for a constant c, write them in base b = n: then each number has only d = c digits, and the cost is Θ(c∙(n + n)) = Θ(n). Linear sorting of integers in any polynomial range.

why base = n makes it linear
T=Θ(d(n+b)) ,   b=n,    d= logn(max key) =O(1)  for max key = nO(1)  ⇒  T=Θ(n)
reconciling the wall & the doorCounting and radix sort do not break the §07 theorem. That theorem bounds algorithms whose only data operation is a comparison. These algorithms use a strictly more powerful operation — reading a key and using its value as an array index — so they live outside the model the bound describes. The bound is intact; we simply stopped playing the game it governs. Whenever a result claims optimality, the first question is always: in which model?

The integer-key sorts are the specialists: spectacular when their precondition holds, useless when it does not.

11 where it breaks

Failure modes & common mistakes

Keep the gap between the model and the running machine in view. Here is where these methods bite — the quadratic traps, the stability you forgot you depended on, the “linear” sort that quietly allocates a continent of memory.

1 · Quicksort's Θ(n²) worst case is real, just rare

The expected bound is not a guarantee on every run. If the coins conspire to pick the minimum or maximum as pivot every time, partitions peel off one element and you get Θ(n²) comparisons and Θ(n) recursion depth. With random pivots the probability of anything near this is astronomically small, but in an adversarial or safety-critical setting where worst case must be bounded, reach for heapsort or merge sort, or use the deterministic median-of-medians pivot to force a guaranteed balanced split (at a larger constant). “Expected” and “guaranteed” are different promises; know which one your context demands.

2 · The deterministic-pivot-on-sorted-input trap

Choosing the first (or last) element as a fixed pivot turns the single most common real-world input — already-sorted or reverse-sorted data — into the exact worst case. This is not a rare coincidence; sorted-ish data is everywhere. Either randomize the pivot (one line, §04) or take median-of-three. Shipping pivot = A[lo] is a latent quadratic bomb.

3 · Recursion depth: recurse small, loop large

Even with good pivots, naively recursing on both halves can build Θ(n) stack frames in the bad case and overflow. The fix is tail-recursion elimination: always recurse into the smaller partition and loop on the larger. This caps stack depth at Θ(log n) regardless of pivot luck, because each recursive call at least halves the subproblem size.

4 · The all-duplicates collapse — use a 3-way partition

Two-way (Lomuto/Hoare) partitioning on an array of many equal keys degrades to Θ(n²): every key equals the pivot, so each partition is maximally unbalanced. The cure is three-way partitioning (Dijkstra's Dutch-national-flag): split into < pivot, = pivot, > pivot, and recurse only on the outer two. Equal keys are placed once and never revisited, restoring near-linear behaviour on low-diversity data. This is Practice 2.

5 · Misreading the scope of the lower bound

Three honest misreadings. (a) The bound says comparison sorts need Ω(n log n) — it does not say sorting needs Ω(n log n); radix sort is the counterexample. (b) It is a worst-case over inputs bound; a specific easy input (already sorted) can be verified or sorted faster by an adaptive method. (c) It bounds comparisons, not wall-clock time; constants, cache behaviour, and branch prediction decide real races among n log n algorithms. The theorem is precise; quoting it loosely is the error.

6 · Counting sort's silent memory explosion

Θ(n + k) is linear only when k = O(n). Apply counting sort directly to 64-bit keys and k = 2⁶⁴: the count array alone is a request for 10¹⁹ cells — an instant out-of-memory, not a slow program. The range, not the count, governs feasibility. When k is large, that is the signal to switch to radix sort (decompose the key into small digits) rather than count over the raw range.

7 · Radix sort with an unstable inner sort, or MSD-first confusion

LSD radix sort is correct only if every digit pass is stable; swap in an unstable counting/bucket pass and later digits scramble the order earlier digits earned, silently producing wrong output on ties. Equally, do not sort LSD-first with an MSD mindset: MSD radix is a different (recursive, bucket-partitioning) algorithm. And radix assumes a fixed-width, decomposable key — variable-length strings need careful padding or an MSD variant. Stability here is not a nicety; it is the correctness condition.

8 · Forgetting that “optimal” is model-relative

The meta-mistake that contains the rest: treating “n log n is optimal” as an absolute. It is optimal in the comparison model. Change the assumptions — integer keys, bounded range, external memory, parallel hardware, a stream you see once — and the right algorithm and the right bound both change. Always re-state the model before you invoke its limits.

Maximum gap in linear time

beat the barrier · bucket / radix · LeetCode 164

Given an unsorted array nums, return the maximum difference between two successive elements in its sorted order, or 0 if it has fewer than two elements. The catch: you must run in O(n) time and O(n) space — so a comparison sort is forbidden by the very lower bound of §07. Escape it. Either radix-sort the integers, or use the pigeonhole idea: with n values spread over [min, max], place them in n−1 buckets of width ⌈(max−min)/(n−1)⌉; the max gap must straddle two buckets, so track each bucket's min and max only. Justify why the answer never lies within a bucket.

A lower bound for merging two sorted lists

adversary / decision-tree argument · proof

Two sorted arrays, each of length n, are to be merged into one sorted array of length 2n using only comparisons between elements. Prove that any comparison-based merge must perform at least 2n−1 comparisons in the worst case. Build the argument the way §07 builds its bound: either count the leaves a correct merge's decision tree must have, or run an adversary that answers each comparison so as to keep two outputs consistent until 2n−1 comparisons have been forced (consider interleavings where every adjacent pair from opposite lists must be directly compared). Then exhibit a merge achieving exactly 2n−1, proving the bound tight.

13 recap & next

The one thing to remember

A lower bound is a statement about a model, not a problem. In the comparison model, sorting n items demands Ω(n log n) — proved by counting the n! leaves a decision tree must reach — and randomized quicksort nearly meets it, ≈1.39 n log₂n in expectation, proved by summing one indicator per pair at probability 2/(j−i+1). Change the model — let keys be integers you may use as addresses — and counting and radix sort sort in Θ(n), walking straight through a wall that never moved. Ask always: optimal in which model?
