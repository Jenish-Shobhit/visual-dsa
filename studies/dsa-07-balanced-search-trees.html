Lecture 07 the dictionary problem, part i

Balanced Search Trees & the Logarithmic Ideal

A dictionary is the most-used abstraction in all of computing: store keyed records, then search, insert, and delete by key. The binary search tree promises to do all three in O(log n) — the logarithmic ideal — by mechanising binary search into a structure. But the promise is conditional, and the condition is balance. Break it and the same tree degrades, silently, into a linked list. This lecture is about the invariants that make the promise unconditional.

A number to unsettle you. Load one million keys into a textbook binary search tree. If they arrive in a random order the tree is short and a lookup costs about 20 comparisons. If they arrive already sorted — the single most common shape real data takes — the very same code builds a tree of height 999,999, and a lookup costs up to a million comparisons.

Same data structure. Same operations. A 50,000× gap, opened by nothing but the order of arrival. The self-balancing tree exists to close that gap by force — to guarantee the short tree no matter what the adversary feeds it. Learning the invariant that delivers the guarantee is the craft of this lecture.

01 the problem beneath the structure

What a dictionary really asks

Begin by separating the operation from the engine that performs it. Here the operation is ancient and simple: keep a collection of records, each labelled by a key drawn from some ordered universe, and support three verbs — find the record with a given key, insert a new one, delete an old one. This is the dictionary problem, and it is everywhere: a symbol table in a compiler, an index in a database, the routing table in a switch, the set of live objects in a memory allocator. Solve it well and a thousand systems get faster at once.

Lecture 01 gave us two ways to lay a sequence in memory, and each answers the dictionary problem badly. A sorted array searches in O(log n) by binary search — excellent — but every insert or delete shifts half the array, Θ(n) per update. An unsorted linked list inserts in O(1) but searches in Θ(n). Each structure makes one verb cheap by making another dear. The dictionary problem asks for all three verbs cheap at once, and neither linear layout can give it.

The binary search tree is the idea that you need not choose. It takes the decisive act of binary search — “compare to the middle, then discard half” — and freezes it into the shape of the data itself, so that the halving structure persists across edits instead of being rebuilt each time. The catch is that the halving only happens if the tree stays short. The whole lecture turns on one quantity, the tree's height, and on the invariants that hold it down.

the formal lensOne problem, many engines. We will hold the contract — search, insert, delete by key — absolutely fixed, and vary only the representation. Every cost we meet is a property of the representation, never of the contract.
02 objectives & prerequisites

What you will be able to do

  • State the binary-search-tree ordering invariant precisely, and derive why every one of search / insert / delete costs exactly Θ(h), the tree's height.
  • Prove the two-sided bound on height — ⌊log₂n⌋ ≤ h ≤ n−1 — and explain why the lower end is the dream and the upper end is a linked list wearing a tree's clothes.
  • Execute a left and a right rotation by hand and argue, from the in-order traversal, that a rotation changes a tree's shape while leaving its meaning — the ordering — untouched.
  • Maintain the AVL height-balance invariant through an insertion, choosing correctly among the four rotation cases (LL, RR, LR, RL), and prove via the Fibonacci recurrence that AVL height is at most ≈1.44·log₂n.
  • Contrast red-black trees with AVL — the looser invariant, the 2·log₂n height bound, and why fewer restructurings make them the standard library's choice.
  • Explain why databases and filesystems abandon binary trees for B-trees: how counting block transfers instead of comparisons turns log₂n into log᲻n and finds one record among a billion in three disk reads.

Prerequisites

Three ideas, each a short phrase you should already hold comfortably. The first two are taught on the linked pages.

asymptotic notation — O / Θ / Ω binary search / ordering recursion

If you can read O(log n) as “the work to repeatedly halve n down to one,” trust that binary search over a sorted run is Θ(log n), and follow a function that calls itself on a sub-part of its input, you are ready. We are about to give that halving a permanent home.

03 fix the interface before the memory

The dictionary, as an abstract type

An abstract data type is a set of values plus the operations permitted on them — a contract about behaviour that says nothing about storage. The Dictionary (or Map) ADT holds a set of (key, value) pairs with distinct keys and offers:

  • search(k) — return the value stored under key k, or “absent”;
  • insert(k, v) / delete(k) — add or remove a pair by key.

If that were the whole contract, a hash table — next lecture — would answer it in expected O(1) and trees would be a curiosity. But most real dictionaries quietly demand a richer contract: the keys are ordered, and we want the order back. The Ordered Dictionary adds:

  • min() / max() — the extreme keys;
  • predecessor(k) / successor(k) — the neighbouring keys in sorted order;
  • range(lo, hi) — every key in an interval, in order.

These are exactly the queries a hash table cannot answer cheaply, because hashing deliberately destroys order to spread keys uniformly. A search tree keeps the keys sorted by structure, so it answers all of them along the same O(h) root-to-leaf walk. That is the real reason trees survive in the age of hashing: they remember the order. Hold this distinction; it is the spine connecting this lecture to the next.

Hashing buys speed by forgetting the order. A search tree's whole value is that it remembers it.
04 the invariant that makes a tree searchable

The binary search tree, from first principles

A binary tree is either empty or a node holding a key plus two children, each itself a binary tree — a recursive shape. To make it searchable we impose one law on where keys may sit. This is the BST invariant:

the bst ordering invariant — holds at every node x

For every node x: every key in x's left subtree is < key(x), and every key in x's right subtree is > key(x).

Read the word every carefully — it is the whole structure and the source of the most common bug in §13. The law is not about a node and its two children; it is about a node and its two entire subtrees. The key at a node is a wall: everything to its left is smaller, everything to its right is larger, all the way down.

One consequence is immediate and beautiful. Walk the tree in order — left subtree, then node, then right subtree — and the keys come out sorted:

INORDER(x):
  if x ≠ nil:
    INORDER(left(x))          // all keys < key(x), in order
    visit(key(x))             // then x itself
    INORDER(right(x))         // then all keys > key(x), in order

A BST is therefore a sorted sequence that has been folded into a tree so that the binary search is built into the folding. Searching is just descending the fold:

SEARCH(x, k):                // x = subtree root, k = key sought
  while x ≠ nil and k ≠ key(x):
    if k < key(x): x ← left(x)    // smaller → the wall sends us left
    else:          x ← right(x)   // larger  → right
  return x                    // the node, or nil if k is absent

Each comparison discards an entire subtree — exactly the “throw away half” move of binary search, now a physical descent. Insertion reuses the search: walk down as if looking for k; where the search falls off the tree (hits nil), that empty slot is precisely where k belongs, so hang a new leaf there.

INSERT(x, k):
  if x = nil: return Node(k)               // fell off → the key lives here
  if   k < key(x): left(x)  ← INSERT(left(x), k)
  elif k > key(x): right(x) ← INSERT(right(x), k)
  return x                              // k == key(x): duplicate — a policy choice (§13)

Deletion is the one operation with real cases, because removing an interior node would split the tree. Three situations: a leaf simply vanishes; a node with one child is spliced out, its child taking its place; a node with two children cannot leave directly, so we overwrite its key with its in-order successor — the smallest key in its right subtree — and then delete that node, which by construction has no left child and so falls into one of the two easy cases. Every one of these — search, insert, delete — is a single walk from the root toward a leaf. Their cost is the length of that walk. Which brings us to the only quantity that matters.

05 the one quantity that governs everything

Height is destiny

Define the height of a tree as the number of edges on the longest path from the root down to a leaf — a single node has height 0, an empty tree height −1. Every dictionary operation is a root-to-leaf walk, so each touches at most h+1 nodes. The cost law is therefore exact and merciless:

the cost law of search trees
T(search)= T(insert)= T(delete) =Θ(h)

So the entire performance of a search tree collapses to a single question: how tall is it? And a binary tree's height is bounded on both sides by how many nodes it must spread across its levels. Level 0 holds at most 1 node, level 1 at most 2, level d at most 2ᵈ. A tree of height h therefore holds at most 2ᵒ⁺¹−1 nodes, and to hold n of them it needs height at least log₂(n+1)−1. At the other extreme, nothing forbids a tree from being a single drooping path, one node per level, height n−1. So:

height is pinned between a logarithm and a line
⌊log2n⌋ ≤h≤ n−1

The gap between those two ends is the whole drama. At the floor, h≈log₂n, and a million keys cost twenty steps — the logarithmic ideal. At the ceiling, h=n−1, and the tree is a linked list: the same Θ(h) law now reads Θ(n), and we have built an elaborate pointer structure that performs strictly worse than the array we were trying to beat. A plain BST gives you no say in which end you land at — the order of insertion decides. Figure 1 shows both fates for the same seven keys.

06 why imbalance is the common case, not the rare one

The adversary feeds you sorted data

It is tempting to wave the degenerate tree away as a pathological corner that never happens in practice. The opposite is true. Sorted or nearly-sorted input is the single most common shape real data arrives in. Timestamps land in time order. Auto-increment database keys arrive ascending. Log files, version numbers, re-imported exports, the output of a previous sort — all monotone. Feed any ascending stream to the plain INSERT of §04 and every new key is larger than all before it, so it walks to the far right and hangs there. The tree grows as a single right-leaning stick of height n−1. The most natural input produces the worst possible tree.

One might hope the average saves us, and on paper it nearly does: a BST built from a uniformly random permutation has expected height Θ(log n), with the average node sitting about 1.39·log₂n deep. But “average over random insertion orders” is a promise about a distribution you do not control. The adversary — or merely an upstream ORDER BY — chooses the order, and a single sorted batch lands you on the Θ(n) ceiling. Relying on the average here is relying on luck you have already lost.

the boundary of the average“Balanced in expectation” and “balanced in the worst case” are different guarantees. Expectation is defended only against a random adversary; a self-balancing invariant is defended against every adversary. The next four sections build that unconditional defence. (Randomness can be re-introduced deliberately — the treap of Lecture 22 — but as a designed tool, not a hope.)

The fix cannot be “ask callers to insert in random order.” It must be structural: after each update, detect when the tree is leaning too far and repair it — cheaply, in O(log n), without disturbing the ordering that makes it a search tree at all. There is exactly one primitive that can do this. Everything that follows is built from it.

07 the one move that changes shape without changing meaning

The rotation

A rotation is a local re-pivoting of one parent-child pair that re-balances the heights between them while preserving the BST invariant exactly. It is the only restructuring primitive we need, and it touches a constant number of pointers, so it costs O(1). Consider a node x whose right child is y, with three subtrees hanging off them — A, B, C. A left rotation at x lifts y up into x's place and lets x descend to become y's left child:

ROTATE-LEFT(x):            // precondition: x has a right child y
  y ← right(x)
  right(x) ← left(y)        // subtree B moves across, under x
  left(y)  ← x              // x descends to become y's left child
  return y                  // y is the new root of this subtree

Why is the ordering safe? Read off the in-order sequence before and after. Before the rotation the order is A, x, B, y, C. After it the order is… A, x, B, y, C — identical. The constraints A < x < B < y < C hold in both shapes; the rotation merely re-hangs B from y to x, the one subtree that sits, in value, between them and so is legal under either parent. A right rotation is the exact mirror, lifting a left child. Because in-order is preserved, a rotation is invisible to search — it changes only the heights, which is exactly what we want to adjust.

A rotation, then, is a knob: it shifts one unit of height from one side of a pivot to the other, for free, without anyone downstream noticing. A self-balancing tree is nothing more than a policy for when to turn that knob. There are two famous policies.

08 the strict policy

AVL trees: keep every node nearly balanced

The first self-balancing tree, due to Adelson-Velsky and Landis in 1962, enforces the most direct invariant imaginable. Define a node's balance factor as the height of its right subtree minus that of its left. The AVL invariant demands:

the avl height-balance invariant

At every node, balanceFactor = height(right) − height(left) ∈ {−1, 0, +1} — the two subtrees may differ in height by at most one.

This is a local law — checked one node at a time — yet it forces a global guarantee: the tree can never be tall. The argument is one of my favourites in all of data structures, because it answers “how bad can a barely-balanced tree get?” by building the worst legal one and counting it.

Derive the AVL height bound (the Fibonacci argument)

Ask the dual question: among all AVL trees of height h, what is the fewest nodes one can contain? Call it N(h). A sparsest tree of height h has a root, and to reach height h one child must have height h−1; to stay legal the other may be as short as h−2. Both children are themselves sparsest AVL trees, so:

a fibonacci recurrence
N(h)= 1+ N(h−1)+ N(h−2) , N(0)=1, N(1)=2

This is the Fibonacci numbers in disguise: N(h) = F(h+3) − 1. Checking: N(0)=1, N(1)=2, N(2)=4, N(3)=7, N(4)=12 — each the sum of the previous two plus one. Since Fibonacci grows like φᵒ with φ=(1+√5)/2≈1.618, the minimum node count grows exponentially in the height. Invert it: a tree with n nodes satisfies n ≥ N(h) ≈ φᵒ, hence

h≤ logφn ≈ 1.4404⋅ log2n

An AVL tree is never more than about 44% taller than a perfectly balanced one. The local ±1 rule has bought a global O(log n) height — unconditionally.

Maintaining the invariant is the art. After an INSERT, walk back up from the new leaf updating heights; the first node whose balance factor reaches ±2 is the lowest point of damage. Exactly one of four configurations holds there, named for the two steps of the path from that node down toward the new leaf, and each is repaired by one or two rotations:

INSERT(t, k):                              // returns the (possibly new) subtree root
  if t = nil: return Node(k, height=0)
  if k < key(t): left(t)  ← INSERT(left(t), k)
  else:          right(t) ← INSERT(right(t), k)
  update_height(t)                          // 1 + max(h(left), h(right))
  return REBALANCE(t)

REBALANCE(t):
  b ← bf(t)                                  // h(right) − h(left)
  if b < −1:                                // left-heavy
    if bf(left(t)) > 0: left(t) ← ROTATE-LEFT(left(t))   // LR: straighten first
    return ROTATE-RIGHT(t)                                    // LL or finished LR
  if b > +1:                                // right-heavy
    if bf(right(t)) < 0: right(t) ← ROTATE-RIGHT(right(t)) // RL: straighten first
    return ROTATE-LEFT(t)                                     // RR or finished RL
  return t                                  // already legal

The find costs O(log n), the retrace updating heights costs O(log n), and the rotations are O(1) each. An insertion triggers at most one single-or-double rotation; a deletion may trigger up to O(log n) of them as the imbalance propagates upward. Either way, every operation is O(log n) worst case. The promise of §01 is now unconditional.

10 the looser policy

Red-black trees: balance you can afford to maintain

AVL keeps trees beautifully short, but its rigidity has a price: a delete can cascade rotations all the way up. For workloads heavy on updates, a looser invariant that does less restructuring can win overall, even at the cost of a slightly taller tree. The red-black tree is that bargain, and it is the one your standard library actually ships — C++ std::map and std::set, Java's TreeMap and TreeSet, and the Linux kernel's scheduler and virtual-memory areas are all red-black trees.

Colour every node red or black and impose five rules. Together they let the longest root-to-leaf path be at most twice the shortest, which is all you need for O(log n):

  • Every node is red or black.
  • The root is black; every nil leaf is black.
  • A red node's children are both black — no two reds in a row.
  • Every path from a node down to its nil leaves crosses the same number of black nodes — that count is the node's black-height.

The fourth rule pins the “shortest path” (all black) and the third rule stops the “longest path” (alternating red/black) from being more than twice it. A short calculation makes it exact.

Derive the red-black height bound (h ≤ 2·log₂(n+1))

Claim: a subtree rooted at x contains at least 2bh(x)−1 internal nodes, where bh(x) is its black-height. Prove it by induction on the subtree's height. Base: a nil leaf has bh=0 and 2⁰−1=0 nodes. Step: each child of x has black-height at least bh(x)−1, so by hypothesis each child's subtree holds at least 2bh(x)−1−1 nodes; the subtree at x therefore holds at least (2bh(x)−1−1)+(2bh(x)−1−1)+1 = 2bh(x)−1. Now, by the no-two-reds rule at least half the nodes on any root-to-leaf path are black, so bh(root) ≥ h/2. Combining: n ≥ 2h/2−1, hence h ≤ 2·log₂(n+1).

The pay-off is in the update cost. A red-black insert finishes with at most 2 rotations; a delete with at most 3 — both constant, whereas an AVL delete may rotate O(log n) times. (Recolourings can still ripple up the tree, but recolouring is cheap and rotation-free.) The trade is now stateable in one line, and it is a genuine engineering choice, not a verdict:

avl vs red-blackAVL — tighter balance (≤1.44 log₂n), so lookups are shallower and faster; pays with more restructuring on churn. Favour it for read-heavy tables. Red-black — looser balance (≤2 log₂n) but O(1) rotations per update; favour it for write-heavy workloads and as a safe general default — which is exactly why the libraries chose it.
11 when memory is not flat

B-trees: changing the cost model changes the tree

Everything so far has assumed Lecture 00's RAM model, where every memory access costs the same 1. Lecture 01 already showed that promise fraying against the cache. Push the data onto a disk or SSD and it shatters completely: a random read does not fetch a byte, it fetches a whole block — thousands of bytes — and that single transfer costs as much as millions of arithmetic operations. The honest cost model is no longer “count comparisons” but the external-memory model: count block transfers (I/Os), each moving B items at once.

Under that model a balanced binary tree is a disaster. Its log₂n ≈ 30 levels for a billion keys become up to thirty separate block reads, each a random seek, because consecutive nodes on the path live in unrelated blocks. The structure is right; the branching factor is wrong. The fix, due to Bayer and McCreight in 1970, is to match the node to the block: let each node hold not one key but as many as fill a block — hundreds or thousands — with one more child pointer than it has keys. This is the B-tree.

A B-tree of minimum degree t keeps every node (bar the root) between t−1 and 2t−1 keys, holds all leaves at the same depth, and keeps each node's keys sorted so that its children interleave as separators. With branching factor up to 2t, its height is O(logᲿn) — a logarithm in base thousands, not base two:

the external-memory pay-off
I/Os per operation= O( logBn ) = Olog2nlog2B

This is the same lesson as Lecture 01's array-versus-list timing, escalated: the abstract Θ(log n) was never the whole story; the base of the logarithm, set by how much useful work one memory transfer buys, is where the real performance lives. Change the cost model and the optimal tree changes with it. The binary search tree is the right answer in RAM; the B-tree is the right answer on disk; both are the same idea — a balanced, ordered, logarithmic-height search structure — tuned to a different machine.

13 where it breaks

Failure modes & common mistakes

Keep the gap between the clean invariant and the running machine in view. Here is where search trees bite — the seductive-but-wrong checks, the input that detonates the average, the operation everyone implements halfway.

1 · Validating a BST by checking only children

The most common BST bug in existence: testing left.key < node.key < right.key at each node and calling it valid. The invariant is about whole subtrees, not immediate children. The tree with root 5, right child 7, and 7's left child 3 passes every local check yet is not a BST — 3 sits in 5's right subtree but is smaller than 5. Validate with a descending (low, high) bound or by confirming the in-order traversal is strictly increasing (Practice 1).

2 · Trusting “average” balance against real input

A plain BST is O(log n) only in expectation over random insertion orders — and real data is the opposite of random. Sorted timestamps, auto-increment keys, or the output of a prior sort drive it straight to the Θ(n) stick of §06. If you cannot guarantee random insertion order — and you almost never can — you must use a self-balancing tree or a randomized one (treap, Lecture 22). “It tested fine on shuffled data” is how this ships and then melts in production on the first bulk import.

3 · Implementing insert but botching delete

Insertion always lands at a leaf; deletion has the awkward two-children case and is where hand-rolled trees go wrong. Forgetting that the in-order successor must be spliced out after copying its key, copying the successor's key but not its satellite data, or — in a balanced tree — returning up the recursion without re-checking balance/colour, all silently corrupt the structure. In AVL especially, remember that a delete may require rotations at several ancestors, not just one.

4 · The comparator that lies

A search tree is only as sound as its ordering. A comparator that is not a strict weak ordering — non-transitive, or the classic return a - b on machine integers that overflows for large operands and flips sign — corrupts placement invisibly: keys get inserted on the wrong side, searches miss elements that are present, and the bug is unreproducible. Compare with explicit <, never subtraction; ensure a<b, b<a, and equality are mutually exclusive and transitive.

5 · Undefined duplicate-key policy

What does insert do when the key already exists? There is no default — decide. Reject it, overwrite the value, keep a count, or store a bucket. A careless “< goes left, ≥ goes right” scatters equal keys across the tree and interacts badly with rotations and with delete, which may now remove the wrong copy. State the policy in the type, not in folklore.

6 · Recursion depth on the very tree that is already slow

A recursive search/insert on a degenerate BST recurses n frames deep and overflows the call stack — so the imbalance that makes the tree slow also makes it crash. Balanced trees cap depth at O(log n) and dodge this; for any tree you cannot prove balanced, prefer an explicit iterative walk.

7 · Forgetting that augmented data must be O(1)-maintainable

Augmenting nodes with extra fields — subtree size for order statistics (Practice 4), subtree max for interval trees — only works if the field at a node is computable from its children's fields in O(1), so a rotation can fix it locally. Cache a field that depends on the whole subtree in a non-local way and every rotation silently invalidates it. The maintainability of the augmentation is a real proof obligation, not an afterthought.

Validate a binary search tree

the invariant · the local-check trap · LeetCode 98

Given root of a binary tree, return true iff it is a valid BST (left subtree strictly less, right subtree strictly greater, recursively). Constraints: up to 10⁴ nodes; values span the full signed-integer range, so guard the boundary keys. AVL insertion with rebalancing

the balancing mechanism · four cases · build problem

Implement insert(root, key) for an AVL tree, returning the (possibly new) root and maintaining |balanceFactor| ≤ 1 at every node via the four rotation cases. As a concrete check, give the pre-order traversal of the tree obtained by inserting 1,2,3,4,5,6,7 in that order into an initially empty AVL tree. 3

Lowest common ancestor in a BST

exploit the ordering · O(h) not O(n) · LeetCode 235

Given the root of a BST and two existing nodes p, q, return their lowest common ancestor. Use the ordering, not a general-tree search: from the root, if both keys are smaller go left, if both larger go right, otherwise the current node is the split point. Examples on the BST [6,2,8,0,4,7,9,null,null,3,5]: LCA(2,8)=6; LCA(2,4)=2 (a node may be its own ancestor). Achieve O(h) time and O(1) extra space, and explain in one line why a general binary tree would force O(n) — i.e. what the BST property buys you.

4

k-th smallest, then make it fast under updates

in-order + augmentation · order-statistic tree · LeetCode 230

Given the root of a BST and integer k (1-indexed), return the k-th smallest key. The base case is a partial in-order traversal in O(h+k). Now the real question (LeetCode's follow-up): if the BST is modified often and you must answer many such queries, redesign so each kthSmallest is O(log n) on a balanced tree. Specify the augmentation (subtree size), give select(k) and its mirror rank(key), and — the crux — prove the size field is maintainable in O(1) per node through both updates and rotations. This is an order-statistic tree; it foreshadows Lecture 10.

15 recap & next

The one thing to remember

A search tree's entire cost is its height, and balance is the invariant that keeps the height logarithmic no matter how the keys arrive. The BST ordering law turns search into a descent; the Θ(h) cost law makes height destiny; a single O(1) rotation changes shape without changing order; and a policy on when to rotate — AVL's strict ±1, red-black's looser colouring, the B-tree's block-sized fan-out — converts “O(log n) on average” into “O(log n), guaranteed.” And unlike the hash table you meet next, the tree keeps the keys in order, so it answers min, successor, and range for free.
