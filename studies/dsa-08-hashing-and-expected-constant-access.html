Collisions are possible. Expected constant time is not a worst case bound for every hash function and input.

Lecture 7 gave us a structure that stays ordered while it changes, at a worst-case O(log n) per operation — and proved that is the best a comparison-based search tree can promise. This lecture asks the audacious next question: can we do better than logarithmic? Can lookup cost nothing that grows with n at all? The answer is yes, but you must pay for it in a new currency — you surrender sorted order, you surrender worst-case determinism, and you take on a coin flip. What you buy is expected O(1) search, insert, and delete. We will build the hash table from the direct-address dream, watch collisions become inevitable, tame them with chaining and open addressing, then close the one hole an adversary can exploit with universal and perfect hashing.

A number to fix the stakes. Fill a hash table until it holds exactly as many items as it has slots — load factor one. Search for a key that is present and you will examine, on average, about 1.5 entries. Search for one that is absent and you will examine about 2. Those two numbers do not change when the table holds a thousand keys, a million, or a billion. The cost of access is constant in the size of the data — the single most useful fact in all of practical computing.

And yet there is a shadow. The worst case is Θ(n) — every key in one slot, a linked list wearing a table's clothes — and for any fixed hash function, an adversary who can read your code can hand you exactly the input that triggers it. Reconciling the constant average with the linear worst case, and proving the average holds even against that adversary, is the whole intellectual content of this lecture.

01 the dream of constant access

What if the key told you where it lived?

I think first about what a machine is permitted to do, because the permissions fix the price. A search tree learns about its keys by comparing them, and we proved last lecture that comparing is a thin channel — one bit per question — so it cannot pin a key in fewer than log n questions. But suppose the key is not an opaque token to be compared; suppose it is a number we may read and use as an address. Then there is nothing to search. The key is the location. We walk to it in one step.

That is the whole dream, and it is worth stating as a principle before we complicate it: a lookup is free when the key can be turned into an index. An array does exactly this — A[i] in one step — because the index is the address. The dictionary problem is the project of making arbitrary keys behave like array indices. Everything that follows — the hash function, the collisions, the chains, the probe sequences, the randomized families — is engineering around the one obstacle that stands between us and that free lookup.

Let me name the problem formally so we can attack its skeleton rather than its surface. A dynamic dictionary (or symbol table, or map) maintains a set of (key, value) pairs under three operations: insert(k, v), delete(k), and search(k). Keys are drawn from a universe U. We will hold at most n keys at once. The question of this lecture is exactly: how cheaply can the three operations run, as a function of n, if we are allowed to read the bits of a key?

the formal lensNotice what we are about to give up. A search tree keeps keys in sorted order, so it answers range queries, successor, predecessor, and min/max almost for free. A hash table scatters keys deliberately — it destroys order to gain speed. The right structure is never “the fast one” in the abstract; it is the one whose retained invariant matches the queries you will ask. Hashing keeps membership and nothing else.
02 objectives & prerequisites

What you will be able to do

  • Explain why a direct-address table gives O(1) operations yet is unusable for real keys, and how a hash function trades Θ(|U|) space for Θ(m) at the price of collisions.
  • Implement both collision strategies — separate chaining and open addressing (linear probing, quadratic probing, double hashing) — and state the deletion subtlety that makes open addressing trickier than it looks.
  • Derive, with indicator variables, that a chained table under simple uniform hashing answers a search in expected Θ(1+α) time, where α=n/m is the load factor.
  • State and use the open-addressing probe bound 1/(1−α), and read off why a table must be resized before it fills.
  • Define a universal family of hash functions and prove that drawing h at random from it gives expected Θ(1+α) access for every input — defeating the adversary by randomizing the function, not hoping about the data.
  • Construct the FKS perfect-hashing scheme: O(n) space and O(1) worst-case lookup for a static set, and justify the quadratic second-level table by the birthday bound.
  • Diagnose the failure modes: adversarial hash flooding, primary clustering, the open-addressing tombstone bug, mutable keys, and the silent assumption that real hash functions behave uniformly.

03 the idea that almost works

Direct addressing, and the wall it hits

Start with the purest version of the dream. Suppose the universe of keys is small — say every key is an integer in {0, 1, …, |U|−1}. Then allocate an array T of |U| slots and store the value for key k at T[k]. This is the direct-address table. Every operation is a single array access:

function insert(T, k, v): T[k] = v        # O(1)
function search(T, k): return T[k]          # O(1)
function delete(T, k): T[k] = NIL      # O(1)

Perfect worst-case O(1), no probability, no cleverness. So why isn't every dictionary a direct-address table? Because of the size of U. The cost is Θ(|U|) space whether you store one key or a million, and real key universes are astronomically large. A 64-bit integer key has |U| = 2⁶⁴ ≈ 1.8×10¹⁹ — a table you cannot allocate in this universe, let alone fill. Strings, URLs, and tuples are worse still. We routinely store n = 10⁶ keys drawn from a universe of size 2⁶⁴: the direct-address table would be 99.99999…% empty.

Now extract the skeleton of the difficulty. We have a huge address space we cannot afford and a tiny occupancy we actually need. The fix writes itself: choose a table size m proportional to n, not to |U|, and install a function that folds the universe down onto those m slots. That folding function is the hash function h : U → {0, 1, …, m−1}, and the array of m slots it feeds is the hash table. Key k now lives near slot h(k) instead of at slot k.

Why is a collision unavoidable? The pigeonhole principle: any function from a set of size > m into m slots must send two elements to the same slot. Since |U| > m always (that was the entire point), every hash function has colliding pairs. We cannot escape collisions; we can only arrange that, on the keys we actually store, they are rare and cheap. That reframing — collisions are certain in the universe but should be improbable on the sample — is the bridge from a deterministic worry to a probabilistic guarantee.

04 the fold, designed

What makes a hash function good

A hash function has one job: spread keys across the m slots as evenly as possible, so that no slot is overloaded. The ideal we analyse against is the simple uniform hashing assumption (SUHA): each key is equally likely to hash to any of the m slots, independently of where the others go. No real, deterministic function achieves this for all inputs — §08 explains why and how we repair it — but SUHA is the clean model in which the cost formulae are derived, exactly as the comparison model was the clean model for sorting's lower bound.

Two classic constructions, both assuming the key has already been turned into a non-negative integer:

The division method

h(k) = k mod m. One instruction, very fast. The catch is the choice of m. If m = 2ᵖ, then k mod m is just the low p bits of k — the high bits are thrown away, so any structure in the upper bits is invisible to the table and patterned keys collide en masse. The standard remedy is to pick m to be a prime not close to a power of two, so the remainder mixes all the bits of the key.

The multiplication method

h(k) = ⌊ m · (k·A mod 1) ⌋ for an irrational-flavoured constant 0 < A < 1 (Knuth suggests A ≈ 0.618, the golden ratio's fractional part). Multiply, take the fractional part, scale to m. It is insensitive to the choice of m, so m = 2ᵖ becomes convenient again, and it mixes the bits far better than raw division.

a hash function is not a checksum, nor a cipherThree different goals get confused. A hash-table function optimises uniform spread and speed; it need not be secure. A cryptographic hash (SHA-256) optimises irreversibility and collision-resistance against an adversary, and is far too slow for a table's hot path. A checksum (CRC) optimises error detection. Using the wrong one is a real bug — a cryptographic hash in an inner loop is needless cost; a fast table hash exposed to untrusted input is a denial-of-service hole (§12).

Whatever the method, the table needs one more parameter, and it is the one every cost formula is written in terms of. The load factor is the ratio of stored keys to slots:

load factor — the single dial that governs cost
α=nm ,  the average number of keys per slot.

Read α as “how full.” At α = 0.5 the table is half full; at α = 1 it holds one key per slot on average; chaining can run at α > 1 but open addressing cannot reach 1 at all. The entire performance story of a hash table is a function of α — and crucially not of n directly. Hold α fixed by growing m with n (a doubling resize, exactly the amortised trick of Lecture 2) and the per-operation cost stays flat as the table grows without bound. That is where “constant” comes from.

A hash function is an attempt to mechanize randomness — to make a deterministic map behave as if it had scattered the keys by chance.
05 collisions, absorbed

Separate chaining and its expected cost

The most direct way to handle collisions is to admit them and store the colliding keys together. In separate chaining, each slot T[j] holds a linked list (a “chain”) of all keys that hash to j. Insert prepends to the list; search scans it; delete unlinks from it.

function insert(T, k, v):
    j = h(k)
    prepend (k, v) to T[j]            # O(1): no scan needed to insert

function search(T, k):
    j = h(k)
    for (key, val) in T[j]:           # walk the chain at slot j
        if key == k: return val
    return NOT_FOUND

function delete(T, k):
    j = h(k)
    unlink the node with key k from T[j]

Insert is unconditionally O(1). The cost of search and delete is the length of the chain we land on. So the entire question is: how long is a chain? This is where the probability earns its place.

Unsuccessful search

Search for a key k that is not in the table. We compute h(k), land on some slot, and scan its whole chain to the end before concluding “absent.” The work is the length of that chain. Under SUHA each of the n stored keys landed in slot h(k) with probability 1/m independently, so let Xᵢ indicate that stored key i is in that slot:

expected chain length = expected work of an unsuccessful search
E[ ∑i=1n Xi ] = ∑i=1n E[Xi] = ∑i=1n 1m = nm = α

Including the one hash computation and the one walk to the end, the expected cost is Θ(1 + α). Linearity of expectation did all the work — note we never needed the chain lengths to be independent of one another, only the expectation of a sum equalling the sum of expectations.

Successful search

A successful search for a key that is present scans, on average, only half its chain — it stops when it finds the key, not at the end. Averaging over the n stored keys (each equally likely to be the target), and counting one comparison for the key itself plus one for each key inserted into its chain after it, the expected number of comparisons works out to a clean closed form:

expected comparisons in a successful search
1+ α2 − α2n = Θ(1+α)
derive the successful-search bound, term by term

Number the keys k₁, …, kₙ in the order they were inserted, and insert at the head of each chain. The number of elements examined when searching for kᵢ equals 1 (for kᵢ itself) plus the number of keys that were inserted after kᵢ into the same chain — because head-insertion puts later arrivals in front of kᵢ. Let Xᵢⱼ indicate h(kᵢ)=h(kⱼ), with E[Xᵢⱼ]=1/m under SUHA. Then the cost of searching for kᵢ is 1 + Σⱼ>ᵢ Xᵢⱼ, with expectation 1 + (n−i)/m. Average over i = 1 … n:

1n ∑i=1n 1+n−im = 1+ 1nm n2−n(n+1)2 = 1+n−12m = 1+α2−α2n

The middle step uses Σ(n−i) = n(n−1)/2. The result is Θ(1+α) — the same order as the unsuccessful search, with a constant smaller by about half.

The headline now follows. If we keep α = O(1) — that is, keep the table size proportional to the number of keys — then every dictionary operation runs in expected Θ(1) time, independent of n. At α = 1, a successful search touches ≈ 1.5 entries and an unsuccessful one ≈ 2. Those are the numbers from the hook, now earned.

07 store inside the table itself

Open addressing & the probe sequence

Chaining stores collisions in lists outside the table. Open addressing takes the opposite vow: every key lives in the table itself, one key per slot, no external lists, no pointers. When a key's home slot is taken, we follow a deterministic probe sequence of alternative slots until we find an empty one. The hash function gains a second argument — the probe number — and produces, for each key, a sequence h(k,0), h(k,1), …, h(k,m−1) that ideally visits every slot.

The simplest rule is linear probing: on a miss, try the next slot, wrapping around.

linear probing — try home, then home+1, home+2, …
h(k,i) = (h'(k)+i) modm 
function insert(T, k, v):
    for i in 0 .. m-1:
        j = (h(k) + i) mod m         # the probe sequence
        if T[j] is EMPTY or T[j] is TOMBSTONE:
            T[j] = (k, v); return
    error "table full — must resize"

function search(T, k):
    for i in 0 .. m-1:
        j = (h(k) + i) mod m
        if T[j] is EMPTY: return NOT_FOUND   # a true gap ends the search
        if T[j] is not TOMBSTONE and T[j].key == k:
            return T[j].val
    return NOT_FOUND

Let me run it on the same seven keys as §06, so you can compare the two strategies on identical input. With h(k) = k mod 8 and linear probing: 21→5, 9→1, 14→6, 17 wants 1 (taken) → probes to 2, 28→4, 33 wants 1 (taken), 2 (taken) → probes to 3, 5 wants 5 (taken), 6 (taken) → probes to 7.

The cost, and why α must stay below 1

Under the uniform hashing assumption (the probe sequence is a uniformly random permutation of the slots), the expected number of probes in an unsuccessful search has a famous bound:

expected probes, unsuccessful search, open addressing
E[probes] ≤ 11−α
where 1/(1−α) comes from — a geometric series

Every search makes a first probe. It needs a second only if the first slot was occupied, which happens with probability n/m = α. It needs a third only if the first two were occupied: probability (n/m)·((n−1)/(m−1)) ≤ α². In general the probability of needing at least i probes is at most αⁱ⁻¹. Summing the tail gives the expected count:

E[probes] = ∑i=1∞ Pr[≥ i probes] ≤ ∑i=0∞ αi = 11−α

The successful-search bound is gentler, (1/α)·ln(1/(1−α)), but it diverges at α→1 just the same.

Read the formula as a warning. At α = 0.5 an unsuccessful search costs ≤ 2 probes; at α = 0.9 it costs ≤ 10; at α = 0.99 it costs ≤ 100. The curve is a wall at α = 1, where the table is exactly full and a search may probe every slot. So open-addressed tables must be resized before they fill — typically kept below α ≈ 0.7. Linear probing is worse than this idealised bound because real probe sequences are not independent permutations — clustering correlates them. The cures are better probe sequences:

  • Quadratic probing: h(k,i) = (h'(k) + c₁i + c₂i²) mod m. The jumps grow, so displaced keys do not pile into one contiguous run — this kills primary clustering. But two keys with the same home slot still share an entire probe sequence (secondary clustering).
  • Double hashing: h(k,i) = (h₁(k) + i·h₂(k)) mod m, where a second hash function sets the step size. Now even keys with the same home slot probe differently, because h₂ distinguishes them. This is the closest practical approach to the uniform-hashing ideal.
the tombstone — open addressing's sharpest edgeYou cannot delete by simply emptying a slot. In §06's probed table, 33 sits at slot 3 only because it walked through slots 1 and 2. If you delete 17 at slot 2 by marking it EMPTY, a later search for 33 probes slot 1 (miss), slot 2 (EMPTY → stop, wrongly conclude absent) and never reaches slot 3. The fix is a tombstone: a special DELETED marker that search treats as “keep going” but insert treats as “reusable.” Tombstones accumulate and slowly degrade performance, which is a second reason open-addressed tables need periodic rebuilds.

08 defeat the adversary

Universal hashing: randomize the function, not the data

Now the uncomfortable truth SUHA was hiding. A real hash function is fixed and deterministic — you write it down, you ship it. The pigeonhole principle (§03) guarantees that for any fixed h, some block of ⌈|U|/m⌉ ≥ n keys all map to the same slot. An adversary who can read your code — a user submitting form fields, JSON keys, HTTP headers — can choose exactly those keys, collapse every one into a single chain, and turn your expected-O(1) table into a Θ(n) linked list. This is not hypothetical; it is the hash-flooding denial-of-service attack, and it has taken down real web frameworks (§12).

Here is the resolution, and it is the same move that saved quicksort in Lecture 6. The flaw is not in any one function; it is in fixing the function in advance. So do not fix it. Keep a whole family of hash functions and, at table-creation time, pick one at random. The adversary chooses keys without knowing which h you will draw; your guarantee becomes an expectation over your coin flips, holding for every input. We have moved the randomness out of an unjustified assumption about the data and into an honest algorithmic choice we control.

For this to work the family must be good in a precise sense:

universal family — collisions are rare for every distinct pair
Prh∈H [h(x)=h(y)] ≤ 1m for every x≠y

In words: pick h at random from H; then any two fixed, distinct keys collide with probability at most 1/m — exactly the collision rate of an idealised random function. A family with this property is called universal. The payoff theorem needs nothing more:

Theorem (universal hashing gives expected Θ(1+α) for any input). Fix any set of n keys and any key x. Draw h from a universal family H into m slots. Then the expected number of keys colliding with x is at most α = n/m.

Proof. For each stored key y ≠ x let Cⱼ = 1 if h(y) = h(x). By universality E[Cⱼ] = Pr[h(y)=h(x)] ≤ 1/m. By linearity, the expected slot population around x is E[Σⱼ Cⱼ] = Σⱼ E[Cⱼ] ≤ n/m = α. There is no SUHA here and no assumption about the keys — the only randomness is our own choice of h. ■

That is the whole game. The same 1+α bound as §05, but now it holds against an adversary who picked the worst possible keys, because they could not see our coin. A concrete universal family — Carter and Wegman's, 1979 — costs only a multiply and two mods:

Carter–Wegman universal family
ha,b (k) = ((ak+b) modp) modm

Choose a prime p > |U| once. Draw a uniformly from {1, …, p−1} and b from {0, …, p−1} at table creation; those two random numbers are your chosen h. One can prove this family is universal by a short argument in modular arithmetic: for fixed x ≠ y, the pair (ax+b, ay+b) mod p ranges over all distinct ordered pairs as (a,b) varies, and at most (p−1)/m of the p−1 nonzero differences survive the final mod m as a collision — at most 1/m. Cheap to compute, provably safe on every input. This is what production hash tables actually do (often with a random seed chosen at process start) to shut the flooding attack.

the through-lineLecture 6 converted “quicksort is slow on some inputs” into “quicksort is slow on some coin flips, with vanishing probability,” by randomizing the pivot. Universal hashing performs the identical conversion for the dictionary: “this hash is bad on some key sets” becomes “our random hash is bad with vanishing probability, for whatever key set you bring.” Randomization is not a hack here — it is the formal instrument that makes a worst-case-fragile structure robust.
09 when the set never changes

Perfect hashing: O(1) worst case, not just expected

Everything so far has bought an expected constant with a lurking Θ(n) worst case. Can we ever get a worst-case O(1) guarantee — no probability in the promise the caller hears? Yes, for the important special case of a static set: the keys are fixed and known in advance (think reserved words of a language, a routing table, a content-addressed index). For static sets, perfect hashing achieves O(1) worst-case lookup using only O(n) space. The construction is the FKS scheme (Fredman, Komlós, Szemerédi, 1984), and it is a beautiful two-level idea.

A perfect hash function for a set has no collisions at all on that set. The trouble is that a single collision-free table needs to be large: hashing n keys with no collision into one table generally requires size ≈ n² (the birthday bound, below) — far too much space. FKS gets the best of both: a first level of size n to keep space linear, and a second level of tiny squared tables to kill collisions exactly.

  1. Level 1. Hash all n keys into a table of size m = n with a universal h. Collisions happen; let nⱼ be the number of keys landing in slot j.
  2. Level 2. For each slot j, build a secondary hash table of size nⱼ² with its own universal hash hⱼ, chosen so it is collision-free on those nⱼ keys.

A lookup is now exactly two hash evaluations — slot j = h(k), then position hⱼ(k) inside the collision-free secondary table — and at most one key comparison. Two probes, worst case, always.

Two facts make this work, and both are pure probability:

Why a squared table has no collisions (the birthday bound)

Hash nⱼ keys into a table of size nⱼ² with a universal function. The expected number of colliding pairs is ∙C(nⱼ,2)·(1/nⱼ²) < nⱼ²/2 · 1/nⱼ² = 1/2. By Markov's inequality, the probability of any collision is below 1/2 — so a randomly drawn hⱼ is collision-free with probability over a half. Draw, test, redraw if needed: in expectation fewer than two tries find a perfect hⱼ.

Why the total space is still O(n)

The space is dominated by the second level, Σⱼ nⱼ². The identity Σⱼ nⱼ² = n + 2·(number of colliding pairs at level 1) turns this into an expectation we already know how to take:

expected second-level space, level-1 table of size m = n
E[ ∑j nj2 ] = n+2⋅ n(n−1)2 ⋅ 1n = 2n−1 <2n

So the expected total table space is O(n); pick a level-1 h whose Σ nⱼ² is below 4n (Markov again: since the expectation is below 2n, at most half of the draws can reach 4n, so at least half qualify) and the bound becomes a guarantee. The result is the striking combination the section promised: O(n) space and O(1) worst-case lookup, with all the probability spent once, at build time, never at query time. Modern variants (cuckoo hashing, and the minimal-perfect-hash generators behind compilers and search indexes) descend directly from this idea.

10 the tail the average hides

Concentration: how bad can the worst slot be?

An expectation is a promise about the average operation. But a single slow operation — the unlucky slot with a long chain — can dominate a latency budget. So the honest question is not only “what is the expected chain length?” (we know: α) but “how long is the longest chain likely to get?” That is a concentration question, and it is exactly the balls-in-bins model from Lecture 5: throw n balls (keys) into n bins (slots) uniformly, and ask for the fullest bin.

Maximum load. When n keys are hashed uniformly into n slots, the expected length of the longest chain is Θ (log n / log log n) with high probability — even though the average chain has length 1. So although typical access is constant, the worst single access in a table of a million keys is around a dozen, not one. The gap between 1 and log n / log log n is the tail the title warns about.

Two consequences worth carrying:

  • Tighten the tail with two choices. If each key is hashed by two independent functions and inserted into the shorter of the two candidate chains (“the power of two choices”), the maximum load collapses from Θ(log n / log log n) to Θ(log log n) — an exponential improvement in the tail for one extra hash. This is the engine behind modern load balancers and cuckoo hashing.
  • Keep α bounded by resizing. Because every cost is a function of α, the table must grow as keys arrive. Double m whenever α crosses a threshold (say 0.75) and re-hash everything into the larger table. A single resize costs Θ(n), but it happens rarely enough that the amortised cost per insertion stays O(1) — precisely the doubling-array argument of Lecture 2, reused here for hash tables.
three promises, kept straightThis syllabus has now built three different cost guarantees for the same dictionary problem. A balanced tree (Lecture 7) promises O(log n) worst case, every time. A chained hash table promises O(1) expected, with a rare Θ(n) tail. FKS perfect hashing promises O(1) worst case, but only for a static set. There is no universally best answer — only a match between the promise you need and the price you will pay in space, order, and dynamism.

A practitioner's reading: open addressing wins on small, cache-friendly tables with a known load ceiling and few deletions — linear probing's sequential memory access often beats chaining's pointer-chasing despite its worse clustering math (recall the locality lessons of Lecture 1). Chaining wins when deletions are frequent or the load factor is hard to bound, because removing a node is trivial and α > 1 degrades gracefully. Universal hashing is not optional anywhere untrusted input reaches the keys. And perfect hashing is the specialist for fixed dictionaries that are built once and queried forever.

12 where it breaks

Failure modes & common mistakes

Keep the gap between the idealised model and the deterministic function in view. Here is where hashing bites — the security holes, the silent quadratics, the deletion bug that corrupts the table, the assumptions that are false in production.

1 · Hash flooding — the adversarial worst case is a weapon

A fixed hash function exposed to untrusted keys is a denial-of-service vulnerability. An attacker computes keys that all collide, collapses every operation to Θ(n), and a single crafted request burns minutes of CPU. This is not theoretical — it hit PHP, Java, Python, Ruby, and ASP.NET web stacks in 2011–2012, and the fix shipped industry-wide was exactly §08: a randomly seeded universal (or keyed, like SipHash) hash chosen at process start. If keys can come from outside your program, a deterministic hash is a bug, not a performance choice.

2 · A bad hash function silently destroys the guarantee

Every bound on this page assumes good spreading. Ship h(k) = k mod 2ᵖ and you key on the low bits only; feed it pointers or aligned addresses (all ending in 000) and most slots are dead while a few overflow. Worse, a hash that ignores part of a composite key — hashing only the first field of a struct — turns whole classes of distinct keys into collisions. Test your hash's distribution, not just its correctness; a hash that compiles and “works” can still be quietly quadratic.

3 · The open-addressing deletion bug (deleting to EMPTY)

The single most common hash-table bug: in an open-addressed table, deleting a key by marking its slot EMPTY severs the probe chains that ran through it, so later searches for displaced keys stop early and report false absences — silent data loss. You must use a tombstone (§07). And because tombstones accumulate and lengthen probe sequences over time, a long-lived table needs periodic full rebuilds to flush them.

4 · Letting the load factor drift toward 1

Open-addressing cost is 1/(1−α) — it does not degrade gracefully, it detonates. At α = 0.99 an average search probes a hundred slots; at α = 1 insertion never terminates. Forgetting to resize, or resizing too late, converts a fast table into a hang. Pick a ceiling (commonly 0.7 for open addressing, higher for chaining) and resize before crossing it. Resizing is the amortised-doubling discipline of Lecture 2; skipping it is not an optimisation, it is a latent outage.

5 · Mutable keys — hashing something that then changes

A hash table places a key by h(k) at insertion time. If the key object is later mutated so that h(k) changes, the key is now filed under its old hash but searched for under its new one — it becomes unreachable while still occupying space, and the invariant “a key sits at h(k)” is broken. Keys must be immutable, or at least hash-stable for their time in the table. This is why mutable lists cannot be dictionary keys in most languages, and why equals and hashCode must be defined consistently — two keys equal under == must share a hash, or lookups miss.

6 · Mistaking the expectation for a guarantee

“Hash tables are O(1)” is shorthand, not a theorem about every operation. The bound is expected, the worst case is Θ(n), and the worst single access in a large table is Θ(log n / log log n) even in the average case (§10). In a hard-real-time or worst-case-latency-bounded setting (avionics, high-frequency trading, an SLA on the 99.99th percentile), an expected constant may be unacceptable — reach for a balanced tree's worst-case O(log n) or a static perfect hash. Always ask which promise the caller actually needs.

7 · Integer overflow and sign in hash computation

A polynomial string hash Σ sᵢ·Bⁱ overflows machine integers fast. That is fine — overflow is just arithmetic mod 2⁶⁴ — provided you account for it (and never index with a negative result in languages where % can return a negative). Forgetting the sign of the modulo, or mixing signed and unsigned, produces out-of-bounds indices or skewed distributions. Reduce to [0, m) deliberately, not by accident.

8 · Reaching for a hash table when you needed order

The meta-mistake. A hash table answers membership and point lookup and nothing else. The moment you need sorted iteration, range queries, nearest-key, successor/predecessor, or min/max, the scattering that made hashing fast is now your enemy, and you are sorting the keys on every query. That is the signal you wanted the ordered dictionary of Lecture 7, not this one. Choose the structure by the queries, never by the headline speed.

Subarray sum equals K

hash map as a prefix-sum counter · O(n) · LeetCode 560

Given an integer array nums and an integer k, return the total number of contiguous subarrays whose elements sum to exactly k. The brute force is Θ(n²); reach O(n) with one pass. Define the prefix sum P[i] = nums[0] + … + nums[i−1]; a subarray (i, j] sums to k exactly when P[j] − P[i] = k, i.e. P[i] = P[j] − k. Sweep left to right keeping a hash map from prefix-sum value to how many times it has occurred, and at each j add the count of P[j] − k seen so far. State why a hash map (not a sorted structure) is the right tool here, and handle the empty-prefix and negative-number cases. Note that nums may contain zeros and negatives, so two-pointer/sliding-window does not apply.

subarraySum(nums, k) -> int    # 1 ≤ n ≤ 2e4;  -1e3 ≤ nums[i] ≤ 1e3

Group anagrams

designing a canonical hash key · O(n·k) · LeetCode 49

Given an array of strings strs, group together all strings that are anagrams of one another (return the groups in any order). The art is choosing a canonical key that two strings share iff they are anagrams, then hashing on it: either the sorted characters ("eat" → "aet", key cost O(k log k)) or a length-26 count vector (key cost O(k)). Use a hash map from canonical key to the list of original strings. Argue which canonical form gives the better total complexity, and explain what property the key must have for the grouping to be correct — connect this back to §12's rule that equal keys must hash equal.

groupAnagrams(strs) -> List[List[str]]   # 1 ≤ n ≤ 1e4, 0 ≤ len(s) ≤ 100, a–z

Insert, delete, and getRandom in O(1)

hash map + dynamic array · expected O(1) all ops · LeetCode 380

Design a set structure supporting insert(x), remove(x), and getRandom() — return a uniformly random current element — each in average O(1). Neither structure alone suffices: a hash map gives O(1) insert/remove/membership but cannot pick a uniform random element in O(1); a dynamic array gives O(1) random indexing and append but O(n) removal from the middle. Combine them: an array holds the elements (so getRandom is one random index) and a hash map sends each value to its index in the array (so removal is O(1)). The trick for remove: swap the victim with the last array element, pop the tail, and fix the moved element's stored index. Explain why the swap-to-tail is what keeps removal constant, and exactly which map entries you must update.

class RandomizedSet:
    insert(val) -> bool;  remove(val) -> bool;  getRandom() -> int
4

No fixed hash function can escape the worst case

pigeonhole / adversary argument · proof

Prove the claim that motivates universal hashing. Let h : U → {0, …, m−1} be any fixed, deterministic hash function on a universe with |U| > (n−1)·m. Show that there exists a set S of n distinct keys that all hash to the same slot — so that, for this S, a chained table built with h degrades to a single chain and answers a search in Θ(n) time. Argue it cleanly with the pigeonhole principle (some slot has at least ⌈|U|/m⌉ ≥ n preimages). Then explain in two or three sentences why drawing h at random from a universal family escapes this argument even though every single function in the family still has its own bad set — i.e., what exactly the randomization changes about when the adversary must commit to the keys.

14 recap & next

The one thing to remember

Hashing buys expected-constant access by turning a key into an address and paying for collisions in probability. Fold the universe onto m ≈ n slots; absorb the unavoidable collisions with chaining or open addressing; and read every cost off the load factor α = n/m as 1+α (chaining) or 1/(1−α) (open addressing). The lurking Θ(n) worst case is real but defanged: universal hashing randomizes the function so the guarantee holds against any adversary, and perfect hashing spends all the randomness at build time to deliver O(1) worst-case lookup on a static set in O(n) space. You traded order and determinism; you bought a constant that does not grow.
