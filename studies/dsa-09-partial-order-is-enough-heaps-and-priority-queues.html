Build onTree arrays

Core invariantA heap stores enough order to expose one extreme; it does not sort all siblings.

Try this first · Is the second smallest key always a child of the root in a min heap?

Yes. Every other node has an ancestor that is one of the root's children, so a child has a key no larger than it.

A sorted array knows everything: the rank of every element. Most of the time you never use that knowledge — you only ask, again and again, “what is the most extreme thing left?” This lecture builds the structure that answers exactly that question and not one bit more: the binary heap, a complete tree that lives invisibly inside a flat array, peeks at its extremum in O(1), and repairs itself in O(log n). We will derive it from the priority-queue contract, prove the startling fact that you can build one in Θ(n) time, and turn it into an in-place sort.

A dilemma to fix the stakes. You must repeatedly grab the smallest of a changing set of n numbers and keep adding new ones — the inner loop of Dijkstra's shortest paths, of Prim's spanning tree, of every event-driven simulation and every top-k over a stream. Keep the set in an unsorted array: adding is O(1), but finding the smallest is O(n). Keep it sorted: finding the smallest is O(1), but inserting in order is O(n). Either way one of the two operations you do constantly is linear, and n rounds cost Θ(n²).

The heap refuses the trade. Insert and extract-min both cost O(log n); peeking the minimum is O(1); and assembling a heap out of n loose items costs only Θ(n). The same n rounds now cost Θ(n log n). The trick that buys this is to stop maintaining a total order and maintain only a partial one — just enough so the extremum is always on top.

01 a question, asked a million times

You don't need the whole order

I think first about what an algorithm is actually asked, because the question fixes the cheapest honest answer. Survey the great repeat-offenders — Dijkstra, Prim, Huffman coding, discrete-event simulation, the k largest items of a billion-row stream, an operating-system scheduler choosing the next task — and a single pattern surfaces. None of them ever needs the data fully sorted. Each one runs a loop that does exactly two things: pull out the current extremum, and add some new elements. Over and over.

If that is the whole demand, then sorting is a waste. Sorting establishes a total order — it pins the rank of every pair of elements — and we proved last lecture that doing so by comparisons costs Ω(n log n) up front and gives you a brittle arrangement that any insertion shoves out of place at O(n) cost. We are paying for knowledge of every rank and using only the top one.

So strip the requirement to its skeleton. We want a container that supports a tiny contract — add an element, look at the extremum, remove the extremum — and supports all three cheaply while the set keeps changing. That object is the priority queue, and its canonical implementation is the binary heap. The whole lecture is the unfolding of one idea: maintain only as much order as the question requires.

the formal lensA data structure is the materialisation of an invariant — a property you promise to keep true after every operation, traded against the cost of keeping it. A sorted array keeps the strongest invariant (total order) at the highest maintenance price. The heap keeps a deliberately weaker invariant, and the weakness is the whole point: less to maintain means cheaper to maintain. Choosing the minimal sufficient invariant is the central act of data-structure design.
02 objectives & prerequisites

What you will be able to do

  • Define the heap property and explain why this partial order is exactly enough to keep the extremum at the root, yet far cheaper to maintain than a total order.

One fact you must hold firmly: in a complete binary tree — every level full except possibly the last, which fills left to right — a tree of n nodes has height ⌊log₂ n⌋. That bound is the source of every log n on this page; the heap is engineered to stay complete precisely so the bound never slips.

03 the contract, before the mechanism

The priority-queue ADT

Before a single array, fix the abstraction. An abstract data type is a specification: a set of operations and the promises they keep, said without committing to how they are stored. The priority queue holds a multiset of elements, each with a comparable key (its priority), and promises four operations:

  • insert(x) — add element x to the collection.
  • peek() — return the element of extremal priority without removing it.
  • extract() — remove and return the element of extremal priority.
  • build(list) — form a priority queue from n given elements at once.

“Extremal” means the maximum (a max-priority-queue) or the minimum (a min-priority-queue); the two are perfect mirror images, obtained by flipping every comparison. Throughout the build I will work with the max version because it makes heapsort fall out naturally; every statement holds for the min version with > swapped for <. Some applications add decrease-key / increase-key (re-prioritise an element already inside) — we will meet its sharp edge in §10, because it is what Dijkstra leans on.

Now the engineering question: which implementation honours this contract cheaply? Hold the ADT fixed and audit the obvious candidates. The deciding column is the one in red.

Three implementations of the same priority-queue contract (n elements)
implementation insert peek extremum extract extremum build from n

Sorted array (descending)O(n)O(1)O(1)O(n log n)

The naive rows each hide one O(n) landmine on an operation the caller runs constantly. The heap row has no linear operation at all (its build is linear, but that is paid once). That single observation is why the heap exists.

The sorted array is seductive — two of its operations are O(1)! — but the third, insert, is fatal in any workload that interleaves insertions with extractions, which is precisely the workload §01 catalogued. The heap's genius is to be uniformly good rather than spikily great: nothing it does is ever worse than logarithmic.

04 the central insight

Partial order is enough

Here is the move that makes the table's last row possible. A sorted array enforces a total order: for every pair of positions you know which is larger. That is a great deal of enforced structure — Θ(n) ordering relations along the sequence — and structure is exactly what costs money to preserve when the set changes. Ask instead for the weakest structure that still keeps the extremum findable in O(1).

The answer is a single local rule. Arrange the elements as the nodes of a binary tree and demand only this:

the max-heap property

Every node's key is ≥ the keys of its children. Equivalently: along every root-to-leaf path the keys never increase.

That is all. Notice what it does not say: it says nothing about the order between siblings, nothing about cousins, nothing about two nodes in different subtrees. A heap is profoundly under-determined — the same six keys admit many valid heaps — and that looseness is the saving. We are no longer maintaining Θ(n) pairwise facts; we are maintaining one inequality per parent–child edge, and there are only n−1 edges, each repairable locally.

Yet the rule is strong enough to do the one job we need. Apply it transitively: the root is ≥ its children, which are ≥ their children, and so on down. So the root dominates every node in the tree — the maximum sits at the top, readable in O(1). We have purchased exactly the capability the priority queue sells, and nothing more. This is the formal heart of the lecture: the heap property is the minimal invariant that keeps the extremum at a known address.

A sorted array answers every question about rank. A heap answers one. Charge only for the question you actually ask.

Two immediate consequences worth naming. First, a heap is not sorted: reading the array left to right gives no meaningful order beyond “parents precede the children that happen to follow them.” Searching a heap for an arbitrary value is still O(n) — it is the wrong tool for membership. Second, because the constraint is so local, a single element that violates it can be slid back into compliance by swapping it along one root-to-leaf path — a walk of length at most the tree's height. That walk is the whole mechanism, and we build it in §06.

05 no pointers required

A tree hidden inside an array

A tree usually means nodes and pointers — each node carrying the addresses of its children, an allocation per element, cache misses on every hop. The heap pays none of that, and the reason is the second design decision: we insist the tree be complete. Every level is entirely full except possibly the last, which is packed from the left with no gaps. A complete tree has a rigid, predictable shape — and a rigid shape can be addressed by arithmetic instead of pointers.

Lay the nodes into an array A in level order: the root at index 0, then the two nodes of level 1, then the four of level 2, left to right. Because completeness forbids holes, the array is dense — indices 0…n−1 with nothing skipped — and the family relationships become fixed index formulas. For a node at index i (zero-based):

the implicit-tree index arithmetic (0-based)
left child=2i+1 ,     right child=2i+2 ,     parent= ⌊i−12⌋

So “go to my left child” is a multiply-and-add, not a dereference. The structure is implicit: there is no tree object anywhere in memory, only an array and these three formulas. We have stored the shape in our arithmetic and spent zero bytes on it. (This same implicit complete-tree layout returns next lecture for Fenwick and segment trees — learn it once here.) Where do the leaves live? In an n-element heap, any index i ≥ ⌊n/2⌋ has its first child 2i+1 ≥ n, off the end of the array — so the second half of the array, indices ⌊n/2⌋…n−1, are the leaves. That single fact — half of all nodes are leaves — is the seed of the linear-time build in §07.

06 one element out of place

Two repairs: sift up, sift down

Every heap operation reduces to a single primitive: a lone element violates the heap property while everything else already obeys it, and we slide that element along one path until order is restored. There are exactly two directions it can travel.

Sift-up — the engine of insert

To insert, append the new key at the first free slot — the next leaf, index n, which keeps the tree complete — and then bubble it up. Compare it with its parent; if it is larger (max-heap), it violates the property, so swap them and repeat one level higher. The element rises until it meets a parent at least as large, or reaches the root. Because it climbs at most the height of the tree, insert is O(log n).

function siftUp(A, i):                 # A[i] may be too big for its place
    while i > 0:
        parent = (i - 1) // 2          # integer floor — the parent index
        if A[i] ≤ A[parent]: return     # parent dominates ⇒ property restored
        swap(A[i], A[parent])
        i = parent                       # keep climbing the single path

function insert(A, x):
    A.append(x)                       # new leaf at index n — tree stays complete
    siftUp(A, len(A) - 1)             # O(log n)

Sift-down — the engine of extract

The maximum is at the root, A[0] — trivial to return. The art is repairing the hole it leaves. Move the last leaf into the root (which keeps the tree complete), shrink the array by one, and now sink that interloper down. Compare it with both children, swap it with the larger of the two (this is the step everyone gets wrong), and repeat until it dominates its children or becomes a leaf. Again it travels one root-to-leaf path, so extract is O(log n).

function siftDown(A, i, n):              # restore the subtree rooted at i, heap size n
    while true:
        l = 2*i + 1;  r = 2*i + 2
        largest = i
        if l < n and A[l] > A[largest]: largest = l
        if r < n and A[r] > A[largest]: largest = r    # compare BOTH children
        if largest == i: return          # dominates its children ⇒ done
        swap(A[i], A[largest])
        i = largest                      # follow the larger child downward

function extractMax(A):
    top = A[0]                         # the root is the maximum — O(1) to read
    A[0] = A[len(A) - 1]            # last leaf takes the throne
    A.pop()                           # drop the now-duplicated leaf
    if A: siftDown(A, 0, len(A))      # sink the interloper — O(log n)
    return top

The asymmetry is worth dwelling on. siftUp compares against one node (the unique parent); siftDown must compare against two (both children) and choose the larger, because swapping with the smaller child would leave that smaller child lording over its larger sibling — an instant violation. Forgetting this is the single most common heap bug, and it is failure mode 2 in §10.

07 the surprising linear bound

Building a heap in Θ(n)

Suppose you already hold all n elements and want a heap. The obvious route — insert them one by one — costs n sift-ups of up to log n each, i.e. O(n log n). We can do strictly better, and the better way is one of the most counter-intuitive small results in the subject: a heap can be assembled in linear time.

The method is bottom-up. Drop all n elements into the array in any order, then run siftDown on every internal node, from the last one back to the root:

function buildHeap(A):
    n = len(A)
    for i from n//2 - 1 down to 0:   # every internal node, deepest first
        siftDown(A, i, n)              # leaves (i ≥ n//2) are already valid heaps

Two things make it correct. We skip the leaves — recall from §05 that indices ⌊n/2⌋…n−1 are leaves, and a single node trivially satisfies the heap property. And we go deepest-first, so when siftDown processes node i, both of its subtrees are already valid heaps — exactly the precondition siftDown needs to merge them, through i, into one larger heap. By induction the root call produces a heap over the whole array.

Now the cost, and the surprise. A loose bound says n/2 sift-downs of O(log n) each, giving O(n log n) — true but wasteful, because almost every node is near the bottom, where sift-down barely moves. A node at height h (distance to its deepest leaf) costs at most h swaps, and a heap of n nodes has at most ⌈n/2ʰ⁺¹⌉ nodes of height h. The total work is therefore

sum the work over heights, not over a flat log n
T(n) ≤ ∑h=0⌊logn⌋ n2h+1 ⋅h = n2 ∑h=0∞ h2h = n2⋅2 = n = Θ(n)

The series ∑h≥0 h/2ʰ converges to a constant, 2, and a constant times n is Θ(n). The intuition behind the algebra is the picture below: the expensive nodes (high up, big h) are rare, and the cheap nodes (the leaves, h = 0) are half of everything. Insertion-order build pays log n for every element because it processes them in the wrong direction — cheap ones first; the bottom-up build pays log n only for the lonely root.

Where the constant 2 comes from — the series, closed

We used ∑h≥0 h/2ʰ = 2. It follows from the standard generating identity ∑h≥0 h·xʰ = x/(1−x)² for |x| < 1. Substitute x = 1/2: the numerator is 1/2 and the denominator is (1/2)² = 1/4, so the sum is (1/2)/(1/4) = 2. To derive the identity from scratch, start from the geometric sum ∑ xʰ = 1/(1−x), differentiate both sides with respect to x to get ∑ h·xʰ⁻¹ = 1/(1−x)², then multiply by x. The finiteness of this sum — the fact that the tail decays geometrically — is the entire reason the build is linear and not log-linear.

read the result carefullyLinear build-heap does not beat the sorting barrier. It produces a heap — a partial order — in Θ(n), not a sorted array. To fully sort, you still must extract all n maxima, and that phase costs Θ(n log n), landing exactly on the Ω(n log n) floor from Lecture 06. The cheap build is real; it is the extraction that is destiny.
08 see it run end to end

Worked example: build a heap, then heapsort it

Take A = [3, 9, 2, 1, 4, 5]. We will first build a max-heap bottom-up, then sort ascending by repeatedly extracting the max into the space the heap vacates — the algorithm called heapsort. Everything happens in place, in the one array, with O(1) extra space.

Part A — bottom-up build

With n = 6, the internal nodes are indices 0,1,2 (since ⌊6/2⌋ = 3 begins the leaves). Sift down from i = 2 up to i = 0.

392145i=2: child 5 > 2 → swap
395142i=1: 9 ≥ children 1,4 → no move
395142i=0: 3 sinks — swap with 9, then with 4
945132max-heap built: [9,4,5,1,3,2]

That last i = 0 step is exactly Figure 2: 3 compares with children 9 and 5, swaps with the larger 9; then at its new spot compares with 1 and 4, swaps with 4; then it is a leaf. The array is now a valid max-heap, root 9.

Part B — sort by repeated extraction

Heapsort's move: swap the root (the max) with the last element of the current heap, then shrink the heap by one so that maximum is now frozen in its final sorted position, and sift the new root down over the smaller heap. The array splits into a shrinking heap region (left) and a growing sorted region (right). Repeat until the heap holds one element.

The result, [1,2,3,4,5,9], is sorted with no auxiliary array. Here is the whole algorithm; note that the build is the same siftDown loop from §07, and the sort phase reuses siftDown with a shrinking size argument.

function heapsort(A):
    buildHeap(A)                     # Θ(n): the cheap part
    for end from len(A) - 1 down to 1:
        swap(A[0], A[end])           # park current max just past the heap
        siftDown(A, 0, end)          # re-heap A[0..end-1] in O(log n)

Total cost: Θ(n) to build, then n−1 sift-downs of O(log n) — Θ(n log n) overall, worst case and average, with O(1) extra space. That guaranteed worst case and that constant space are heapsort's signature: unlike quicksort it can never degrade to Θ(n²), and unlike merge sort it needs no second array. Its cost is poorer locality — sift-down leaps across the array — which is why quicksort usually wins wall-clock races despite the identical asymptotics.

A practitioner's reading. The binary heap is the default priority queue everywhere because it is simple, cache-respecting for its size, allocation-free, and never worse than logarithmic on the operations that matter. Its blind spots are search and merge — and the subtle one, decrease-key, which is O(log n) only when you already hold a handle to the element's current index. Dijkstra's algorithm (Lecture 13) needs exactly that, so a real implementation carries a side map from vertex to heap-index, updated on every swap. Forgetting that map silently turns decrease-key into an O(n) search and the algorithm into a tar pit — failure mode 6.

10 where it breaks

Failure modes & common mistakes

The heap is small enough to hold entirely in your head, which makes its bugs precise — almost always an index formula, a comparison direction, or a forgotten side effect. Here is the catalogue I check against every time.

1 · Index arithmetic off by one (the 0-vs-1 based trap)

The formulas 2i+1, 2i+2, ⌊(i−1)/2⌋ are for 0-based arrays. Many textbooks use 1-based indexing, where the formulas become 2i, 2i+1, ⌊i/2⌋ — cleaner, but only if index 0 is left unused. Mixing the two conventions in one implementation corrupts the tree shape invisibly: the “heap” still looks like an array, but parents and children no longer point at each other. Pick one convention and write the three formulas down before any logic.

2 · Sifting down toward the smaller child

In a max-heap, siftDown must swap with the larger of the two children. Swap with the smaller and you promote a node above its larger sibling — an instant violation that the loop then propagates as if it were correct, scrambling the heap. Always compute largest across both children before swapping (the three-line guard in §06), and remember the right child may not exist — test r < n.

3 · Using sift-up where sift-down is needed (and vice-versa)

After extract, the element that lands on the root came from the bottom and is probably too small — it must sift down. After insert, the new leaf is probably too big for the bottom — it must sift up. Mixing them is a real bug: sift-up on the post-extract root does nothing (the root has no parent) and leaves the heap broken. Match the repair direction to where the rogue element entered.

4 · Building top-down instead of bottom-up

Running siftDown from the root toward the leaves is wrong twice over: it violates siftDown's precondition (children must already be heaps), so it can produce a non-heap; and even the insert-one-at-a-time alternative costs O(n log n). Build from index ⌊n/2⌋−1 downward to 0 — deepest internal node first — for both correctness and the Θ(n) bound.

5 · Expecting a heap to be sorted

A heap guarantees the root, and nothing else, about array order. A[1] and A[2] have no defined relationship; the second-smallest of a max-heap could be either child of the root, never deeper, but the array does not sort itself. If you need the elements in order you must extract them one by one (that is heapsort) — reading the backing array is meaningless. Likewise, do not binary-search a heap.

6 · decrease-key without an index map

Re-prioritising an element already in the heap is O(log n) — but only if you can find it in O(1). A bare heap has no such lookup, so the find degrades to an O(n) scan, demolishing the bound Dijkstra and Prim rely on. The fix is an auxiliary hash map from element to current index, meticulously updated inside every swap in both siftUp and siftDown. The most common Dijkstra performance bug is omitting that bookkeeping (or its lazy-deletion alternative: push duplicates and skip stale pops).

7 · Heapsort is not stable; quicksort-grade locality it is not

Equal keys can be reordered by the long-range swaps of siftDown, so heapsort is unstable — do not use it when a secondary order must survive. And although its asymptotics match quicksort's, those array-spanning swaps thrash the cache, so it typically loses real-time races to quicksort. Choose heapsort when you need the guaranteed Θ(n log n) worst case with O(1) space; choose quicksort for raw speed; choose merge sort for stability.

8 · Forgetting the right child can be absent

At the last internal node, the left child may exist while the right does not (an odd number of nodes). Code that reads A[2i+2] without the 2i+2 < n guard reads past the heap — into the sorted region during heapsort, or out of bounds entirely. Every child access is conditional on its index being inside the current heap size. This is the bug that makes heapsort “mostly work” on even-length inputs and corrupt odd-length ones.

K-th largest element in a stream

design / ADT · size-k min-heap · LeetCode 703

Design a class KthLargest initialised with an integer k and a starting array nums. Each call add(val) inserts val into the stream and returns the k-th largest element seen so far. Merge k sorted lists

k-way merge · min-heap of heads · LeetCode 23

You are given an array of k sorted linked lists. Merge them into one sorted list. The naive pairwise merge is O(kn); do better with a min-heap of size k holding the current head of each list. Repeatedly extract the global minimum, append it to the output, and push that node's successor. Argue the bound: each of the N total nodes is pushed and popped once at O(log k), giving O(N log k) — the heap collapses the k-way comparison to one logarithmic step. mergeKLists(lists) -> ListNode   # 0 ≤ k ≤ 1e4, total nodes ≤ 1e4

Find the median from a data stream

two heaps · balance invariant · LeetCode 295

Design a structure with addNum(x) and findMedian(), where the median of the values seen so far must be returned in O(1) and insertion in O(log n). Keep two heaps: a max-heap for the lower half and a min-heap for the upper half, maintaining the invariant that their roots straddle the median and their sizes differ by at most one. The median is then a root (odd total) or the mean of the two roots (even total). addNum(x) -> void;  findMedian() -> double
4

Sort a nearly-sorted (k-sorted) array

bounded-window heap · O(n log k) · partial order pays off

An array of n elements is k-sorted: every element is at most k positions away from its final sorted position. Sort it in O(n log k) time and O(k) extra space — beating a general sort whenever k ≪ n. The idea is a min-heap holding a sliding window of only k+1 elements: because the true minimum of the remaining elements must lie within the next k+1 slots, the heap's root is always the next output. Prove that invariant — why k+1 and not k? — and give the exact push/pop schedule.

sortKSorted(arr, k) -> void   # each arr[i] is ≤ k slots from sorted position
12 recap & next

The one thing to remember

Maintain only as much order as the question requires. The priority queue asks for the extremum and nothing else, so the heap keeps only a partial order — one inequality per parent–child edge — which keeps the maximum at the root for O(1) peeking and lets a single out-of-place element be repaired along one root-to-leaf path in O(log n). The complete-tree shape lets that whole tree live implicitly in a flat array, addressed by 2i+1, 2i+2, ⌊(i−1)/2⌋, with no pointers. And because the leaves — half the nodes — cost nothing, a heap assembles bottom-up in Θ(n); extracting all n maxima then sorts in place in Θ(n log n). Less invariant, less maintenance: that is the whole trade.

We kept one extremum cheap. Next we keep a whole range aggregate cheap — the sum, min, or max of any contiguous slice — while individual entries change. The structures that do it, the Fenwick (binary-indexed) tree and the segment tree, are built on the very trick you just learned: a complete binary tree laid implicitly into an array, addressed by index arithmetic. The partial order becomes a partial sum, and the same O(log n) reappears. Heaps also return as load-bearing machinery in Lecture 13 (Dijkstra) and Lecture 12 (Prim) — the extract-min you built here is their inner loop.
