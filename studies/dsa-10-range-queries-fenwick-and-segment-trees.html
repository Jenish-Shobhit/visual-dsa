Range Queries on Sequences: Fenwick & Segment Trees

FIELD NOTE / 10Before the long read

Build onPrefix sums

Core invariantStore aggregates at scales that let both updates and queries touch logarithmically many nodes.

Try this first · What changes if range sum queries stay fixed but point values never change?

A prefix sum array gives O(1) range queries after O(n) preprocessing. Dynamic updates motivate Fenwick or segment trees.

Give me an array and two demands at once: change any element, and aggregate any contiguous block — sum, minimum, maximum — over and over, interleaved, online. A plain array makes the change instant but the aggregate slow; a prefix-sum table makes the aggregate instant but the change slow. Each structure is fast at exactly the operation the other is slow at. This lecture builds the two structures that refuse the trade — the Fenwick tree (a tree hidden inside the bits of an index) and the segment tree (a tree hidden inside an array) — and answers both operations in O(log n).

A number to fix the stakes. Take n = 10⁶ elements and a stream of q = 10⁶ mixed operations — half updates, half range-sum queries. Serve them with the obvious method (scan the range on each query, or rebuild the prefix table on each update) and you pay Θ(n) per operation: about 10¹² elementary steps, roughly quarter of an hour of compute.

Serve them with a Fenwick or segment tree and you pay Θ(log n) ≈ 20 steps per operation: about 2×10⁷ steps total — roughly twenty milliseconds. Same answers. A 50,000× gap, bought with one idea: store partial aggregates over a logarithmic skeleton of canonical sub-ranges, never the whole and never the parts.

01 a wall with two faces

Two structures, each fast where the other is slow

I always begin by asking what an operation is permitted to touch, because the permissions fix the price. Here the workload is two operations on an array a[0…n−1], arriving interleaved and online — you cannot see them all in advance and pre-plan:

  • Update — a[i] ← x, or a[i] &mathbin{+}= δ. Change one cell.
  • Range query — aggregate a[l] ⊕ a[l{+}1] ⊕ … ⊕ a[r{-}1] for some associative ⊕ (sum, min, max, gcd, …).

Two obvious data structures each solve one side perfectly and collapse on the other. This is not bad luck; it is the shape of the problem, and seeing it clearly is half the lecture:

A the raw array

Update: write one cell — O(1). Perfect.

Range sum: add up r−l cells — O(n). A query over the whole array reads everything, every time.

B the prefix-sum table

Range sum: precompute P[k]=a[0]+…+a[k{-}1]; any range is P[r]−P[l] — O(1). Perfect.

Update: changing a[i] shifts every P[k] with k>i — O(n) to repair the tail.

So on a workload of q mixed operations, whichever structure you choose, the adversary feeds you the operation it is slow at and you pay Θ(n) each time — Θ(nq) overall. The raw array stores too little (only the leaves); the prefix table stores too much in too rigid a form (only the global running total, so one edit ripples forever). The escape is to store something in between: partial aggregates over O(n) carefully chosen sub-ranges, arranged so that both a query and an update touch only O(log n) of them.

the formal lensThe prefix table is a Fenwick tree with the tree flattened all the way down — one block of length k per index. Flat blocks make queries trivial and updates global. A balanced hierarchy of blocks of lengths 1, 2, 4, … balances the two costs at log n apiece. The whole lecture is the search for the right granularity of stored partial answers.

02 objectives & prerequisites

What you will be able to do

  • Build a Fenwick / binary-indexed tree, and explain — from the binary representation of an index — why each of its O(log n) jumps strips or adds exactly one set bit.
  • Implement point-update / prefix-query and point-update / range-query in O(log n), and say precisely why a Fenwick needs an invertible aggregate (a group) while a segment tree needs only an associative one (a monoid).
  • Construct an iterative segment tree over 2n array cells for range min / max / sum, and trace how any range decomposes into O(log n) canonical nodes.
  • Extend the segment tree with lazy propagation so that a range update (add δ to a whole block) also costs O(log n), and reason about when two pending tags compose.
  • Apply these to inversion counting and dynamic order statistics — including finding the k-th smallest live element in O(log n) by binary-lifting on the Fenwick.
  • Diagnose the classic disasters: the 1-indexing trap, the non-invertible-min mistake, the 4n sizing bug, the forgotten push-down, the tag-algebra mismatch, and silent 32-bit overflow.

One fact about the implicit binary tree you must hold firmly: a complete binary tree can live in a plain array with no pointers. Put the root at index 1; then node k's children are 2k and 2k{+}1 and its parent is ⌊k/2⌋ — a bit-shift away. The segment tree is exactly this layout carrying aggregates; the Fenwick goes further and discards even the array-of-nodes, encoding the tree in the indices themselves.

03 strip the problem to its skeleton

The unifying skeleton: monoids over canonical ranges

Before either structure, extract what both must share. The aggregate ⊕ cannot be arbitrary. To pre-combine sub-blocks and recombine partial answers in any grouping, ⊕ must be associative — (a⊕b)⊕c = a⊕(b⊕c) — and there must be an identity element e with a⊕e = a (so that an empty range has a well-defined answer). An associative operation with an identity is a monoid. That is the exact, minimal algebraic requirement; everything mechanizable here is a monoid fold.

Invertibility is the dividing line. A Fenwick reconstructs a range as prefix(r) ⊖ prefix(l) — it needs to subtract. With no inverse (min, max, gcd) that subtraction is meaningless, and the segment tree, which combines stored sub-blocks directly without ever undoing one, is the right tool.

Now the second half of the skeleton: the canonical ranges. Both structures pre-store ⊕ over a fixed family of O(n) sub-intervals, chosen so that

  • any query interval is the disjoint union of O(log n) canonical ranges (so a query is a fold of O(log n) stored values), and
  • any single index belongs to only O(log n) canonical ranges (so an update repairs only O(log n) stored values).

The two structures differ only in which family of canonical ranges they pick — and how they store it. The segment tree uses the dyadic intervals of a binary tree, held in an array of nodes. The Fenwick uses the intervals (i−\text{lowbit}(i),\,i], held in nothing but an array indexed by i, with the structure smuggled into the binary digits of i. Same idea, two encodings. Hold that and neither will ever feel like a trick.

Store neither the whole nor the parts, but a logarithmic ladder of partial answers — so that every interval is a short sum of rungs, and every rung sits on a short ladder of intervals.
04 a tree inside the bits

The Fenwick / binary-indexed tree

The Fenwick tree is the more astonishing of the two, because it is just an array tree[1…n] of the same length as your data, and the entire tree structure lives in one arithmetic expression. Index it from 1 (this is not optional — §10 shows why 0 is poison). The single primitive is the lowest set bit:

lowbit — isolate the least-significant 1 bit
lowbit(i) = i&(−i)    e.g.  lowbit(12) = lowbit(11002) = 1002 = 4

Each cell tree[i] is defined to store the aggregate of the range that ends at i and has length lowbit(i):

what tree[i] holds — its responsibility range
tree[i] = ∑ j=i−lowbit(i)+1 i a[j]   — the half-open range  (i−lowbit(i),i]

Picture those responsibility ranges drawn over the data. An odd index covers just itself (length 1); index 2 covers a[1..2]; index 4 covers a[1..4]; index 8 covers all eight. The lengths are exactly the powers of two reading off the lowest set bit — a staircase of blocks:

Prefix query: peel the set bits off

To get prefix(i) = a[1]+…+a[i], stand at i, add tree[i] (the block ending at i), then jump to the index just left of that block: i ← i − lowbit(i). Each jump clears the lowest set bit, so you take exactly \text{popcount}(i) steps — at most ⌊log₂n⌋{+}1. To get an arbitrary range, subtract two prefixes (this is the step that demands invertibility):

def lowbit(i): return i & (-i)              # least significant set bit

def prefix(i):                # sum of a[1..i],  O(log n)
    s = 0
    while i > 0:
        s += tree[i]
        i -= lowbit(i)        # strip the lowest 1-bit
    return s

def range_sum(l, r):           # sum of a[l..r], inclusive (1-indexed)
    return prefix(r) - prefix(l - 1)   # needs an inverse: a GROUP

Point update: climb the indices that cover you

Symmetrically, to do a[i] &mathbin{+}= δ you must repair every tree[k] whose responsibility range contains i. Those are reached by adding the lowest set bit: i ← i + lowbit(i), climbing until you pass n. Again O(log n) steps — the two walks are mirror images, one stripping bits, one carrying them.

def add(i, delta):            # a[i] += delta,  O(log n)
    while i <= n:
        tree[i] += delta
        i += lowbit(i)        # jump to the next index that covers i
Why is i & (-i) the lowest set bit? (two's complement, unfolded)

In two's complement, -i = (~i) + 1. Write i as <high bits> 1 00…0 with t trailing zeros below the lowest set bit. Then ~i is <flipped high> 0 11…1. Adding 1 ripples a carry up through those t ones, turning them back to zeros and flipping the 0 at the lowest-set-bit position to 1: so -i is <flipped high> 1 00…0. The high bits of i and -i are exact complements, so they AND to 0; only the lowest set bit, which is 1 in both, survives. Hence i & (-i) isolates exactly that bit. Because the value of a single set bit is a power of two, the responsibility lengths are powers of two — the whole structure is binary arithmetic made geometric.

Building the tree is then either n calls to add (O(n log n)) or, more elegantly, an O(n) in-place pass: copy a into tree, then for each i push tree[i] into its parent i + lowbit(i). Either way the storage is one array of n+1 integers — no nodes, no pointers, cache-friendly. That economy is the Fenwick's signature.

06 a tree inside an array

The segment tree

When the aggregate is not invertible — min, max, gcd — the prefix-subtraction trick dies, and we need a structure that combines stored sub-blocks directly, never undoing one. That is the segment tree: a complete binary tree whose leaves are the array and whose every internal node stores ⊕ over the contiguous range its subtree spans. The root spans everything; its two children split the range in half; and so on down to single-element leaves.

Lay it in an array t[1…2n] with the implicit layout: leaves at t[n…2n{-}1], and each internal node t[k] = t[2k] ⊕ t[2k{+}1]. A query for [l,r) walks up from the two ends, harvesting any node that sits entirely inside the range and never descending into it again. Those harvested nodes are the canonical decomposition — O(log n) of them.

The iterative form is wonderfully short. Leaves live at t[n+i]; the query climbs from both ends, absorbing a node whenever it is the right child of a left boundary or the left child of a right boundary, then halving both indices:

# 0-indexed iterative segment tree, t has size 2n, identity = 0 for sum
def build(a):
    for i in range(n): t[n + i] = a[i]
    for k in range(n - 1, 0, -1): t[k] = t[2*k] + t[2*k + 1]

def update(p, v):              # point assign a[p] = v,  O(log n)
    p += n; t[p] = v
    while p > 1:
        p >>= 1; t[p] = t[2*p] + t[2*p + 1]

def query(l, r):              # [l, r),  O(log n)
    resL, resR = 0, 0         # keep two sides for NON-commutative monoids
    l += n; r += n
    while l < r:
        if l & 1: resL = resL + t[l]; l += 1   # l is a right child → take it
        if r & 1: r -= 1; resR = t[r] + resR   # r is a left child → take it
        l >>= 1; r >>= 1
    return resL + resR

For sum, min, max the operation is commutative, so a single accumulator suffices; I keep resL and resR to make the point that for a non-commutative monoid (matrix product, string concatenation) the left-harvested pieces and right-harvested pieces must be combined in array order — collapsing them carelessly is a silent bug. Swap the three +s for min and the identity for +∞, and the same skeleton answers range-minimum.

Tracing query(2,7) on our data: with n{=}8, l{=}10, r{=}15. Step 1: r odd → take t[14]{=}8, r{=}14; halve to l{=}5,r{=}7. Step 2: l odd → take t[5]{=}16; r odd → take t[6]{=}10, r{=}6; halve to l{=}3,r{=}3 → stop. Total 8{+}16{+}10 = 34 — the same three canonical nodes the figure highlights.

07 defer the work you can

Lazy propagation: range updates in O(log n)

Point update we can do. But suppose the update itself is a range: add δ to every element of [l,r), then keep answering range sums. Touching every leaf in the range is O(\text{range}) — back to linear. The fix is the same canonical-decomposition idea applied to updates: when a range-add fully covers a node, record the obligation on that node and stop, instead of pushing it down to its leaves. The node's own aggregate is corrected immediately; the promise to its children is stored in a lazy tag and only honored (“pushed down”) if a later operation actually needs to descend through it.

For range-add / range-sum the bookkeeping is exact. A node covering len elements, told to add δ to all of them, updates sum &mathbin{+}= δ · len and remembers lazy &mathbin{+}= δ. Before ever recursing into its children, it first flushes that pending lazy to both of them. That single discipline — push down before you descend — keeps every node's stored sum correct-as-seen and the children correct-when-visited.

# recursive lazy segment tree for range-add / range-sum; arrays sized 4n
def apply(k, lo, hi, d):        # add d to every element in node k's range [lo,hi)
    sum[k]  += d * (hi - lo)
    lazy[k] += d

def push_down(k, lo, hi):
    if lazy[k] != 0:
        mid = (lo + hi) // 2
        apply(2*k,   lo,  mid, lazy[k])
        apply(2*k+1, mid, hi,  lazy[k])
        lazy[k] = 0             # obligation discharged

def range_add(k, lo, hi, l, r, d):
    if r <= lo or hi <= l: return          # disjoint
    if l <= lo and hi <= r:                  # fully covered → tag & STOP
        apply(k, lo, hi, d); return
    push_down(k, lo, hi)                       # MUST flush before descending
    mid = (lo + hi) // 2
    range_add(2*k,   lo,  mid, l, r, d)
    range_add(2*k+1, mid, hi,  l, r, d)
    sum[k] = sum[2*k] + sum[2*k+1]

def range_sum(k, lo, hi, l, r):
    if r <= lo or hi <= l: return 0
    if l <= lo and hi <= r: return sum[k]
    push_down(k, lo, hi)
    mid = (lo + hi) // 2
    return range_sum(2*k, lo, mid, l, r) + range_sum(2*k+1, mid, hi, l, r)

A small trace, on the same data: range_add([0,4), +3) lands on the single covered node [0,4) — it sets sum: 24→36, lazy:+3, and stops; no leaf is touched. Now range_sum([2,3)) must descend through [0,4), so it first pushes the +3 down: child [0,2) becomes sum 8→14, child [2,4) becomes sum 16→22 (Figure 3), then continues to the leaf and reads a[2] = 7{+}3 = 10 — correct. The update cost one node; the query cost one root-to-leaf path. Both O(log n).

tag algebraLazy propagation only works when pending tags compose: two queued range-adds combine by + (lazy &mathbin{+}= d). The moment you mix update kinds — range-assign (a[i] ← v) and range-add — you must define how an assign absorbs a pending add and vice versa, and apply them in the right order. A wrong composition law is the subtlest segment-tree bug there is; §10 returns to it.
08 what the ladder buys you

Two applications: inversions & order statistics

The point of these structures is not range sums for their own sake — it is that a Fenwick over value space becomes a live, sorted multiset you can interrogate. Two classic uses make this vivid.

A — Counting inversions in O(n log n)

An inversion is a pair i<j with a[i]>a[j] — a measure of how unsorted a sequence is. You met inversion counting through the merge-sort “count while you merge” trick in Lecture 03. Here is the Fenwick way, often simpler to reason about. Sweep j from left to right, keeping a Fenwick over ranks that counts how many already-seen elements have each rank. At step j, the elements already inserted are exactly those at indices <j; among them the ones greater than a[j] are inversions ending at j. That count is (\text{seen}) − \text{prefix}(\text{rank}(a[j])).

def count_inversions(a):              # O(n log n)
    rank = compress(a)               # map values → 1..m, order-preserving
    bit  = Fenwick(m)
    inv  = 0
    for j in range(len(a)):
        r = rank[j]
        inv += j - bit.prefix(r)    # seen-so-far minus those ≤ a[j]
        bit.add(r, 1)             # now a[j] is "seen"
    return inv

The coordinate compression step is essential: values can be up to 10⁹, but there are only n of them, so we replace each value by its position in the sorted distinct list. The Fenwick then needs only m ≤ n cells. Forgetting to compress is how a clean idea turns into an out-of-memory crash (§10).

B — Dynamic order statistics: the k-th smallest, live

Use the same Fenwick-over-ranks as an order-statistics tree. insert(x) is add(rank(x), +1); erase(x) is add(rank(x), −1); “how many live values ≤ x” is prefix(rank(x)). The elegant part is find the k-th smallest in one O(log n) descent — not log² from binary-searching the prefix. Walk the bit-lengths from high to low, greedily extending a position as long as the accumulated count stays below k. This is binary lifting on the Fenwick itself:

def find_kth(k):                  # k-th smallest live value (1-indexed), O(log n)
    pos = 0
    for step in [1 << b for b in range(LOG, -1, -1)]:   # high power of two down to 1
        nxt = pos + step
        if nxt <= m and tree[nxt] < k:       # this whole block fits below rank k
            pos = nxt
            k  -= tree[nxt]                  # consume its count
    return pos + 1                         # first rank whose prefix reaches k

Because each tree[nxt] already holds the count of a power-of-two-length block, this stitches the answer together from O(log m) blocks without a single extra prefix call. A Fenwick has quietly become a balanced search tree over a dynamic multiset — insertion, deletion, rank, and select, all in logarithmic time, in one integer array. That is the kind of structural surprise I find genuinely beautiful: the order-statistics tree was hiding inside the prefix-sum tree all along.

10 where it breaks

Failure modes & common mistakes

These structures are short, which makes their bugs silent — they return a number, just the wrong one. Here is the catalogue I have watched trip up everyone, including me.

1 · the 1-indexing trap (Fenwick)A Fenwick must be 1-indexed. At i=0, lowbit(0)=0, so the update walk i &mathbin{+}= lowbit(i) never advances — an infinite loop — and the query walk reads tree[0], which holds nothing. If your data is 0-indexed, add 1 on the way into the BIT and the off-by-one disappears. This single mistake accounts for most “my BIT returns garbage” reports.
2 · asking a Fenwick for a minimumWriting range_min(l,r) = something(prefix_min(r), prefix_min(l-1)) is meaningless: min has no inverse, so you cannot remove the left part's contribution. A Fenwick can maintain a prefix-min that only ever shrinks under updates, but not a general range-min. For range-min / max / gcd, use a segment tree. Invertibility is not a detail; it is the membership card for the Fenwick.
3 · sizing a recursive segment tree at 2n or 3nThe clean iterative tree fits in 2n. The recursive tree, indexing children as 2k, 2k{+}1 from node 1, can reach indices up to nearly 4n when n is not a power of two, because the implicit tree is padded to the next power of two and the array is addressed by node id, not by leaf count. Allocate 4n. Under-allocating gives out-of-bounds writes that corrupt neighbouring nodes — again, silently.
4 · reading a child before pushing downIn a lazy tree, any code path that descends into children must call push_down first — in both range_add and range_sum. Skip it and a child returns a sum that ignores a pending parent tag. Equally, after recursing in an update you must pull up (sum[k] = sum[2k]+sum[2k+1]), or the parent goes stale. Push down on the way in, pull up on the way out — every time.
5 · tag algebra that does not composeMixing range-assign and range-add needs a deliberate composition law: an incoming assign must overwrite any pending add (and set add to 0); an incoming add stacks onto a pending assign. Get the order or the absorption wrong and most tests still pass — the failure shows only when two updates of different kinds overlap the same node. Define the tag monoid explicitly and test overlapping mixed updates on purpose.
6 · overflow, the quiet killerA range sum of 10⁶ values each up to 10⁹ reaches 10¹⁵ — far past 32-bit range. Lazy's d · len overflows even faster. Use 64-bit accumulators (and watch the tag product too). The bug is invisible until an input crosses 2³¹.
7 · forgetting coordinate compressionInversion counting and order statistics build a Fenwick over value space. With raw values up to 10⁹ that is a billion-cell array — an instant out-of-memory. Compress to ranks 1..m first; only the relative order matters. And mind ties: decide whether equal values share a rank (for strict inversions they should) before you compress.
8 · half-open vs closed intervalsFix one convention and never drift. This page uses inclusive [l,r] for the Fenwick (so range_sum(l,r)=prefix(r)-prefix(l-1)) and half-open [l,r) for the segment tree (so a leaf is [i,i{+}1)). Mixing the two within one solution is a reliable source of off-by-one range bugs.

Build it yourself

1

Range Sum Query — Mutable

Design a structure over an integer array nums supporting two interleaved operations, each in O(log n): update(i, val) sets nums[i] = val, and sumRange(l, r) returns nums[l] + … + nums[r] inclusive.

Signature: class NumArray { NumArray(int[] nums); void update(int i, int val); long sumRange(int l, int r); }

Constraints: 1 ≤ n ≤ 3×10⁴; up to 3×10⁴ calls; −100 ≤ val ≤ 100. Example: nums=[1,3,5]; sumRange(0,2)=9; update(1,2); sumRange(0,2)=8.

Hint lens: point update + prefix query → Fenwick. Watch the assign-vs-add distinction (you must store old values to convert an assignment into a delta).

2

Count of Smaller Numbers After Self

Given an integer array nums, return an array counts where counts[i] is the number of indices j > i with nums[j] < nums[i]. Target O(n log n).

Signature: int[] countSmaller(int[] nums)

Constraints: 1 ≤ n ≤ 10⁵; −10⁴ ≤ nums[i] ≤ 10⁴. Example: nums=[5,2,6,1] → [2,1,1,0].

Hint lens: a Fenwick over compressed ranks, swept right→left, querying how many smaller values you have already seen. Cousin of inversion counting (§08).

3

Range Add & Range Sum

Support two operations on an array of length n, each in O(log n): rangeAdd(l, r, delta) adds delta to every element of [l, r], and rangeSum(l, r) returns the sum over [l, r]. Give two designs: a lazy segment tree, and a Fenwick-only solution using the difference-array / two-BIT identity.

Signature: class RangeArray { RangeArray(int n); void rangeAdd(int l, int r, long delta); long rangeSum(int l, int r); }

Constraints: 1 ≤ n, q ≤ 2×10⁵; |delta| ≤ 10⁹ (use 64-bit). Example: start all zeros, rangeAdd(1,3,2), rangeAdd(2,4,3); then rangeSum(0,4)=2{+}5{+}5{+}3{=}15.

Hint lens: for the two-BIT trick, derive ∑_{k=0}^{r} a[k] as a linear function of difference-array prefix sums; maintain one BIT for the constant part and one for the k-weighted part.

Reverse Pairs

Given an integer array nums, count the pairs (i, j) with i < j and nums[i] > 2 · nums[j]. Target O(n log n).

Signature: long reversePairs(int[] nums)

Constraints: 1 ≤ n ≤ 5×10⁴; −2³¹ ≤ nums[i] < 2³¹. Example: nums=[1,3,2,3,1] → 2;  nums=[2,4,3,5,1] → 3.

Hint lens: like inversions, but the threshold is 2·nums[j], not nums[j] — so compress the union of nums[i] and 2·nums[j] values, and be careful querying a strict > with possible overflow in 2·nums[j].

The one thing to remember

Store partial aggregates over a logarithmic skeleton of canonical sub-ranges — neither the whole nor the parts. Then every range query is a short fold of stored rungs, and every update repairs a short ladder of rungs. The Fenwick hides that skeleton in the bits of an index and demands an invertible aggregate (a group); the segment tree hides it in an array of nodes and asks only for an associative one (a monoid); lazy propagation extends the segment tree to range updates by deferring work onto tags and pushing them down only along visited paths. Two operations, both O(log n), from one idea about granularity.

What changed between Lectures 1–9 and this one: until now a structure committed to being good at one thing. The implicit tree is the first structure on this syllabus that refuses the trade by storing answers at every scale at once. Next we let go of the line entirely — elements stop being a sequence and become a graph, where “range” gives way to “reachable,” and the traversal order itself exposes the structure.
