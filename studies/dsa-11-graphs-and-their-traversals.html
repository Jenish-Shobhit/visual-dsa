A graph is just dots and the connections between them — and almost nothing in computing is not one. Roads, web pages, prerequisites, friendships, the call graph of your program, the dependency tree of your build: all graphs. This lecture builds the two ways to walk a graph — breadth-first and depth-first — and then shows the quiet miracle: each walk leaves behind a tree whose shape exposes structure you never explicitly searched for — shortest distances, a legal ordering, hidden cycles, tightly-bound clusters, and the single points whose failure would split the whole apart.

A number to set the stakes. Take a graph with a million vertices and ten million edges — a small social network, a medium codebase. Stored as an adjacency list it occupies about ten million links, and a single full traversal touches each once: roughly 11 million steps, a few milliseconds. Store the same graph as an adjacency matrix and you need a million-by-a-million grid — 1012 cells, a terabyte — of which 99.999% are zero.

Same graph. A 100,000× gap in space, opened by nothing but the representation. And once the representation is right, the astonishing part is that breadth-first and depth-first search each run in O(V+E) — time linear in the graph — yet between them they answer distance, ordering, cyclicity, connectivity, and cut-points. Two linear walks; the entire skeleton of the structure, laid bare.

01 the relation, made first-class

Why graphs are the structure under everything

Every structure so far in this course has been about a single kind of relationship. An array imposes position; a tree imposes hierarchy; a heap imposes partial order. A graph drops the special case and keeps only the essence: a set of things, and an arbitrary set of pairings among them. That is the most general relational structure there is — which is exactly why so many problems turn out to be graph problems once you strip the domain away.

I find it clarifying to do that stripping deliberately. A road map: intersections are vertices, roads are edges. A compiler's symbol resolution: definitions are vertices, “uses” are edges. A spreadsheet: cells are vertices, formula references are edges — and the dreaded circular reference error is a directed cycle the engine detected with the very algorithm in §08. A build system with fifty thousand targets wired by “A must compile before B” is a directed graph, and two questions decide whether it can build at all: is there a legal order, and if not, where is the cycle?

The same walk, pointed at a network of machines, answers a different question entirely: which single node, if it failed, would split the network into disconnected pieces? That node is an articulation point, and finding every one of them costs no more than a single depth-first walk. This is the through-line of the lecture: you will learn only two traversals, and each, almost as a side effect, exposes a different hidden property of the structure.

the formal lensA graph is a relation made into an object you can compute over. The art is the reduction: phrase your messy problem as “vertices, edges, and a question about reachability or order,” and a linear-time answer is usually already waiting in this lecture.
02 objectives & prerequisites

What you will be able to do

  • Choose between an adjacency matrix and an adjacency list from the graph's density, and state the space and per-operation cost of each.
  • Run breadth-first search by hand, and prove that the order of first discovery gives the exact unweighted shortest-path distance from the source.
  • Run depth-first search, assign discovery / finish times, classify every edge as tree / back / forward / cross, and use the back edge as a cycle detector.
  • Produce a topological order of a DAG two ways — DFS finish-time and Kahn's in-degree peeling — and detect when no order exists because a cycle does.
  • Compute the strongly connected components of a directed graph with Kosaraju's two passes and Tarjan's single low-link pass, and explain the condensation DAG they reveal.
  • Find all bridges and articulation points of an undirected graph from one DFS using the disc / low recurrence, with the bridge test low[c] > disc[u].

Prerequisites

Four ideas, each a short phrase. The traversals are nothing but a visited-set plus one of two containers you already know.

If you can enqueue and dequeue, push and pop, and trust a recursive call to remember where it left off, you already hold the machinery. A graph traversal is the moment those three primitives stop being toys and start exposing the shape of real data.

03 fix the vocabulary before the algorithm

The formal object: vertices, edges, and the questions they raise

A graph is a pair G = (V, E): a finite set V of vertices (nodes) and a set E of edges, each edge a pair of vertices. We write n = |V| and m = |E|; nearly every cost in this lecture is stated in those two numbers. The first fork is direction:

  • In an undirected graph an edge {u,v} is symmetric — a two-way street, a mutual friendship.
  • In a directed graph (a digraph) an edge (u→v) is one-way — a hyperlink, a prerequisite, a function call.

This lecture treats unweighted graphs: an edge either exists or it does not, all equally “one step.” Weights — distances, costs — arrive in Lecture 13, and they change the right algorithm completely; mistaking one setting for the other is the headline failure mode of §12.

A few more terms, defined once and used throughout. The degree of a vertex is its number of incident edges; in a digraph it splits into in-degree and out-degree. A path is a sequence of vertices joined by edges; a cycle is a path that returns to its start. An undirected graph is connected if a path joins every pair; its maximal connected pieces are its components. A directed graph is strongly connected if you can travel from any vertex to any other following the arrows — the subtlety that makes §09 its own topic.

One identity will pay for the linear-time bound later, so meet it now. Summing every vertex's degree counts each undirected edge from both of its ends, so:

the handshaking lemma — why “sum of degrees” is just 2m
∑v∈V deg(v) =2m,  so iterating every adjacency list end-to-end is  Θ(n+m).

Finally, density. A simple graph on n vertices has at most ≈ n²/2 edges. When m is close to that ceiling the graph is dense; when m is closer to n — the common case for real-world graphs — it is sparse. That single distinction decides the representation, which is where we go next.

An array remembers position, a tree remembers hierarchy. A graph remembers only the relation — and so it can model anything that relates.
04 the representation decides the cost

Two ways to store a graph

The abstract object “V and E” must become bytes before we can walk it, and there are two canonical layouts. They answer the two primitive questions — “is there an edge u→v?” and “list the neighbours of u” — at opposite costs.

The adjacency matrix is an n×n grid A with A[u][v]=1 exactly when the edge exists. Edge existence is a single O(1) array read — its one great strength — but the grid costs Θ(n²) space whether the graph is full or nearly empty, and listing one vertex's neighbours means scanning a whole row of n cells, most of them zero.

The adjacency list keeps, for each vertex u, a list of just its actual neighbours. Total space is Θ(n+m) — you pay only for edges that exist — and enumerating u's neighbours costs Θ(deg u), optimal. The price is that testing one specific edge u→v means scanning u's list, O(deg u). For the overwhelming majority of real graphs — which are sparse — the list wins decisively, and it is the representation every traversal below assumes.

05 one skeleton, two disciplines

The universal walk — and the container that names it

Both traversals are the same algorithm with one part swapped. The skeleton: keep a set of discovered vertices so you never revisit, and a frontier container of vertices seen but not yet expanded. Repeatedly take a vertex from the frontier, and for each undiscovered neighbour, mark it discovered and add it to the frontier. The walk ends when the frontier empties.

Everything hinges on which vertex you take next, and that is set entirely by the container:

  • A queue (FIFO) takes the oldest frontier vertex first — the walk spreads outward in rings of equal distance. This is breadth-first search.
  • A stack (LIFO), or equivalently the call stack of recursion, takes the newest first — the walk plunges as deep as it can before backing up. This is depth-first search.

Swap the queue for a stack and breadth becomes depth. That is the whole difference, and yet the two leave behind utterly different traversal trees — the tree of edges along which discovery actually happened — and those trees expose different truths. Before the details, the cost, paid once for both:

why every traversal here is linear
T(BFS)= T(DFS)= Θ(n+m) =Θ(V+E)

The accounting is exact: each vertex is discovered and expanded once (the visited set guarantees it), contributing Θ(n); and expanding a vertex scans its adjacency list, so across the whole run we scan every list end-to-end — by the handshaking lemma that is Θ(m) work (or 2m for undirected). Sum: Θ(n+m). No vertex, no edge, is ever touched a third time. This linearity is the reason graphs are tractable at all, and it is why the §04 choice of an adjacency list matters so much: on a matrix the “scan the neighbours” step alone balloons to Θ(n²).

A note on bookkeeping you will see in every implementation below: a three-state colour. White = undiscovered, grey = discovered but not finished (on the frontier / on the recursion stack), black = finished (all neighbours explored). For BFS the grey/black split barely matters; for DFS it is the heart of cycle detection — a grey vertex is an ancestor you are still inside, so an edge back to it closes a loop.

06 the queue measures distance

Breadth-first search: rings of equal distance

BFS explores in layers. Layer 0 is the source s alone. Layer 1 is every vertex reachable in one edge. Layer 2 is everything new reachable from layer 1, and so on — an expanding wavefront. The queue enforces this: because we append newly discovered vertices to the back and remove from the front, the whole of layer i is processed before any of layer i+1. Here is the algorithm, with the one line people get wrong called out.

BFS(G, s):
  for each vertex u: state[u] ← WHITE; dist[u] ← ∞; parent[u] ← nil
  state[s] ← GREY; dist[s] ← 0
  Q ← empty queue; enqueue(Q, s)
  while Q not empty:
    u ← dequeue(Q)                  // u leaves in non-decreasing dist order
    for each v in adj[u]:
      if state[v] = WHITE:
        state[v] ← GREY              // MARK ON DISCOVERY — not on dequeue (see §12.1)
        dist[v] ← dist[u] + 1
        parent[v] ← u
        enqueue(Q, v)
    state[u] ← BLACK

The payoff is a theorem, not a heuristic. The parent pointers form the BFS tree, and the value dist[v] is exactly the fewest edges on any path from s to v — the unweighted shortest-path distance. BFS solves shortest paths for free, as long as every edge counts the same.

Prove it: dist[v] from BFS equals the true shortest-path distance δ(s,v)

Let δ(s,v) be the true minimum edge-count. Two halves. (Upper bound, dist ≤ δ is automatic: any discovery path the tree records is a path, so dist[v] ≥ δ(s,v) can't be beaten downward without a real path.) The substance is the key invariant: BFS dequeues vertices in non-decreasing order of dist, and the queue ever holds only two adjacent layer-values i and i+1. Prove by induction on dequeue order. It holds initially (just s, dist=0). When we dequeue u with dist[u]=i, every white neighbour v gets dist[v]=i+1 and is enqueued behind the existing tail, preserving monotonicity. Now suppose for contradiction some v got dist[v] > δ(s,v). Take the true shortest path s … w → v with δ(s,w)=δ(s,v)-1. By induction w was assigned dist[w]=δ(s,w) and was dequeued; at that moment v was either still white (so it received dist[w]+1=δ(s,v), contradiction) or already discovered with a value ≤ dist[w]+1 by monotonicity (also a contradiction). Hence dist[v]=δ(s,v) for all v. □

07 the stack measures structure

Depth-first search: dive, backtrack, and timestamp

DFS commits to a direction and follows it to exhaustion before backing up. Written recursively it needs no explicit container — the call stack is the frontier. What turns DFS from a mere visiting order into an analytical instrument is a single global clock that stamps each vertex twice: a discovery time d[u] when we first enter it, and a finish time f[u] when we leave it for good, every descendant done.

DFS(G):                          // handles disconnected graphs → a forest
  clock ← 1; for each u: color[u] ← WHITE
  for each vertex u:
    if color[u] = WHITE: VISIT(u)

VISIT(u):
  color[u] ← GREY; d[u] ← clock; clock ← clock + 1
  for each v in adj[u]:
    if   color[v] = WHITE: parent[v] ← u; VISIT(v)   // TREE edge
    elif color[v] = GREY:  record BACK edge (u→v)        // v is a live ancestor → a CYCLE
    else:                  record FORWARD or CROSS (u→v)  // v already finished (black)
  color[u] ← BLACK; f[u] ← clock; clock ← clock + 1

Those timestamps obey the parenthesis theorem: if you print (u at discovery and u) at finish, the result is a balanced parenthesis string. For any two vertices the intervals [d[u],f[u]] and [d[v],f[v]] are therefore either disjoint or nested — never crossing. Nesting is meaningful: [d[v],f[v]] sits inside [d[u],f[u]] iff v is a descendant of u in the DFS tree. The clock literally records the tree's ancestor structure.

And every edge falls into exactly one of four classes, read off the colour of its target at the moment it is explored:

  • Tree edge — target was white; discovery happened along it. These form the DFS forest.
  • Back edge — target was grey (a live ancestor). A back edge exists iff the graph has a cycle. This is the single most useful fact about DFS.
  • Forward edge — target was black and is a descendant (a shortcut down the tree).
  • Cross edge — target was black and is neither ancestor nor descendant (it points “sideways” to an already-finished subtree).

In an undirected graph the menu shrinks to two — only tree and back edges occur — which is exactly what makes the bridge test of §10 so clean.

Read the figure's times against the four classes to cement the rule. For a back edge like 5→3, the target encloses the source: d[3]=5 < d[5]=7 < f[5]=12 < f[3]=14 — 5 is inside 3, and the arrow points up to a living ancestor. For the forward edge 4→6: d[4]=6 < d[6]=9 < f[6]=10 < f[4]=13 — nested again, but pointing down to a finished descendant. The timestamps don't just describe the walk; they are the classifier.

08 ordering what must come first

Topological order — and the cycle that forbids it

A directed acyclic graph (DAG) is a digraph with no cycles — precisely the graphs whose DFS finds no back edge. On a DAG a beautiful thing is possible: a topological order, a linear arrangement of the vertices such that every edge u→v points forward (u before v). It is exactly “a valid order to do the tasks” when edges mean “must come before.” If — and only if — the graph has a cycle, no such order exists: the cycle is a set of tasks each waiting on the next.

Two algorithms produce it, and each doubles as a cycle detector.

Method A — DFS by finish time

Run DFS; as each vertex finishes, push it onto the front of a list. The result is a topological order. Why: for any edge u→v on a DAG, f[u] > f[v] always (the only way f[u]<f[v] would require v to be a grey ancestor — a back edge — which a DAG forbids). So ordering by decreasing finish time puts every edge's tail before its head. One DFS, O(V+E); a back edge encountered along the way is the proof that no order exists.

Method B — Kahn's algorithm (in-degree peeling)

Repeatedly emit a vertex with no remaining prerequisites — in-degree 0 — and delete it, decrementing its neighbours' in-degrees. A queue makes it linear. If you emit all n vertices, that sequence is a topological order; if the queue empties early with vertices left over, those survivors all lie on or after a cycle — Kahn's leftover count is a cycle detector.

KAHN(G):
  for each v: indeg[v] ← number of edges into v
  Q ← all v with indeg[v] = 0;   order ← [ ]
  while Q not empty:
    u ← dequeue(Q); append u to order
    for each v in adj[u]:
      indeg[v] ← indeg[v] - 1
      if indeg[v] = 0: enqueue(Q, v)
  if length(order) < n: report "CYCLE — no topological order"
  else: return order

09 mutual reachability

Strongly connected components

In a digraph, two vertices are strongly connected if each can reach the other following arrows. This is an equivalence relation, so it partitions V into strongly connected components (SCCs) — maximal blobs of mutual reachability. Contract each SCC to a single super-vertex and you get the condensation, which is always a DAG: if two SCCs reached each other they would be one SCC. So every digraph is, at the coarse scale, a DAG of tightly-tangled clusters — a fact that underlies deadlock detection, dataflow analysis, and the “2-SAT” trick. Two linear-time algorithms find them.

Kosaraju — two passes and a transpose

The cleaner one to understand:

  1. Run DFS on G, pushing vertices on a stack as they finish (decreasing finish time).
  2. Build Gᵀ, the transpose — every edge reversed.
  3. Pop vertices off the stack; from each unvisited one, run DFS on Gᵀ. Each tree this grows is exactly one SCC.

Why it works in one line: reversing edges leaves SCCs unchanged (mutual reachability is symmetric), but the finish-time order ensures you start each second-pass DFS in a “sink” SCC of the condensation, so it cannot leak into another component. Two DFS passes ⇒ O(V+E).

Tarjan — one pass, one stack, the low-link

Tarjan finds the same components in a single DFS by tracking, for each vertex, the oldest vertex its subtree can reach via at most one non-tree hop to a vertex still “in progress.” Maintain disc[u] (discovery index) and

tarjan's low-link recurrence
low[u]=min { disc[u], mintree child clow[c], minedge u→w, w on stackdisc[w] }

Push every vertex on an explicit stack as it is discovered. When a vertex u finishes with low[u]=disc[u], it is the root of an SCC: pop the stack down to and including u — those are its members. The critical subtlety (and §12's classic bug): the third term uses disc[w], not low[w], and only for w still on the stack.

TARJAN(G):
  idx ← 0; S ← empty stack; for each u: disc[u] ← UNSET
  for each u: if disc[u] = UNSET: SC(u)

SC(u):
  disc[u] ← low[u] ← idx; idx ← idx + 1
  push(S, u); onStack[u] ← true
  for each v in adj[u]:
    if   disc[v] = UNSET: SC(v); low[u] ← min(low[u], low[v])    // tree edge
    elif onStack[v]:     low[u] ← min(low[u], disc[v])         // live cross/back — disc, not low!
  if low[u] = disc[u]:                                       // u roots an SCC
    start new component; repeat w ← pop(S); onStack[w] ← false; add w until w = u

10 the points of failure

Bridges & articulation points

Now an undirected question with real operational teeth. A bridge is an edge whose removal disconnects the graph (splits one component into two); an articulation point (cut vertex) is a vertex whose removal does. These are the single points of failure in a network: the one cable, the one router whose loss partitions everything. Naively you could delete each edge or vertex and re-run connectivity — O(V·E). DFS finds them all in one pass.

The instrument is the same low-link idea, specialised to undirected DFS (where only tree and back edges exist). For each vertex, disc[u] is its discovery time and

undirected low — and the bridge / articulation tests
low[u]=min { disc[u], minback edge (u,w)disc[w], mintree child clow[c] }

Read low[u] as “the highest (oldest) vertex u's subtree can climb back to.” Then, for a tree edge (u,c) with c the child:

  • Bridge: (u,c) is a bridge iff low[c] > disc[u] — c's whole subtree has no back edge reaching u or above, so that one edge is its only lifeline.
  • Articulation point (non-root): u is a cut vertex iff some child c has low[c] ≥ disc[u] — the subtree can't bypass u to reach an ancestor.
  • Articulation point (root): the DFS-tree root is a cut vertex iff it has two or more tree children — it is the only thing joining them.

The single dangerous detail (§12.4): when scanning u's neighbours, skip the edge back to u's parent once — but any other edge to an already-seen vertex is a genuine back edge that must update low via disc.

12 where it breaks

Failure modes & common mistakes

The gap between the recurrence and the running loop is where mistakes appear. Here is where graph code goes wrong — the off-by-one of state, the seductive-but-wrong reach for the wrong tool, the detail that silently corrupts an answer that still looks plausible.

1 · Marking visited at dequeue instead of at discovery (BFS)

If you only mark a vertex visited when you pop it, the same vertex can be enqueued many times before it is ever processed — the queue bloats, distances get overwritten, and on a dense graph it degrades toward quadratic. Mark state[v]=GREY the instant you enqueue it, exactly where the §06 code flags it. One misplaced line is the difference between correct linear BFS and a slow, wrong one.

2 · Using BFS distances on a weighted graph

The most seductive error. BFS counts edges; it returns true shortest paths only when every edge has equal weight. The moment edges carry distinct costs, a path with more edges can be cheaper, and BFS confidently returns a wrong answer. Weighted shortest paths need Dijkstra or Bellman-Ford (Lecture 13). (The honourable exception: 0/1 weights yield to a deque-BFS, and small integer weights to edge-splitting — but plain BFS is not it.)

3 · Recursive DFS blowing the call stack

A graph with a path of length V makes recursive DFS recurse V frames deep; at a few hundred thousand vertices that overflows the native stack and crashes — on exactly the large inputs you care about. Either convert to an explicit-stack iterative DFS, or raise the recursion limit deliberately. Tarjan in particular is usually written iteratively in production for this reason.

4 · The parent-edge trap in undirected low-link

In undirected DFS you must ignore the edge back to your parent — but ignore it exactly once. Skipping every edge to the parent silently swallows a genuine second (parallel) edge to that same vertex, which is a real back edge and would correctly stop something from being a bridge. Track the parent edge id, not just the parent vertex, when multi-edges are possible. And update low from a back edge with disc[w], never low[w].

5 · Forgetting the graph is disconnected (and the forest)

A single BFS(s) or VISIT(s) only reaches s's component. Counting components, topological-sorting, or finding SCCs requires the outer loop that restarts the traversal from every still-white vertex, producing a forest. Omit it and you silently process only one component and report a confidently partial answer.

6 · Directed vs. undirected: building the wrong adjacency list

For an undirected edge {u,v} you must push v into adj[u] and u into adj[v]; for a directed edge only the first. Add both directions to a directed problem and you fabricate reachability, merge SCCs, and destroy any topological order; add only one to an undirected problem and you sever half the graph. Decide the model first, build the list to match.

7 · Tarjan's low update: disc[w], and only if on the stack

Two bugs in one line. Updating low[u] with low[w] instead of disc[w] on a non-tree edge can wrongly merge distinct SCCs; and updating from a vertex w that has already been popped (no longer on the stack, i.e. its component is closed) is also wrong — that edge crosses into a finished component and must be ignored. The guard is precisely elif onStack[v]: low[u] = min(low[u], disc[v]).

14 recap & next

The one thing to remember

A graph traversal is one algorithm — visited-set plus a frontier — and the container you pick decides everything it reveals. A queue gives breadth-first search, and its layers are unweighted distance. A stack gives depth-first search, and its discovery/finish clock exposes cycles (the back edge), a topological order (decreasing finish time), strongly connected components (Tarjan's low=disc roots), and an undirected graph's bridges and articulation points (low[c]>disc[u]). All of it in O(V+E) — provided you stored the graph as an adjacency list. Learn the two walks; collect the five structures for free.
