Tries and Suffix Structures

Try this first · What is the time to look up a word of length m in a trie, ignoring alphabet map cost?

O(m), because the lookup follows at most one edge per character.

Last lecture we searched a text once. KMP scans an n-character string for a pattern in O(n+m) and throws the work away. But real systems ask the same text a thousand questions: every read aligned against a genome, every query typed into a search box, every grep over a fixed corpus. Re-scanning is a confession that we never understood the text — we only walked it.

The number that forces the idea

The human reference genome is ≈ 3.1 × 109 characters. Align one 30-base read by re-scanning and you pay 3 billion comparisons. A sequencing run produces hundreds of millions of reads. Re-scanning is ≈ 1018 operations — years of compute. Build an index over the genome once, and each read costs ≈ 30 steps. Same data, same question, eighteen orders of magnitude apart. The difference is entirely the data structure.

This lecture is about preprocessing the text instead of the pattern — turning a string into a structure that answers any substring query fast. We build three indices, each a refinement of the last: the trie (an index over a set of strings), the suffix tree (a trie over all suffixes, compressed), and the suffix array (the same information, sorted into a flat array) together with its LCP companion.

Section 04 · First principles

Extract the computational skeleton

Strip the domain away — genomes, search boxes, log files — and the formal object is the same. We are given a fixed text T of length n over an alphabet Σ. We will face a stream of queries, each a pattern P of length m, and for each we must answer "does P occur in T, where, and how often?" The decision we control is where to spend the work: at query time (KMP — cheap to set up, O(n) per query) or at build time (an index — expensive once, then O(m) per query). When queries are many and T is fixed, the index wins decisively.

To build an index we need one structural observation, and the entire lecture turns on it. A substring is any contiguous slice T[i..j]. A suffix is a slice that runs to the end, T[i..n−1]. Now look at the substring T[i..j]: it begins at position i — and so does the suffix T[i..n−1]. The substring is exactly the first (j−i+1) characters of that suffix. That is to say:

Every substring of a text is the prefix of one of its suffixes. — the lemma that turns "search a text" into "organise its suffixes"

The consequence is mechanical and total. "Is P a substring of T?" is precisely "Is P a prefix of some suffix of T?". So if we hold the set of all n suffixes in a structure that answers prefix queries quickly, we have answered every substring query for free. The work splits cleanly: a part that can be fully mechanised — collect the suffixes, organise them, search the organisation — and a part that needs judgement — which organisation, given memory, alphabet size, and how many queries you will ask. We build the mechanical part precisely; we name the judgement explicitly.

So we first need a structure for prefix queries over a set of strings. That structure is the trie. Then we feed it the one special set — the suffixes of T — and refine it twice for size.

Section 05 · The prefix tree

The trie: an index keyed by spelling

A trie (from retrieval; say it "try" to disambiguate from "tree") is a rooted tree in which edges carry characters and paths spell strings. The root is the empty string. From any node, at most one child edge leaves per alphabet symbol, so the child for character c is unique. The string a node represents is the concatenation of edge labels from the root down to it. A node flagged terminal means "the string spelled to here is a member of the set."

The structural payoff is that shared prefixes are shared paths. The words car, card, care do not store the letters c‑a‑r three times; they walk the same three edges and then diverge. Lookups never branch on the dataset size — to find a key of length L you follow exactly L edges and check a flag. The cost of a query depends on the query, never on how many keys you stored.

Worked example — build the trie of {cat, car, card, care, dog}

Insert in order. Each insertion walks from the root, creating an edge only when the needed child is missing, and flags the final node terminal. Trace it: cat lays the path c→a→t; car reuses c→a, adds r; card reuses c→a→r, adds d; care reuses c→a→r, adds e; dog starts a fresh branch d→o→g. The node for car is terminal and has children — both facts coexist.

The mechanism, in code

A node is just a map from character to child plus a terminal flag. Every operation is one walk.

trie.py — insert / search / startsWith
class TrieNode:
    def __init__(self):
        self.kids = {}          # char -> TrieNode
        self.end  = False     # is a key spelled exactly here?

class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word):
        node = self.root
        for ch in word:               # O(L) — one edge per char
            if ch not in node.kids:
                node.kids[ch] = TrieNode()
            node = node.kids[ch]
        node.end = True

    def _walk(self, s):              # follow s, return node or None
        node = self.root
        for ch in s:
            node = node.kids.get(ch)
            if node is None: return None
        return node

    def search(self, word):           # exact membership
        node = self._walk(word)
        return node is not None and node.end

    def startsWith(self, prefix):     # any key with this prefix?
        return self._walk(prefix) is not None

The one design judgement: how to store kids

A hash map (above) costs O(1) expected per step and only as much memory as there are real children — ideal for sparse, large alphabets (Unicode). A fixed array of σ pointers per node is faster and cache-friendlier but spends σ slots per node whether used or not — for σ=256 bytes that is mostly empty space. A ternary search tree sits between them. This is the part that does not mechanise away: the structure is fixed, the representation is an engineering call about σ, density, and the cache.

Tries already earn their keep — autocomplete (descend to the prefix node, enumerate the subtree), spell-checkers, and IP routing tables (longest-prefix match) are all tries. But our goal is substring search on one text, and §04 told us how: feed the trie the suffixes.

Section 06 · Compressing the suffix trie

From a trie of suffixes to a suffix tree

Take the lemma at its word. Insert all suffixes of T into a trie. Now a prefix query on this suffix trie answers any substring query: to test P, walk it from the root; if the walk survives, P is a prefix of some suffix, i.e. a substring. Searching costs O(m) — exactly the index we wanted.

One hygiene step first. Append a unique sentinel $ — a symbol not in Σ, defined to be lexicographically smaller than every real character. Without it, a suffix can be a prefix of another (na sits inside nana) and would end in the middle of a path rather than at its own node. With $, no suffix is a prefix of another, so the suffixes stand in bijection with the leaves — exactly one leaf per starting position.

The suffix trie is correct but fat. The suffixes of an n-character string have total length n + (n−1) + ⋯ + 1 = n(n+1)/2 = Θ(n²), so the trie has Θ(n²) nodes. For a 1 MB file that is 1012 nodes — unusable. The fix is pure structural economy:

Path compression — the suffix tree

Any chain of nodes with a single child carries no branching information. Collapse every non-branching chain into one edge, and label that edge not by copied characters but by an interval (start, len) into T. Now branching happens only where suffixes genuinely diverge. A tree with n leaves and only branching internal nodes has at most n−1 internal nodes — so the whole structure is O(n) nodes and O(n) space, regardless of how long the individual suffixes are. That is the suffix tree.

Worked example — the suffix tree of banana$

The seven suffixes are banana$(0), anana$(1), nana$(2), ana$(3), na$(4), a$(5), $(6). Group by first character, then recurse on where they split. Suffixes starting a share just a, then split into those continuing na… and the bare $; the na… pair splits again at the next na$ vs $. The result has 7 leaves (one per suffix) and 3 internal branch nodes — drawn below.

What the shape gives you, read directly off the tree

Occurs? spell P from the root — O(m).  How many times? count the leaves under where P ends (precompute subtree leaf-counts once).  Longest repeated substring? the deepest internal node by string-depth.  Longest common substring of two texts? build a generalised suffix tree of A#B$ and find the deepest node with leaves from both. The tree is a Swiss-army index.

Dig deeper — can we build it fast?

Built naively the suffix tree costs O(n²). There are celebrated linear-time constructions — Weiner (1973), McCreight (1976), and Ukkonen (1995), an elegant online O(n) algorithm using suffix links and "active point" bookkeeping. They are correct and beautiful, but intricate to implement and heavy in pointers (often 20–40 bytes per character in practice). For most engineering, the next structure — the suffix array — delivers the same queries with a fraction of the memory and code, which is why it is what ships.

Section 07 · The index, flattened by sorting

Suffix arrays: the same information, sorted

Look again at Figure 2 and read the leaves left to right under a lexicographic ordering of the children. You get the suffixes in sorted order. That observation is the whole trick: we do not need the tree's pointers to search — we need the suffixes sorted. So store only that.

The suffix array SA of T is the array of starting indices of all suffixes, listed in lexicographic order of the suffixes they name. It is a permutation of 0…n−1 — one integer per position, O(n) space, four bytes a character instead of the tree's dozens. For T = banana the suffixes sort as:

Searching: a binary search on sorted text

Because the suffixes are sorted, all suffixes that share a given prefix P form a contiguous block. So P occurs in T iff some suffix has P as a prefix, and we find that block by two binary searches — the lower bound and the upper bound of P. The number of occurrences is hi − lo; the positions are SA[lo…hi−1].

Trace P = "ana" against SA = [5,3,1,0,4,2]. Binary search compares P to the suffix at the midpoint. a(rank 0) < ana; ana(rank 1) matches as a prefix; anana(rank 2) also has ana as a prefix; banana(rank 3) > ana. So the block is ranks [1, 3) → lo=1, hi=3, count = 2, at text positions SA[1]=3 and SA[2]=1. Figure 3 shows the block.

Each comparison in the binary search may scan up to m characters, and there are ⌈log₂ n⌉ of them, so a plain suffix-array search is O(m log n) — not the tree's O(m), but with a tiny constant and superb cache behaviour. (LCP-aware refinements reach O(m + log n); we will not need them today.)

Building it: sort the suffixes — but cleverly

The definition says "sort the suffixes," and the naïve reading is fatal. Hand n suffixes to a comparison sort and each comparison can scan O(n) characters, giving O(n² log n) — fine at n=10³, hopeless at n=10⁶. We need the comparisons to be O(1). The trick is prefix doubling (Manber–Myers): sort suffixes by their first character, reuse those ranks to sort by the first two, then four, eight… doubling the sorted prefix length each round. After ⌈log₂ n⌉ rounds the suffixes are fully sorted.

The engine is that once every suffix has a rank for its first k characters, the order on the first 2k characters of suffix i is decided by the pair (rankk[i], rankk[i+k]) — the rank of its first half and the rank of its second half (which is just the suffix starting k later). Comparing two integers is O(1). Sort by the pairs, re-rank, repeat.

Three rounds because 2³ = 8 ≥ 6. Each round sorts n pairs: with a comparison sort that is O(n log n) per round and O(n log² n) overall; swap in a two-pass radix sort on the pair (it is two small integers) and each round is O(n), giving the clean O(n log n). Here is the doubling in code, with a comparison sort for clarity:

suffix_array.py — prefix doubling, O(n log² n)
def suffix_array(s):
    n = len(s)
    sa   = list(range(n))                 # the suffixes, to be ordered
    rank = [ord(c) for c in s]            # round 0: rank by 1 char
    tmp  = [0] * n
    k = 1
    while k < n:
        # key of suffix i over its first 2k chars = (rank[i], rank[i+k] or -1)
        def key(i):
            return (rank[i], rank[i + k] if i + k < n else -1)
        sa.sort(key=key)                       # O(n log n); radix → O(n)
        tmp[sa[0]] = 0
        for i in range(1, n):              # re-rank; equal keys share a rank
            tmp[sa[i]] = tmp[sa[i-1]] + (1 if key(sa[i]) > key(sa[i-1]) else 0)
        rank = tmp[:]
        if rank[sa[-1]] == n - 1:            # all ranks distinct → sorted
            break
        k *= 2
    return sa

Production code uses radix sort and the linear-time SA-IS or DC3 / skew algorithms for true O(n) construction; prefix doubling is the version you can derive from scratch and debug by hand — which is why we learn it first.

Section 08 · The companion array

LCP: the glue that restores the tree's power

A bare suffix array can search, but it has forgotten the internal nodes of the suffix tree — the shared structure that answers "what repeats?" The LCP array restores it. Define LCP[i] as the length of the longest common prefix of the two adjacent suffixes in sorted order, T[SA[i−1]…] and T[SA[i]…], with LCP[0] = 0. It measures how much consecutive sorted suffixes agree before they split — which is exactly the string-depth of the branching node between them in Figure 2.

For banana (Figure 3, right column): a→ana share a (1); ana→anana share ana (3); anana→banana share nothing (0); banana→na nothing (0); na→nana share na (2). So LCP = [–, 1, 3, 0, 0, 2]. Two payoffs fall straight out:

① Longest repeated substring = max LCP

A substring repeats iff it is a shared prefix of two different suffixes — and the longest such shared prefix between any two suffixes is maximised between adjacent ones in sorted order. So the longest repeated substring has length max(LCP); here max = 3 at i=2, giving T[SA[2]…SA[2]+3] = ana. Same answer as the deepest internal node of the tree — recovered from two flat arrays.

② Counting distinct substrings

Each suffix SA[i] contributes n − SA[i] prefixes — i.e. all substrings that start at that position. Walking the suffixes in sorted order, the first LCP[i] of those prefixes were already contributed by the previous suffix (they are the shared part), so they are duplicates. Subtract them once:

D= ∑i=0n−1 (n−SA[i]) − ∑i=1n−1 LCP[i] = n(n+1)2 − ∑i=1n−1 LCP[i]

For banana: total prefixes = 6·7/2 = 21, shared = 1+3+0+0+2 = 6, distinct = 15. Enumerating by hand confirms 15 distinct substrings. The whole count, in O(n) after the arrays exist.

Computing LCP in linear time — Kasai's algorithm

Naïvely each LCP[i] costs O(n) to recompute — O(n²) total. Kasai's insight: process suffixes in text order, not array order, and reuse work. If suffix i shares h characters with its sorted neighbour, then suffix i+1 (one character shorter at the front) shares at least h−1 — so h drops by at most 1 between consecutive starting positions. The pointer never rewinds far; the total work is O(n).

kasai.py — LCP array in O(n)
def kasai(s, sa):
    n = len(s)
    rank = [0] * n
    for i in range(n):
        rank[sa[i]] = i                # inverse of SA: position → its rank
    lcp = [0] * n
    h = 0
    for i in range(n):                # i walks text order, NOT sorted order
        if rank[i] > 0:
            j = sa[rank[i] - 1]        # the suffix just above i in sorted order
            while i + h < n and j + h < n and s[i+h] == s[j+h]:
                h += 1
            lcp[rank[i]] = h
            if h > 0:
                h -= 1                 # reuse: drop at most 1 for the next start
        else:
            h = 0
    return lcp                         # lcp[rank[i]] convention; lcp[0] = 0

The rank array — the inverse of SA — is the quiet workhorse here and a frequent source of bugs: SA maps rank→position, rank maps position→rank, and Kasai needs the second. Build it once; never conflate the two.

Section 09 · The trade space

Four indices, side by side

All four answer "is P a substring of T?" — they differ in what they cost to build, what they weigh, and what extra questions they answer cheaply. Reading this table is the engineering judgement §04 set aside.

Substring-index structures · n = |text|, m = |pattern|, σ = alphabet, occ = #matches
structure build time space query also gives you
Trie of a key set O(Σ|keys|) O(Σ|keys|·σ) O(L) prefix/autocomplete over a set (not one text)
Suffix trie O(n²) O(n²) O(m) everything below — but quadratic; never build it big
Suffix tree O(n) (Ukkonen) O(n) ·20–40 B/char O(m) repeats, LCS, occurrence counts — richest, heaviest
Suffix array + LCP O(n) SA-IS · O(n log n) doubling O(n) ·~4–8 B/char O(m log n) repeats & distinct counts via LCP — lean, cache-friendly

The practical verdict is nearly always the bottom row. The suffix tree is the clearer mental model and the better asymptotic query; the suffix array ships, because 4n bytes beats 30n bytes and a flat array of integers is what a CPU's cache wants. They are the same information — the array is the tree's leaves in order, and LCP is the tree's internal depths — so you can always think in trees and build in arrays.

Section 10 · Where it breaks

The mistakes that look correct

Formal elegance hides sharp edges. These are the ones that compile, pass the toy test, and then fail on real input.

① The missing sentinel

Drop $ and a suffix can be a prefix of another (na inside nana). Now a suffix ends in the middle of an edge, the suffix↔leaf bijection breaks, occurrence counts via leaf-counting go wrong, and "is P a suffix vs a proper substring?" becomes ambiguous. The sentinel must be unique and lexicographically smallest (so it sorts first and never ties). Forgetting it is the single most common suffix-structure bug.

② Building the suffix trie — the O(n²) trap

"Just insert every suffix into a trie" is correct and unusable: Θ(n²) nodes (a 1 MB text → 1012 nodes). The seductive-but-wrong move is to scale it up. The right move is to compress (suffix tree) or sort (suffix array). Equally, a plain trie with an array of σ children per node burns σ pointers per node — for UTF-32 that is millions of empty slots. Use a hash-map child table for large alphabets.

③ The accidental O(n² log n) suffix array

sorted(range(n), key=lambda i: s[i:]) looks like one line of correctness and is a performance landmine: every key s[i:] materialises an O(n) slice and every comparison scans O(n). That is O(n² log n) time and O(n²) transient memory. Fine for n=10³; it melts at n=10⁶. Use prefix doubling (O(n log n)) or SA-IS (O(n)). The definition "sort the suffixes" is not an implementation.

④ Claiming O(m) for a suffix-array search

Plain binary search on a suffix array is O(m log n), not O(m) — each of the log n probes can re-scan up to m characters. O(m) is the suffix tree's bound, or the array's only with the LCP-augmented Manber–Myers search. Quoting the tree's bound for the array's search is a classic interview slip.

⑤ Off-by-one in the occurrence block & the SA/rank mix-up

The match block is the half-open range [lo, hi); count is hi − lo; lo is a lower bound (first suffix ≥ P) and hi an upper bound (first suffix > P, allowing a higher last char). And: SA maps rank→position while rank (its inverse) maps position→rank. Kasai needs rank; LCP is indexed by rank, with LCP[0] undefined/0. Swapping the two arrays is a silent, classic defect.

⑥ Character signedness & multibyte text

Compare characters consistently: a signed char makes byte 0x80 sort below $, corrupting the order; cast to unsigned and keep the sentinel below all. And "one character" in UTF-8 is several bytes — index suffixes by code units consistently, or an edge label can split a multibyte glyph and your matches drift.

Section 11 · Practice

Build the index yourself

Four problems, escalating from the trie to suffix-array counting. They are stated only — wrestle each one before you read a solution. Track your reasoning; the derivation is the skill, not the final code.

Implement a Trie (prefix tree)

Difficulty MediumTags trie · design

Design a Trie supporting three operations over lowercase words: insert(word) adds a key; search(word) returns true iff the exact word was inserted; startsWith(prefix) returns true iff any inserted key has that prefix.

class Trie: def insert(self, word: str) -> None def search(self, word: str) -> bool def startsWith(self, prefix: str) -> bool

Constraints: 1 ≤ |word|, |prefix| ≤ 2000; lowercase a–z; up to 3·10⁴ total calls. Each call must run in O(|argument|), independent of how many keys are stored.

Example: insert("apple"); search("apple")→true; search("app")→false; startsWith("app")→true; then insert("app"); search("app")→true.

Replace Words

Difficulty MediumTags trie · longest-prefix

You are given a dictionary of root words and a sentence of space-separated words. If a word in the sentence has any root as a prefix, replace it with the shortest such root. If several roots are prefixes, the shortest wins; if none, leave the word unchanged. Return the rewritten sentence.

def replaceWords(dictionary: List[str], sentence: str) -> str

Constraints: 1 ≤ |dictionary| ≤ 1000, each root ≤ 100 chars; sentence has ≤ 1000 words; lowercase letters and single spaces.

Example: dictionary = ["cat","bat","rat"], sentence = "the cattle was rattled by the battery" → "the cat was rat by the bat".

Longest Repeated Substring

Difficulty HardTags suffix array · LCP

Given a string s, return the longest substring that appears at least twice in s (the two occurrences may overlap). If no substring repeats, return the empty string. If several answers tie in length, return any one.

def longestRepeatedSubstring(s: str) -> str

Constraints: 1 ≤ |s| ≤ 3·10⁴, lowercase. An O(n²) enumeration of substrings will time out — build an index.

Example: s = "banana" → "ana" (positions 1 and 3). s = "abcd" → "". s = "aaaa" → "aaa".

Count Distinct Substrings

Difficulty HardTags suffix array · LCP · counting

Given a string s, return the number of distinct non-empty substrings of s.

def countDistinctSubstrings(s: str) -> int

Constraints: 1 ≤ |s| ≤ 10⁵, lowercase. There are up to ≈5·10⁹ substrings counted with multiplicity, so you cannot enumerate them into a set; derive the count from a suffix index.

Example: s = "aaa" → 3 (a, aa, aaa). s = "banana" → 15. s = "abc" → 6.

Attempt each problem before comparing your approach with the invariants and examples above.
Section 12 · Recap & next

The one thing to remember

To search a text many times, stop scanning it and start sorting its suffixes — every substring is the prefix of one of them.

From that single lemma the whole edifice follows. A trie indexes a set of strings for prefix queries in time tied to the query, not the data. Feed it the suffixes and you can answer any substring query — but the raw suffix trie is Θ(n²), so you either compress it (the O(n) suffix tree) or sort it (the O(n)-space suffix array). The LCP array is the bridge between them: it stores the tree's internal depths, and from it the longest repeat and the distinct-substring count fall out in linear time. Think in trees; build in arrays.
